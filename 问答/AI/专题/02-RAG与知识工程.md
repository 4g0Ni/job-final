# 02｜RAG 与知识工程（13 题）

记忆链：**数据进入 → 候选召回 → 排序融合 → 证据门禁 → 生成引用 → 持续评测**。

## RAG-01｜请讲清一个完整的生产 RAG 链路。

**关键词：** ingestion、chunk、index、retrieve、rerank、grounding、eval  
**关联：** RAG-02、RAG-04、RAG-10、RAG-12

**参考答案：** 离线侧做采集、解析、清洗、分块、权限与版本标注、embedding 和倒排/向量索引；在线侧做意图与过滤条件抽取、多路召回、融合、rerank、证据充分性判断，再把少量可引用证据交给生成模型。最后程序化校验引用，并持续记录召回、答案、延迟、成本和坏例。任何一层都必须能单独评测和回滚。

## RAG-02｜文档和代码为什么不能只做固定长度分块？

**关键词：** 语义边界、AST、标题层级、重叠、父子块  
**关联：** RAG-03、RAG-08

**参考答案：** 固定切分会把函数、类、标题、表格或条件上下文切断，造成召回片段无法独立解释。文档应利用标题/段落/表格结构，代码优先按 AST、符号和文件关系切分；长单元可再递归切小，并保留父节点、路径、符号和邻接信息。chunk 大小要用 Recall@K、答案质量和 token 成本共同选择。

## RAG-03｜Embedding、向量库和索引参数怎么选？

**关键词：** 领域、语言、维度、距离、ANN、过滤、可重建  
**关联：** RAG-09、ENG-05、PROJ-07

**参考答案：** 先用真实查询—证据对比较不同 embedding 的 Recall/MRR，而不是只看公开榜单；再依据语料规模、过滤能力、更新频率、P95、成本和运维复杂度选择本地或托管向量库。模型名、维度、归一化、文档模板、query instruction 和索引参数必须进入版本契约；向量索引是可重建派生物，不应成为唯一事实源。

## RAG-04｜BM25 与向量检索为什么要混合？

**关键词：** lexical、dense、错误码、专名、语义差距、互补召回  
**关联：** RAG-05、RAG-06、PROJ-08

**参考答案：** BM25/FTS 擅长错误码、路径、产品名和精确词，dense 擅长同义改写和自然语言症状。二者错误模式不同，混合能提高覆盖，但前提是各通道先独立评测并保留贡献信息。精确 ID 应走 direct lookup，结构化字段走 metadata filter，不要把所有信号都硬塞进向量相似度。

## RAG-05｜RRF 是什么，为什么常用于多路融合？

**关键词：** rank fusion、倒数排名、异量纲、权重、消融  
**关联：** RAG-04、RAG-06、PROJ-09

**参考答案：** RRF 对每个候选累加 `weight / (k + rank)`，依赖名次而不是原始 BM25/cosine 分数，因此适合融合量纲不同的通道。它简单稳健，但不保证混合必胜：权重、候选深度和相关通道会把强单路结果挤出 Top-K。必须对单路、混合和逐 case contribution 做消融，必要时采用 query-aware 权重或 learned fusion。

## RAG-06｜Rerank 为什么可能提高质量却拖慢 P95？

**关键词：** cross-encoder、候选数、批处理、级联、超时  
**关联：** RAG-05、EVAL-08、ENG-09

**参考答案：** Cross-encoder 或 LLM reranker 要对 query—document 对逐一计算，候选数越多，尾延迟和费用越高。常见优化是先用低成本召回缩到合理 Top-N、批量推理、短文本裁剪、按查询难度启用 rerank、设置超时并回退到融合排名。评估要同时看 Recall/nDCG 增益和 P50/P95、吞吐、成本。

## RAG-07｜HyDE、Multi-query 和 Query Rewrite 如何取舍？

**关键词：** 假设文档、查询扩展、召回、漂移、预算  
**关联：** RAG-04、RAG-13

**参考答案：** Query Rewrite 用更清晰的单查询保留原始约束；Multi-query 从多个角度补召回；HyDE 先生成“可能的答案文档”再做 embedding，能跨越短查询与长文档的表达差距。三者都可能引入事实和意图漂移，所以原始 query 必须保留，各路结果需标记来源，并用困难桶评测收益；不能默认所有查询都扩展。

## RAG-08｜Parent-Child / Small-to-Big Retrieval 是什么？

**关键词：** 小块召回、大块生成、上下文完整、去重  
**关联：** RAG-02、RAG-12

**参考答案：** 用小块做 embedding 能提高定位精度，命中后回溯到父段、函数、章节或文档作为生成上下文，从而兼顾召回和可读性。实现时要保存 child→parent 关系、父块版本与权限，合并相邻父块并去重；否则容易重复塞入同一文档、浪费上下文或跨权限扩大内容。

## RAG-09｜为什么 metadata 过滤应尽量前置？

**关键词：** pre-filter、post-filter、ACL、全局 Top-K、漏召回  
**关联：** RAG-03、RAG-11、PROJ-08

**参考答案：** 全局 ANN Top-K 后再过滤，可能把真正满足 repo/date/tenant/ACL 的记录排除在候选池之外。窄条件应先在允许集合中检索，或使用支持过滤的 ANN；权限必须在召回前生效，生成前再次校验。过滤策略也要计入 Eval，否则整体指标可能掩盖某些租户或条件组合的零召回。

## RAG-10｜如何评估 Retriever，而不是只看最终答案？

**关键词：** Recall@K、MRR、nDCG、negative、分桶、gold  
**关联：** EVAL-01、EVAL-03、PROJ-13

**参考答案：** 为每个 query 保存一个或多个 gold evidence，计算 Recall@K、MRR、nDCG，并按精确 ID、自然语言、长查询、过滤条件、OOD 等分桶。还要比较 lexical/dense/hybrid/rerank 消融和逐 case 排名变化。最终答案可能偶然答对，也可能检索正确却生成遗漏，所以 Retriever 与 Answer 必须分层诊断。

## RAG-11｜RAG 如何处理更新、删除、多租户和权限？

**关键词：** CDC、幂等 upsert、tombstone、ACL、tenant、审计  
**关联：** RAG-09、ENG-03、EVAL-11

**参考答案：** 以稳定业务 ID 和版本做幂等 upsert，数据变更通过 CDC/事件或定期扫描同步；删除用 tombstone 先阻断查询，再异步清理倒排、向量和缓存。每个 chunk 继承 tenant、ACL、有效期和来源，召回前按调用者权限过滤，生成与引用阶段复核。跨租户缓存键、日志和评测集也必须隔离。

## RAG-12｜GraphRAG / 知识图谱什么时候值得用？

**关键词：** 实体关系、多跳、社区摘要、构图成本、增量  
**关联：** RAG-01、RAG-08、PROJ-02

**参考答案：** 当问题依赖实体关系、多跳路径、全局主题或跨文档聚合时，图结构能补足平面 Top-K；普通 FAQ、代码符号定位或短文档检索未必需要。要评估实体/关系抽取误差、构图与增量维护成本、权限传播和图检索增益。先建立 vector/lexical baseline，再用多跳 gold set 证明 GraphRAG 的必要性。

## RAG-13｜长查询为何可能让 Dense Retrieval 变差？如何处理？

**关键词：** 信号稀释、噪声、query condensation、字段化、保留约束  
**关联：** LLM-03、RAG-07、PROJ-09

**参考答案：** 很长的工单会混合症状、环境、尝试和无关日志，单个向量把多个意图平均后会稀释关键线索。可抽取标题、错误码、组件、时间和期望行为，生成短主查询与若干字段化子查询，同时保留原文供验证；对长度分桶评测，确认 condensation 的收益和约束保真度。
