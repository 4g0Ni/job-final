# 02｜RAG 与知识工程（13 题）

记忆链：**数据进入 → 候选召回 → 排序融合 → 证据门禁 → 生成引用 → 持续评测**。

## RAG-01｜请讲清一个完整的生产 RAG 链路。

**关键词：** **Ingestion**、**Chunk**、**Index**、**Retrieve**、**Rerank**、**Grounding**、**Eval**  
**关联：** RAG-02、RAG-04、RAG-10、RAG-12

**参考答案：** 我一般把 RAG 分成离线和在线两部分。离线先做**采集、解析、清洗、分块、权限标注、Embedding 和索引**；在线先理解问题和过滤条件，再做**多路召回、融合、Rerank 和证据门禁**，最后只把少量真正相关、可以引用的证据交给模型。回答出来以后还要程序化检查引用，并持续记录召回、答案、延迟、成本和坏例。关键点是每一层都能单独评测，不然出了问题不知道该怪哪一层。

### RAG-01 展开｜每一步具体做什么？

#### 一、离线链路：把原始数据加工成可检索、可追踪的知识

1. **采集（Ingestion）**
	- 从数据库、对象存储、Wiki、工单、代码仓库或第三方 API 拉取数据。
	- 为每份数据保留稳定业务 ID、来源、更新时间、版本和内容哈希，方便做增量同步、去重、删除和审计。
	- 生产环境通常采用全量初始化加 CDC、Webhook 或定时扫描，而不是每次重建整个知识库。

2. **解析（Parsing）**
	- 把 PDF、Word、HTML、Markdown、表格和代码转换成统一的内部结构，而不只是抽取一段纯文本。
	- 尽量保留标题层级、段落、表格、页码、代码符号和链接关系；扫描件还需要 OCR。
	- 解析失败、乱码、空文档要进入隔离队列，避免脏数据直接污染索引。

3. **清洗（Cleaning）**
	- 去掉页眉页脚、导航栏、重复模板、无意义空白和明显乱码，并做格式规范化与近重复检测。
	- 清洗不能过度：错误码、大小写、路径、表格结构等可能正是检索所需的关键信号。
	- 清洗前的原文仍然保留在事实源中，索引内容只是可重建的派生数据。

4. **分块（Chunking）**
	- 文档优先按标题、段落和表格边界切，代码优先按 AST、类、函数和符号关系切，而不是只按固定 token 数切。
	- 太长的语义单元再递归拆分；必要时增加少量重叠，并保留 parent、邻接块、文件路径和章节路径。
	- 可以用小块做召回、命中后回填父块，让定位精度和生成上下文完整性兼顾。

5. **权限与元数据标注（Metadata / ACL）**
	- 每个 chunk 都携带 tenant、用户组、ACL、文档类型、时间、语言、来源和有效期等字段。
	- 权限必须继承自原文档，并在召回前过滤；不能等模型生成后再隐藏，因为那时内容已经泄露给模型。
	- 元数据还用于精确过滤、结果解释、引用回链、生命周期管理和评测分桶。

6. **Embedding**
	- 使用与语种、领域和查询类型匹配的模型，把 chunk 转成向量；有些模型还要求文档与 query 使用不同 instruction。
	- 模型名、维度、归一化方式、输入模板和版本都要记录，变更后通常需要重新计算向量。
	- 选型要用真实的“查询—证据”样本比较 Recall@K、MRR、延迟和成本，而不是只看公开榜单。

7. **建立索引（Indexing）**
	- 通常同时建立倒排索引和向量 ANN 索引，分别支持 lexical 与 dense retrieval，并让元数据字段可过滤。
	- 写入要幂等，旧版本要能替换，删除要通过 Tombstone 立即不可见，再异步清理索引和缓存。
	- 索引参数、Embedding 版本和构建时间都要可追踪，并保证索引能从原始事实源重新构建。

#### 二、在线链路：从用户问题中找到最可靠的证据

8. **问题理解（Query Understanding）**
	- 识别用户意图、关键实体、错误码、时间范围、租户、repo 等显式或隐式条件，并判断是否需要追问。
	- 长查询可以抽取短主查询和字段化子查询，但必须保留原始问题及其约束，防止 Query Rewrite 改变意图。
	- 精确 ID 应走数据库或关键词查询，不必强行进入向量检索；闲聊、无权限或无需检索的问题也可以路由到其他链路。

9. **多路召回（Retrieval）**
	- 并行使用 BM25/FTS、Dense Retrieval，必要时再加入实体、图、SQL 或规则召回。
	- ACL、tenant、时间等过滤尽量前置，避免先取全局 Top-K 再过滤造成符合条件的证据根本没有进入候选池。
	- 每个候选要保留通道、原始分数、排名和查询版本，方便解释与后续消融分析。

10. **融合与去重（Fusion）**
	 - 不直接混加 BM25 分数和 cosine 分数，而是使用 RRF 等方法按排名融合，或先对分数进行可靠校准。
	 - 按文档 ID、chunk ID 或内容哈希去重，合并相邻块，并控制同一文档占据的候选数量。
	 - 融合权重和各通道候选深度要通过离线实验确定，因为混合检索不一定天然优于最强单路。

11. **重排（Rerank）**
	 - 用 Cross-Encoder 或 LLM 对 query 与候选逐对判断，得到比初筛相似度更精细的相关性顺序。
	 - 一般只重排召回后的 Top-N，并采用批处理、级联或条件启用控制 P95 和费用。
	 - Rerank 超时或失败时应回退到融合排序，不能让非核心增强模块拖垮整个问答链路。

12. **证据门禁（Evidence Gate）**
	 - 在进入生成前检查相关性阈值、证据覆盖度、权限、时效性、来源可信度以及证据之间是否冲突。
	 - 证据不足时应追问、换查询重试或明确拒答，而不是让模型依赖内部记忆补出一个看似合理的答案。
	 - 门禁阈值需要按业务风险校准：客服推荐可以相对宽松，合规、医疗或财务场景应更保守。

#### 三、生成与返回：让答案有依据、能核验

13. **上下文组装（Context Construction）**
	 - 在 token 预算内优先放高质量且互补的证据，补充必要的父块或邻接块，同时去掉重复和低信息片段。
	 - 每段证据分配稳定引用 ID，并附带标题、来源、版本等必要信息，但避免把无关元数据塞满上下文。
	 - 证据与用户指令要明确分隔，并把检索内容视为不可信输入，防范文档中的 Prompt Injection。

14. **生成（Grounded Generation）**
	 - Prompt 明确要求模型只依据给定证据回答、逐项标注引用、证据不足就说明不足，并遵守输出格式。
	 - 复杂问题可先生成答案草稿或事实清单，再绑定对应证据；高风险操作仍需规则或人工审批。
	 - 模型参数、Prompt 模板、上下文和输出都要带版本，便于复现问题和比较发布效果。

15. **引用与答案校验（Post-check）**
	 - 程序先检查引用 ID 是否存在、链接是否可访问、用户是否有权限，以及每个关键结论是否至少有一条证据支持。
	 - 进一步可做 claim-evidence entailment、数字一致性、敏感信息和格式检查，但不能只让同一个模型自评后就认为可靠。
	 - 校验失败时可以删除无依据表述、重新生成、降级为证据列表，或者直接返回“证据不足”。

#### 四、持续评测与运营：知道问题究竟出在哪一层

16. **分层评测（Evaluation）**
	 - 数据层看解析成功率、重复率、索引新鲜度和删除生效时间；召回层看 Recall@K、MRR、nDCG 和过滤正确率。
	 - 排序层看重排前后的 nDCG、候选去除率；答案层看正确性、Faithfulness、引用准确率、完整性和拒答质量。
	 - 系统层同时看 P50/P95、吞吐、错误率、token 与模型费用；安全层覆盖越权检索、跨租户泄露和 Prompt Injection。

17. **可观测与坏例闭环（Observability）**
	 - 为一次请求记录 trace ID、查询改写、过滤条件、各路候选、融合与重排结果、最终上下文、模型版本、引用、延迟和成本。
	 - 对失败样本归因：是数据没进入、解析错、没召回、排序错、门禁错、上下文丢失，还是模型没有使用已经找到的证据。
	 - 把线上反馈和典型坏例沉淀进版本化 Gold Set，发布前回归、灰度对比，确认质量收益没有换来不可接受的延迟、成本或安全退化。

**一句话收束：** 完整的生产 RAG 不是“向量检索加一次 LLM 调用”，而是一条从**可治理的数据、可评测的召回排序、可拒答的证据门禁，到可核验生成和持续反馈**的工程链路。

## RAG-02｜文档和代码为什么不能只做固定长度分块？

**关键词：** **语义边界**、**AST**、**标题层级**、**重叠**、**父子块**  
**关联：** RAG-03、RAG-08

**参考答案：** 固定长度切分最大的问题是，它很容易把一个函数、一个类，或者一段表格和标题上下文从中间切开，召回以后片段本身就看不懂。文档我会尽量按**标题、段落和表格结构**切，代码则优先按 **AST、符号和文件关系**切。太长的单元再递归拆小，同时保留父节点、路径和邻接信息。块多大不能拍脑袋，要结合 **Recall@K、回答质量和 token 成本**一起测。

## RAG-03｜Embedding、向量库和索引参数怎么选？

**关键词：** **领域与语言**、**维度**、**距离函数**、**ANN**、**过滤**、**可重建**  
**关联：** RAG-09、ENG-05、PROJ-07

**参考答案：** 我会先拿真实的“查询—证据”样本比较不同 **Embedding** 的 Recall 和 MRR，而不是只看公开榜单。向量库则看语料规模、过滤能力、更新频率、P95、成本和运维复杂度，再决定本地还是托管。还有一个容易漏掉的点：**模型名、维度、归一化、文档模板、Query Instruction 和索引参数都要版本化**。向量索引只是派生数据，坏了应该能重建，不能把它当唯一事实源。

## RAG-04｜BM25 与向量检索为什么要混合？

**关键词：** **Lexical**、**Dense**、**错误码**、**专有名词**、**语义差距**、**互补召回**  
**关联：** RAG-05、RAG-06、PROJ-08

**参考答案：** **BM25/FTS** 和 **Dense Retrieval** 擅长的东西不一样。错误码、文件路径、产品名这种精确词，lexical 往往更稳；用户用自然语言描述症状或者换一种说法，dense 通常更有优势。所以我会让它们互补，但会先单独评测每个通道，保留每个结果是从哪里来的。像 SHA 这种精确 ID 直接查，repo、日期、作者走 metadata filter，不会什么都塞给向量相似度。

## RAG-05｜RRF 是什么，为什么常用于多路融合？

**关键词：** **Rank Fusion**、**倒数排名**、**异量纲**、**权重**、**消融实验**  
**关联：** RAG-04、RAG-06、PROJ-09

**参考答案：** **RRF** 的思路很直观：不直接比较 BM25 和 cosine 这些不同量纲的分数，而是根据每个结果在各通道里的名次，用 `weight / (k + rank)` 累加。它比较简单，也容易解释。但我会特别强调，混合不一定比最强单路好，权重或者候选深度不合适，反而会把好结果挤出 Top-K。所以一定要做**单路、混合和逐 case 贡献的消融**，不能只看一个总分。

### RAG-05 展开｜如何做单路、混合和逐 case 贡献的消融？

1. **单路基线**
	- 在同一份 Gold Set、同一 Top-K 和相同过滤条件下，分别运行 BM25 only、Dense only 以及其他召回通道 only。
	- 统一比较 Recall@K、MRR、nDCG、P95 和成本，先确认每条通道独立擅长和薄弱的查询类型。

2. **混合对比**
	- 保持其他条件不变，依次比较 BM25 + Dense、BM25 + Dense + RRF、Hybrid + Rerank。
	- 再分别调整各路候选深度、RRF 权重和最终 Top-K；每轮只改变一个变量，才能判断收益来自哪里。

3. **逐 case 贡献分析**
	- 对每个 query 比较各方案的 Gold Evidence 命中与排名，将结果归为：单路未命中而混合命中的**互补收益**、都命中但混合排名更高的**排序收益**、结果不变的**无变化**，以及单路命中却被混合挤出 Top-K 的**负贡献**。
	- 再按错误码、自然语言、长查询、过滤条件等类型分桶，统计每条通道新增命中和破坏命中的数量。

| Query 类型 | BM25 | Dense | Hybrid | 结论 |
|---|---:|---:|---:|---|
| 错误码查询 | 命中@1 | 未命中 | 命中@1 | BM25 主贡献 |
| 同义改写 | 未命中 | 命中@3 | 命中@2 | Dense 主贡献，融合提升排名 |
| 文件路径 | 命中@2 | 未命中 | 未命中 | 融合产生负贡献 |

最终不仅要报告“Hybrid Recall@10 提升 3%”，还要说明**提升集中在哪类 query、由哪条通道贡献、牺牲了哪些 case，以及增加了多少延迟和成本**。如果平均分提升但关键业务分桶退化，也不能直接上线。

## RAG-06｜Rerank 为什么可能提高质量却拖慢 P95？

**关键词：** **Cross-Encoder**、**候选数**、**批处理**、**级联**、**超时回退**  
**关联：** RAG-05、EVAL-08、ENG-09

**参考答案：** Rerank 质量更高，是因为 **Cross-Encoder 或 LLM** 会更细地看 query 和每个候选之间的关系；问题是候选越多，计算次数越多，P95 和成本就会上去。我的做法通常是先用便宜的召回把范围缩到合理的 Top-N，再做批量 Rerank；简单查询可以跳过，超时就回退到融合排名。评估时不能只看 nDCG 提升，还要一起看 **P50/P95、吞吐和费用**。

## RAG-07｜HyDE、Multi-query 和 Query Rewrite 如何取舍？

**关键词：** **假设文档**、**查询扩展**、**召回**、**意图漂移**、**预算**  
**关联：** RAG-04、RAG-13

**参考答案：** 我会把三者理解成不同程度的查询改造。**Query Rewrite** 是把原问题说清楚；**Multi-query** 是从多个角度搜；**HyDE** 更激进，它先生成一段“可能长得像答案的文档”，再拿这段去做向量检索。它们都有可能提高召回，也都有**意图漂移**风险。所以原始 query 一定要保留，各路结果要标来源，而且只对确实受益的查询启用，不会默认所有问题都扩写。

### RAG-07 展开｜三种查询改造如何工作和落地？

三者都发生在检索前，改变的是“拿什么去搜”，而不是直接生成最终答案。它们的改造程度依次加深，潜在召回收益、延迟、成本和意图漂移风险也通常依次增加。

#### 1. Query Rewrite：把一个问题改写得更适合检索

- 它通常仍然只生成一个查询，主要用于消除指代、去掉噪声、补全上下文，并突出实体、错误码和核心症状。
- 例如原问题是“我昨天升级以后它就连不上了，日志里有 connection refused”，结合会话可改写为“支付服务升级到 v2.3 后连接 Redis 失败，报错 connection refused”。
- 它适合多轮对话、口语化问题和混有大量排查过程的长工单，但不能把版本、环境、时间范围以及用户明确排除的条件改掉。
- 生产中应同时保存原始 query、改写 query 和抽取出的硬约束；tenant、ACL、时间等条件应使用 metadata filter，而不是交给模型自由改写。

#### 2. Multi-query：从多个互补角度同时搜索

- 它会围绕原问题生成少量不同侧重点的子查询，各自召回候选后再进行去重、融合和重排。
- 例如“为什么升级后支付服务连不上 Redis”可以扩成“升级后 Redis connection refused”“v2.3 Redis 配置变更”“支付服务与 Redis 版本兼容性”等查询。
- 它适合表达模糊、术语不确定或包含多个检索角度的问题，可以减少单个查询措辞碰巧不匹配知识库的风险。
- 代价是检索次数、P95 和费用上升，候选池也会引入更多噪声；子查询过多或彼此同质化，不但没有新增召回，还可能把原本靠前的证据挤出 Top-K。

#### 3. HyDE：先生成假设文档，再用它检索真实文档

- HyDE 全称是 **Hypothetical Document Embeddings**，链路是 `原始问题 → LLM 生成假设文档 → Embedding → 检索真实文档`。
- 用户问题通常较短，而知识库中的答案文档是完整陈述。HyDE 先生成一段“可能像答案”的内容，让检索向量在表达形式和信息密度上更接近真实文档。
- 它适合概念性、描述性问题，以及 query 与文档措辞差异较大的场景；错误码、订单号、SHA、文件路径等精确查询通常应走 BM25、数据库或规则检索。
- **假设文档只是检索媒介，不是事实证据。**它可能虚构原因或术语，因此不能直接作为最终答案依据，也不能替代从知识库召回的真实证据。

#### 4. 如何防止意图漂移？

意图漂移是指查询改造后虽然搜得更多，但搜的已经不是用户原来问的内容。例如原问题限定“Java 17、v2.3、Redis 6”，改写后只剩“Redis 连接失败”；或者 HyDE 擅自假设是 TLS 问题，导致候选全部偏向 TLS。

- 始终保留原始 query，并让原始 query 也参与召回，作为保底通道。
- 将实体、错误码、版本、环境、时间、tenant 和 ACL 等约束结构化，改写前后做约束一致性检查。
- 为每个候选记录 `original`、`rewrite`、`multi-query` 或 `hyde` 等来源，再统一去重、融合和 Rerank，方便回溯贡献与坏例。
- 对高风险、强时效和强约束问题谨慎改写；无法确认用户意图时优先追问，而不是激进扩写。

#### 5. 实际如何取舍？

| 查询类型 | 优先策略 | 原因 |
|---|---|---|
| SHA、订单号、错误码、文件路径 | 原始查询 + 精确检索/BM25 | 关键是字面精确匹配 |
| 长工单、口语化表达、多轮指代 | Query Rewrite | 需要去噪、补全上下文 |
| 表达模糊、存在多个检索角度 | Multi-query | 需要用互补查询扩大召回 |
| 概念性问题、问题与文档语言差异大 | HyDE | 假设文档更接近答案文档的表达 |
| 高风险、强约束、强时效问题 | 原始查询 + 结构化过滤，谨慎改写 | 优先避免约束丢失和错误假设 |

是否启用不能只凭经验判断，应在同一份 Gold Set 上比较 `original only`、`original + rewrite`、`original + multi-query` 和 `original + HyDE`，按查询类型分桶观察 Recall@K、MRR、nDCG、P95 和成本。最终通常不是选一个全局最优方案，而是通过查询路由按需启用。

**一句话收束：** Query Rewrite 是把一个问题说清楚，Multi-query 是从多个角度扩大召回，HyDE 是用假设文档缩小 query 与 document 的语义差距；越激进的改造越需要保留原始查询、锁定硬约束，并用分桶消融证明收益。

## RAG-08｜Parent-Child / Small-to-Big Retrieval 是什么？

**关键词：** **小块召回**、**大块生成**、**上下文完整**、**去重**  
**关联：** RAG-02、RAG-12

**参考答案：** 这个方法可以概括成一句话：**小块负责找准，大块负责讲清楚**。我会给小块做 Embedding，提高定位精度；命中以后，再回到它所属的父段、函数或者章节，把更完整的上下文交给生成模型。实现时要保存 child 到 parent 的关系、版本和权限，还要合并相邻结果并去重，否则很容易重复塞同一篇文档，甚至把不该看到的父内容带进来。

## RAG-09｜为什么 metadata 过滤应尽量前置？

**关键词：** **Pre-filter**、**Post-filter**、**ACL**、**全局 Top-K**、**漏召回**  
**关联：** RAG-03、RAG-11、PROJ-08

**参考答案：** 如果先做全局 ANN Top-K，再按 repo、日期、租户或者 ACL 过滤，真正符合条件的结果可能一开始就没进候选池。所以条件比较窄时，我会优先做 **Pre-filter**，或者使用原生支持过滤的 ANN。权限尤其要在召回前生效，生成前再检查一次。Eval 也要覆盖这些过滤组合，不然总体 Recall 看着不错，某个租户可能其实一条都搜不到。

## RAG-10｜如何评估 Retriever，而不是只看最终答案？

**关键词：** **Recall@K**、**MRR**、**nDCG**、**Negative Case**、**分桶**、**Gold Evidence**  
**关联：** EVAL-01、EVAL-03、PROJ-13

**参考答案：** 我会先给每个 query 标一个或多个 **Gold Evidence**，然后看 **Recall@K、MRR 和 nDCG**。但只看平均值不够，还要按精确 ID、自然语言、长查询、过滤条件和 OOD 分桶，再比较 lexical、dense、hybrid、rerank 的消融结果。因为最后答案可能碰巧答对，也可能检索已经找对了但生成阶段漏掉了，所以 **Retriever 和 Answer 必须分开评**。

## RAG-11｜RAG 如何处理更新、删除、多租户和权限？

**关键词：** **CDC**、**幂等 Upsert**、**Tombstone**、**ACL**、**Tenant**、**审计**  
**关联：** RAG-09、ENG-03、EVAL-11

**参考答案：** 更新这块我会用稳定业务 ID 和版本做**幂等 Upsert**，数据变化通过 CDC、事件或者定期扫描同步。删除时先写 **Tombstone** 让它立刻查不到，再异步清理倒排、向量和缓存。每个 chunk 都要带 tenant、ACL、有效期和来源，召回前按用户权限过滤，生成和引用阶段再复核。缓存、日志和评测集也要按租户隔离，不然检索隔离做对了，旁路还是可能泄露。

### RAG-11 展开｜更新、删除和权限隔离具体如何落地？

这类问题要先区分三层：**原始事实源**保存权威内容，倒排与向量索引是可以重建的派生数据，身份与权限系统则是授权判断的权威来源。索引更新可以短暂最终一致，但旧版本覆盖新版本、已删除内容重新出现、越权内容进入模型上下文，这三件事不能接受。

#### 1. 更新：稳定身份、版本控制和幂等写入

- 每份文档至少带 `tenant_id`、稳定的 `document_id`、单调递增的 `version`、`content_hash`、`updated_at` 和 `acl_version`；每个 chunk 再带 `chunk_id`、parent、来源位置和 Embedding 版本。
- 变更可以由 CDC、Webhook、消息事件触发，定期扫描负责兜底对账。事件只表达“哪份数据变了”，消费者仍从事实源读取指定版本，避免把消息体当成新的事实源。
- 解析、分块和 Embedding worker 可以重复消费同一事件，但写入键与版本判断必须保证幂等；相同版本重复执行结果不变，低版本事件晚到时直接丢弃，防止消息乱序让旧内容覆盖新内容。
- 对一份文档包含多个 chunk 的情况，先完整写入新版本，再原子切换 `active_version` 或版本清单，最后异步回收旧版本。这样不会在更新中途同时看到“半份新文档”和“半份旧文档”。
- `content_hash` 未变化时可以跳过解析和 Embedding；只修改 ACL 时通常只更新权限元数据或授权控制面，不必重新计算向量，但这类事件应高优先级传播。
- 失败任务进入重试和死信队列，并通过周期性 reconciliation 比较事实源版本与索引版本。不能只相信消息一定送达，也不能靠人工发现漏同步。

一条典型链路可以表示为：

`事实源提交 v8 → CDC 事件 → 解析/分块/Embedding → 写入 v8 全部派生索引 → 切换 active_version=v8 → 失效缓存 → 回收 v7`

#### 2. 删除：先阻断可见性，再做物理清理

删除不能只向向量库发一个异步 delete 请求，因为事件传播、索引刷新和缓存过期之间都有窗口。更稳妥的顺序是：

1. 在权威状态表或删除控制面写入带版本的 **Tombstone**，并同步失效相关缓存。
2. 检索入口只允许 `active` 文档参与查询；候选返回后再检查一次 Tombstone，确保旧索引副本中的残留结果也不会进入模型上下文。
3. 发布删除事件，异步清理倒排索引、向量索引、父子块、图关系、派生摘要、缓存和临时对象。
4. 记录各存储层的清理状态，超过删除传播 SLO 就告警，并由对账任务清除孤儿 chunk。

Tombstone 也要参与版本比较。例如文档已经删除到 v8，迟到的 v7 Upsert 不能把它复活；如果业务要恢复文档，应显式产生更高版本的 Undelete/Upsert。涉及合规删除时，还要按保留策略处理快照、备份、导出文件和日志，而不只是在线索引。

所谓“立刻查不到”，准确地说是**在线查询路径立即拒绝返回**，物理数据可以稍后清理。如果查询路径根本不检查 Tombstone，只是把它写进消息队列，就不能声称删除已经立即生效。

#### 3. 多租户：按风险选择隔离强度

| 方案 | 做法 | 适用情况 | 主要代价或风险 |
|---|---|---|---|
| 共享索引 | 所有记录强制携带 `tenant_id`，使用向量库原生 Pre-filter | 租户多、规模较小、成本敏感 | 最依赖过滤正确性，必须做跨租户负向测试 |
| 独立 namespace / collection | 每个租户或安全域单独建命名空间、索引和密钥 | 中等隔离要求、租户规模可控 | 索引数量、连接和运维复杂度上升 |
| 独立账号 / 集群 | 计算、存储、网络和密钥都物理隔离 | 金融、政企等高敏或强合规场景 | 成本最高，容量利用率较低 |

无论使用哪种方案，`tenant_id` 都应从经过验证的登录态或服务凭证中由服务端注入，不能让用户在 Prompt 中声明自己属于哪个租户。数据库主键、对象存储路径、队列 topic、索引 namespace、缓存键和限流统计也都要包含租户边界，避免只在向量检索这一层做隔离。

#### 4. ACL：检索前过滤，生成前和引用时复核

- 权限通常来自用户、组、角色、部门、资源 ACL 和环境属性，可以采用 RBAC、ABAC 或二者组合。chunk 默认继承文档权限，并记录权限版本；`deny` 应优先于 `allow`。
- 检索服务根据可信身份生成授权过滤条件，把 tenant、可访问用户组、有效期和文档状态作为 **Pre-filter** 送入 lexical 与 vector 通道。不能先做全局 Top-K 再过滤，否则不仅有安全风险，还会因为合法候选没进 Top-K 而降低召回。
- 候选进入上下文前再次调用授权判断或校验授权快照；Parent-Child 回填、相邻块扩展、GraphRAG 多跳和 Rerank 都不能越过这个边界。命中的 child 有权限，不代表整个 parent 一定有权限。
- 返回引用、原文预览和下载链接时还要实时复核，防止用户拿着旧引用访问权限已经撤销的文档。ACL 变更应优先失效缓存，并通过 `acl_version` 阻止旧授权结果继续使用。
- 如果检索后端无法可靠做 ACL Pre-filter，应该按安全域拆索引或更换实现；扩大候选数再做 Post-filter 只能缓解召回问题，不能替代进入模型前的强制授权检查。

#### 5. 旁路也必须隔离

- **缓存：** Key 至少包含 tenant、查询、过滤条件、索引版本和授权指纹；用户权限不同就不能共享同一份答案缓存。ACL 变更和删除时要主动失效，TTL 只是兜底。
- **日志与 Trace：** 默认不记录完整文档、Embedding、Prompt 和答案，确需留存时应脱敏、加密、限权并设置保留期。运维人员能看日志，不等于可以看所有租户原文。
- **评测与标注：** Gold Set、坏例平台和人工标注任务同样带 tenant 与 ACL；跨租户汇总时只使用脱敏指标或获得明确授权的数据。
- **其他派生面：** 消息队列、对象存储暂存区、离线数仓、搜索建议、导出文件和备份都可能形成泄露旁路，需要沿用同一租户边界与删除策略。

#### 6. 如何证明方案真的有效？

- **更新测试：** 重放同一事件、让 v7 晚于 v8 到达、在多 chunk 写入中途注入故障，确认线上始终只读取完整的最高有效版本。
- **删除测试：** 分别检查倒排、向量、缓存、父块和引用接口，统计 `delete_visibility_lag` 与物理清理耗时，并验证迟到 Upsert 不会复活文档。
- **权限测试：** 构造“不同租户、同租户不同组、权限刚撤销、Parent-Child 跨边界”等矩阵，确认未授权内容不会出现在候选、上下文、答案或引用中。
- **监控与审计：** 关注 CDC lag、索引新鲜度、版本不一致数、死信数量、孤儿 chunk、缓存失效失败和授权拒绝率；审计记录谁在何时以什么身份访问了哪份资源以及授权结果，但避免在审计日志中复制敏感正文。

**一句话收束：** 内容更新靠“稳定 ID + 单调版本 + 幂等消费 + 对账”，删除靠“Tombstone 先阻断、物理数据后清理”，权限靠“可信身份注入 + 检索前过滤 + 全链路复核”，并把缓存、日志、评测和备份全部纳入同一隔离边界。

## RAG-12｜GraphRAG / 知识图谱什么时候值得用？

**关键词：** **实体关系**、**多跳问题**、**社区摘要**、**构图成本**、**增量维护**  
**关联：** RAG-01、RAG-08、PROJ-02

**参考答案：** 我不会看到知识库就上 **GraphRAG**。如果问题真的依赖实体关系、多跳路径、全局主题或者跨文档聚合，图结构才比较有价值；普通 FAQ、代码符号定位或者短文档检索，平面的 lexical/vector 往往够用。要上图的话，我会先算清楚实体关系抽取误差、构图和增量成本、权限传播，再用**多跳 Gold Set**证明它比基线好。

## RAG-13｜长查询为何可能让 Dense Retrieval 变差？如何处理？

**关键词：** **信号稀释**、**噪声**、**Query Condensation**、**字段化**、**保留约束**  
**关联：** LLM-03、RAG-07、PROJ-09

**参考答案：** 很长的工单通常把症状、环境、排查过程和大量日志混在一起，一个向量把这些信息平均以后，真正关键的信号反而会被稀释。我的做法是抽出**标题、错误码、组件、时间和期望行为**，生成一个短主查询和几个字段化子查询，同时保留原文用于最后验证。然后按查询长度分桶，看 **Query Condensation** 到底有没有提升召回、有没有改坏原始约束。
