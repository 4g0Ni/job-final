# 01｜LLM 与上下文工程（9 题）

记忆链：**模型如何生成 → 上下文如何承载 → 输出如何约束 → 训练/选型如何决策**。

## LLM-01｜为什么主流生成式大模型多采用 Decoder-only？

**关键词：** **自回归**、**因果掩码**、**统一目标**、**Scaling**、**KV Cache**  
**关联：** LLM-02、LLM-03、ENG-05

**参考答案：** 我会先说结论：**Decoder-only 最适合把生成任务统一起来**。它从预训练到对话、代码、工具调用，基本都在做“预测下一个 token”，所以训练链路比较简单，也更容易做大规模扩展。推理时它还能配合 **KV Cache** 复用前面的计算，特别适合连续生成。不过我不会说它对所有任务都最好，像纯编码、双向理解或者强条件生成，**Encoder** 或 **Encoder-Decoder** 还是可能更合适。

**易错点：** 不要说“Decoder-only 能看到未来 token”；训练时有整段输入，但因果掩码禁止关注未来位置。

## LLM-02｜Causal LM、Prefix LM 与 Encoder-Decoder 有什么区别？

**关键词：** **Attention Mask**、**前缀双向**、**因果生成**、**条件生成**  
**关联：** LLM-01、LLM-03

**参考答案：** 这三个概念我一般从“**每个 token 能看到什么**”来区分。**Causal LM** 只能看左边；**Prefix LM** 的前缀内部可以互相看，但真正开始生成以后还是只能看左边；**Encoder-Decoder** 则是 Encoder 先双向理解输入，Decoder 再通过交叉注意力生成。面试里我还会补一句：除了结构，还要比较它们的**训练目标、缓存方式和适用任务**。

### 详细理解

这道题难点在于：**三者都能“输入一段内容，再生成一段内容”**，真正不同的是它们内部如何组织信息。

先抓住一句话：

> **Causal LM 和 Prefix LM 主要是注意力遮罩不同；Encoder-Decoder 则连模型结构都不同。**

假设任务是：

- 输入：`把“今天天气很好”翻译成英文`
- 输出：`The weather is nice today`

把输入叫作**前缀区**，把答案叫作**生成区**。

#### 1. Causal LM：整条序列都只能向左看

典型的 Decoder-only 大模型采用这种形式。

把所有 token 排成一条序列：

```text
[输入 A] [输入 B] [输入 C] | [输出 X] [输出 Y]
```

每个位置只能看到自己和左边：

```text
A 能看：A
B 能看：A、B
C 能看：A、B、C
X 能看：A、B、C、X
Y 能看：A、B、C、X、Y
```

对应的是下三角形因果掩码：

| 当前 token | A | B | C | X | Y |
|---|---:|---:|---:|---:|---:|
| A | ✓ |  |  |  |  |
| B | ✓ | ✓ |  |  |  |
| C | ✓ | ✓ | ✓ |  |  |
| X | ✓ | ✓ | ✓ | ✓ |  |
| Y | ✓ | ✓ | ✓ | ✓ | ✓ |

训练时，模型可以一次拿到完整句子，但掩码会防止当前位置偷看未来答案。

这里的“只能看左边”**不是说生成答案时看不到完整问题**。生成第一个答案 token 时，整个问题都已经位于它左边，所以它能看到完整问题。只是问题中靠前 token 的内部表示不能反过来读取靠后的 token。

#### 2. Prefix LM：输入前缀双向看，答案仍然向左看

Prefix LM 把序列分成两个区域：

```text
[前缀 A B C] | [生成 X Y]
```

它的可见规则是：

```text
A、B、C：彼此都能看
X：能看完整前缀，以及当前/之前的生成内容
Y：能看完整前缀，以及 X、Y
```

对应关系如下：

| 当前 token | A | B | C | X | Y |
|---|---:|---:|---:|---:|---:|
| A | ✓ | ✓ | ✓ |  |  |
| B | ✓ | ✓ | ✓ |  |  |
| C | ✓ | ✓ | ✓ |  |  |
| X | ✓ | ✓ | ✓ | ✓ |  |
| Y | ✓ | ✓ | ✓ | ✓ | ✓ |

它和 Causal LM 最核心的区别是：

- Causal LM 中，前缀内部也只能向左看。
- Prefix LM 中，前缀内部可以双向理解。
- 两者进入生成区后，都不能偷看未来答案。

可以把 Prefix LM 理解为：

> **前半段像 Encoder 一样阅读，后半段像 Decoder 一样生成，但通常仍可以放在同一套 Transformer 中，通过 Attention Mask 实现。**

注意，这里的 Prefix LM 是一种**注意力可见性设计**，不要和日常所说的“给 Decoder-only 模型写一个 prompt 前缀”完全混为一谈。

#### 3. Encoder-Decoder：输入和输出由两套模块处理

它不是把所有内容简单放在同一条序列里，而是分为两部分：

```text
输入 → Encoder → 输入表示
					↓ Cross-Attention
输出 ← Decoder 逐 token 生成
```

Encoder：

- 读取完整输入。
- 输入 token 之间可以双向注意。
- 每个 token 都能结合左右两边的信息。

Decoder：

- 对已生成的答案使用因果自注意力，只能看答案左侧。
- 通过 **Cross-Attention（交叉注意力）**读取 Encoder 的全部输出。

Decoder 中实际上有两种注意力：

1. **Masked Self-Attention**：查看已经生成的答案。
2. **Cross-Attention**：查看完整输入的编码结果。

例如生成 `weather` 时，它可以：

- 通过自注意力看到前面生成的 `The`。
- 通过交叉注意力查看完整中文输入。

#### 4. 为什么 Prefix LM 不等于 Encoder-Decoder？

虽然二者都允许“输入部分双向看”，但实现结构不同。

| 维度 | Causal LM | Prefix LM | Encoder-Decoder |
|---|---|---|---|
| 模型结构 | 单个 Transformer/Decoder | 通常是单个 Transformer | 独立 Encoder 和 Decoder |
| 输入内部 | 因果、向左看 | 双向看 | Encoder 中双向看 |
| 输出内部 | 因果生成 | 因果生成 | Decoder 中因果生成 |
| 如何读取输入 | 同一序列中的自注意力 | 同一序列中的自注意力 | Decoder 的交叉注意力 |
| 常见优势 | 通用生成、缓存简单 | 兼顾输入理解和生成 | 输入输出职责清晰 |
| 常见场景 | 对话、代码、Agent | 条件生成、统一建模 | 翻译、摘要、转换任务 |

#### 5. “训练目标、缓存方式和适用任务”是什么意思？

**训练目标**

Causal LM 通常对整段文本做下一个 token 预测：

$$
P(x)=\prod_t P(x_t\mid x_{<t})
$$

Prefix LM 通常给定完整前缀，只计算或重点计算生成区的预测损失：

$$
P(y\mid x)=\prod_t P(y_t\mid x,y_{<t})
$$

Encoder-Decoder 也是条件生成，但输入先由 Encoder 单独编码：

$$
P(y\mid x)=\prod_t P(y_t\mid y_{<t},\operatorname{Encoder}(x))
$$

**缓存方式**

- Causal LM：历史 token 的 K/V 可以按顺序直接追加，KV Cache 最自然。
- Prefix LM：先一次性计算双向前缀，再缓存前缀 K/V；生成区继续因果追加。
- Encoder-Decoder：Encoder 输出只计算一次；Decoder 缓存历史答案的 K/V，并反复通过交叉注意力读取 Encoder 输出。

**适用任务**

- Causal LM：开放式生成、聊天、代码补全、Agent。
- Prefix LM：希望先充分理解一段给定输入，再继续生成。
- Encoder-Decoder：翻译、摘要、改写等输入输出边界清晰的任务。

面试时可以压缩成下面这段：

> 三者核心区别是信息可见性和模型结构。Causal LM 对整条序列使用因果掩码，每个 token 只能看左侧；Prefix LM 让输入前缀内部双向注意，但生成区仍保持因果注意；Encoder-Decoder 则用 Encoder 双向编码输入，Decoder 一边因果读取已生成内容，一边通过交叉注意力读取完整输入。前两者主要是 Attention Mask 的差异，Encoder-Decoder 则是双模块结构。

## LLM-03｜RoPE、上下文窗口和“无限长输入”是什么关系？

**关键词：** **相对位置**、**长度外推**、**训练分布**、**注意力成本**、**检索**  
**关联：** LLM-04、RAG-13

**参考答案：** **RoPE** 解决的是位置信息怎么进入注意力，它对表达相对距离很有帮助，但不等于模型突然就有了无限上下文。实际窗口还会受训练长度、外推效果、**KV Cache 显存**和注意力计算成本限制。所以工程上我通常先做**检索、摘要、压缩和证据筛选**，最后才考虑把窗口加大，因为“放得进去”和“模型真的用得好”是两回事。

### 详细理解

这道题其实在问三个层次：

1. **RoPE：模型怎么知道 token 的位置**
2. **上下文窗口：模型一次最多能接收多少 token**
3. **无限长输入：模型能否无限接收并有效利用信息**

三者有关联，但不是一回事。

#### 1. RoPE 解决什么问题

Transformer 的 Attention 本身只计算 token 之间的相关性，并天然不知道顺序。

例如：

```text
猫吃鱼
鱼吃猫
```

如果完全没有位置信息，两句话包含相同 token，模型就很难区分顺序。因此需要把位置注入 Attention。

RoPE，全称 **Rotary Position Embedding（旋转位置编码）**，会根据 token 所在位置，对它的 Query 和 Key 向量进行旋转：

$$
Q_m=R_mQ,\qquad K_n=R_nK
$$

其中：

- $m,n$ 是两个 token 的位置。
- $R_m,R_n$ 是由位置决定的旋转矩阵。
- 位置越不同，旋转角度也越不同。

计算 Attention 时：

$$
Q_m^\top K_n=(R_mQ)^\top(R_nK)
$$

经过化简，它主要与位置差 $n-m$ 有关。因此 RoPE 很适合表达：

> 当前 token 和另一个 token 相隔多远。

这就是所说的**相对位置信息**。

可以直观理解为：

> RoPE 给每个 token 的 Q/K 装上一个随位置旋转的“方向标”，模型比较两个方向时，就能感知二者的相对距离。

#### 2. 什么是上下文窗口

上下文窗口是模型一次推理过程中能够处理的最大 token 数量。

例如一个模型支持 128K 上下文，通常意味着：

```text
输入 token 数 + 已生成 token 数 ≤ 128K
```

假设：

- Prompt 占 120K token。
- 模型最多还可以生成约 8K token。

输入和输出一般共享同一个上下文预算，具体取决于服务接口和模型配置。

上下文窗口不仅由 RoPE 决定，还受到多方面限制：

| 限制 | 含义 |
|---|---|
| 模型配置 | 服务端或模型设定的最大序列长度 |
| 训练长度 | 模型训练时实际见过多长的序列 |
| 位置编码 | 超过训练长度后，位置表示是否仍然稳定 |
| Attention 成本 | 输入越长，注意力计算越昂贵 |
| KV Cache | 每层都要保存历史 token 的 K/V |
| 服务限制 | API 可能限制输入、输出或总 token 数 |

所以 RoPE 只是影响窗口能力的因素之一。

#### 3. 为什么 RoPE 不能自动实现无限上下文

假设模型训练时最长只见过 8K token，现在直接输入 100K token。

从数学形式上看，RoPE 可以继续为第 8001、8002 乃至更远的位置计算旋转角度。但这只说明：

> **位置编号还能算出来。**

并不说明：

> **模型理解和利用这些位置的能力仍然可靠。**

原因主要有四个。

**训练分布外推**

模型训练时只学过 8K 范围内的旋转模式和距离关系。突然遇到 100K 的位置和距离，相当于出现了训练中没见过的分布，Attention 可能变得不稳定。

这叫作**长度外推**：

> 模型能否在超过训练长度的序列上保持能力。

RoPE 有一定相对位置表达能力，但不保证无限外推。

**Attention 计算成本**

标准全量 Self-Attention 对长度为 $n$ 的输入，需要构建 $n\times n$ 的注意力关系。

Prefill 阶段的计算量大致是：

$$
O(n^2)
$$

如果上下文长度扩大 10 倍，注意力相关计算可能接近扩大 100 倍。即使使用 FlashAttention 降低显存和常数开销，也没有从根本上把全量注意力变成无限低成本。

**KV Cache 显存**

生成阶段要缓存历史 token 在每一层的 Key 和 Value，其占用大致随上下文长度线性增长：

$$
	ext{KV Cache}\propto
	ext{层数}\times\text{token 数}\times\text{KV 维度}
$$

上下文越长、并发请求越多，KV Cache 消耗的 GPU 显存越大。

而且 KV Cache 只避免重复计算历史 K/V。生成新 token 时，当前 Query 通常仍要读取大量历史 K/V，所以长上下文的单步解码仍会变慢。

**有效利用能力**

即使内容能够放进窗口，模型也不一定能正确找到并使用它。

例如把一个关键事实放在 100K token 文档的中间，模型可能：

- 忽略中间信息，即“Lost in the Middle”。
- 混淆相似证据。
- 更关注最近内容。
- 被无关文本干扰。
- 找到证据却没有正确引用。

因此需要区分：

- **可容纳长度**：API 允许放多少 token。
- **有效上下文长度**：模型能够稳定检索、理解和使用多少 token。

“能塞进去”不等于“能用得好”。

#### 4. RoPE 如何帮助扩展窗口

虽然 RoPE 不会自动提供无限上下文，但可以通过一些方法改善长度外推。

常见方法包括：

- **位置插值（Position Interpolation）**：把更长的位置压缩到训练时熟悉的范围。
- **RoPE Scaling**：调整旋转频率，减缓长距离位置的角度变化。
- **NTK-aware Scaling**：针对不同频率维度调整缩放方式。
- **YaRN 等方法**：组合插值、频率调整和训练校准。
- **长上下文继续训练**：让模型真正接触更长序列，而不只是修改配置。

例如原模型训练长度是 8K，现在希望支持 32K，可以把 32K 的位置范围映射到原来较熟悉的尺度，再用长序列继续训练或微调。

但这些方法仍然是在：

> **扩大可用窗口并改善外推。**

而不是实现真正的无限上下文。

#### 5. 工程上为什么先做检索和压缩

假设用户有一百万 token 的资料。直接全部送给模型通常不是最佳选择：

- 成本高。
- 延迟高。
- KV Cache 占用大。
- 无关信息会干扰模型。
- 关键信息未必能被稳定定位。

更实际的处理流程是：

```text
原始长资料
	↓
切分、索引
	↓
根据问题检索候选证据
	↓
重排和去重
	↓
摘要、压缩、保留引用
	↓
把最相关证据送入模型
```

长对话也类似：

```text
系统规则：保留原文
当前任务：保留结构化状态
最近对话：直接保留
较早对话：压缩成摘要
外部知识：按需检索
工具输出：只保留必要字段
```

核心目标不是追求“塞入最多内容”，而是：

> 在有限 token 预算内，送入最相关、可信、可追溯的信息。

#### 6. 三者关系总结

可以把它们理解成：

```text
RoPE
解决“位置怎么表示”
		  ↓
影响模型的长度外推能力
		  ↓
但上下文窗口还受训练、配置、算力和显存限制
		  ↓
扩大窗口也不代表模型能稳定利用全部内容
		  ↓
因此不能由 RoPE 推导出“无限长输入”
```

面试时可以这样回答：

> RoPE 是一种把位置信息注入 Q/K 的旋转位置编码，它能够较自然地表达 token 的相对距离，并为长度外推提供基础，但不会自动产生无限上下文。模型的实际窗口还受配置、训练长度、外推稳定性、Attention 计算量和 KV Cache 显存限制。即使文本能够放进窗口，模型也可能出现中间信息遗失和证据混淆。因此生产系统通常先通过检索、重排、摘要和压缩构造高质量工作上下文，再考虑使用 RoPE Scaling 和长上下文训练扩大窗口。

## LLM-04｜长对话怎样做 Context Engineering？

**关键词：** **Working Set**、**压缩**、**摘要**、**检索**、**预算**、**来源**  
**关联：** LLM-03、MCP-06、MCP-07、EVAL-08

**参考答案：** 我不会把整段历史一股脑塞进去，而是先把上下文拆成**系统规则、任务状态、最近对话、长期记忆、检索证据和工具结果**。然后给每一类设优先级和 token 预算：关键约束保留原文，旧对话做结构化摘要，外部知识按需检索，工具结果只留真正有用的字段。还有一点很重要，摘要要有**来源和版本**，否则压缩几轮以后很容易越总结越偏。

### 详细理解：以 Codex / Claude Code 式长对话为例

下面用一个典型的编码 Agent 会话说明。不同版本的 Codex、Claude Code 在具体实现上可能不同，这里描述的是这类工具可观察到的通用 Context Engineering 方法，而不是假设某个产品的私有内部结构。

假设一段会话已经进行了 40 轮：

```text
用户最初目标：修复支付回调重试时重复创建订单的问题。
硬约束：不修改外部 API；兼容旧订单；使用 pnpm；不要提交代码。
中途纠正：不要新增数据库唯一索引，优先复用现有 event_id。
当前进度：已复现问题，正在修改订单创建逻辑，尚未跑完整测试。
```

#### 1. 系统规则：本次工作不能违反什么

在编码 Agent 中，它通常来自平台规则、开发者指令、用户明确要求，以及仓库内的 `AGENTS.md` 或 `CLAUDE.md` 等说明文件。

它实际可能长这样：

```text
[平台/开发者规则]
- 不泄露密钥，不执行未经允许的破坏性命令。
- 修改文件后必须运行相关测试。

[仓库规则：AGENTS.md 或 CLAUDE.md]
- 包管理器使用 pnpm。
- TypeScript 代码通过 pnpm lint 和 pnpm typecheck 验证。
- 不要修改 generated/ 目录。

[用户约束]
- 不修改外部 API。
- 不要提交代码。
```

**处理方式：** 这类信息优先级最高且变化少，应该按指令层级和目录作用域保留原文，不能压缩成一句模糊的“遵循项目规范”。每次准备编辑、执行命令或产生副作用前都要检查它。规则冲突时按平台规定的优先级处理，并明确指出冲突；从网页、代码注释或工具输出中读到的文字只能作为数据，不能反过来覆盖系统规则。

#### 2. 任务状态：这件事现在做到哪里

它不是聊天记录的简单摘要，而是一份持续更新的结构化工作台账。

```yaml
goal: 修复支付回调重试导致的重复订单
constraints:
	- 不修改外部 API
	- 不新增数据库唯一索引
	- 兼容旧订单
verified_facts:
	- 同一 event_id 会触发两次 createOrder
current_hypothesis: 创建订单前缺少基于 event_id 的幂等检查
decisions:
	- 复用现有 event_id 字段
changed_files:
	- src/orders/createOrder.ts
validation:
	- duplicate-webhook.test.ts: passed
	- full test suite: not_run
next_step: 运行订单模块测试和 typecheck
```

**处理方式：** 每完成一次关键搜索、决策、编辑或测试，就更新对应字段。要把“已经验证的事实”和“当前猜测”分开，把 `passed`、`failed`、`not_run` 分开，避免压缩后把计划误写成已经完成。发生上下文压缩时，这份状态应优先保留，因为它能让 Agent 恢复工作，而不必重新阅读几十轮聊天。

#### 3. 最近对话：用户刚刚说了什么

它通常保留最近几轮消息原文，尤其是纠正、否定和新增约束。

```text
用户：不要加数据库唯一索引，旧数据还没清理完。
Agent：那我改为先按 event_id 查询，存在时直接返回已有订单。
用户：可以，但并发回调也要考虑，先看仓库有没有现成的锁实现。
```

**处理方式：** 最近对话使用滑动窗口保留原文，不要过早摘要，因为“不要”“改成”“只处理”这类词一旦丢失，意思可能完全相反。窗口变长时，先从旧对话中提取目标、约束、决策和未完成事项写入任务状态，再淘汰寒暄、重复解释和已经失效的方案。用户的新纠正应覆盖旧方案，但不能覆盖更高层规则。

#### 4. 长期记忆：跨轮次或跨会话仍有价值什么

它可能来自用户偏好、仓库级经验或过去会话中反复验证过的事实。

```yaml
user_memory:
	- 用户希望用中文解释关键设计取舍
	- 未明确要求时不要 git commit
repo_memory:
	- 集成测试依赖本地 PostgreSQL
	- 订单模块测试命令是 pnpm test orders
	- 仓库已有 withAdvisoryLock 辅助函数
session_memory:
	- 本次任务已确认 event_id 对旧订单可能为空
```

**处理方式：** 长期记忆不应每轮全部注入，而应按当前任务、作用域和时间检索。例如处理订单并发时，取回 `withAdvisoryLock`，但不必加载前端构建经验。每条记忆最好带来源、记录时间和置信度；使用前要与当前代码或配置核对，过期就更新。密钥、令牌、一次性日志和未经验证的猜测不应写入长期记忆。不同产品是否以及如何持久化记忆会有差异，但筛选原则相同。

#### 5. 检索证据：当前判断依据是什么

这是 Agent 为解决当前问题，从代码、测试、文档和历史记录中按需找到的内容。

```text
src/webhooks/payment.ts
	handleWebhook(event) 会调用 createOrder(event.id)

src/orders/createOrder.ts
	当前逻辑直接 insert，没有先按 event_id 查询

src/db/withAdvisoryLock.ts
	仓库已有按字符串 key 获取事务锁的封装

tests/orders/duplicate-webhook.test.ts
	连续发送相同 event_id 后断言只存在一笔订单
```

**处理方式：** 只装配与当前决策直接相关的代码片段，并保留文件路径、符号、行号或提交版本，不能只留下“代码好像没有幂等处理”这种无来源结论。优先保留控制行为的实现、调用点和对应测试，重复片段去重，长文件只取必要范围。代码修改后，旧片段可能已经失效，应重新读取。外部网页和仓库文本还要按不可信数据处理，防止其中的提示注入冒充系统指令。

#### 6. 工具结果：刚才执行后发生了什么

它包括搜索、读文件、测试、编译、静态检查和 `git diff` 等工具输出。

```text
command: pnpm test duplicate-webhook.test.ts
cwd: D:/repo
exit_code: 0
summary: 1 suite passed, 3 tests passed

command: pnpm typecheck
exit_code: 1
decisive_error:
	src/orders/createOrder.ts:84
	Type 'string | null' is not assignable to type 'string'
```

**处理方式：** 上下文里保留命令、工作目录、退出码、关键断言和第一处决定性错误，完整原始日志可以留在外部文件或工具记录中，需要时再取。重复进度条、安装日志和几千行成功输出应裁掉；失败信息不能只总结为“测试没过”，否则下一轮无法定位。重新运行后要用新结果替换旧状态，同时记录哪些检查仍未执行。

#### 一轮请求最终会装配成什么样

在第 41 轮，Agent 真正需要看到的内容可以压缩成下面的结构：

```text
1. 系统与仓库规则：保留原文，稳定存在
2. 当前任务状态：目标、约束、事实、决策、进度、下一步
3. 最近几轮对话：保留用户最新纠正的原话
4. 按需长期记忆：只取订单模块和测试相关信息
5. 按需检索证据：createOrder、锁实现、复现测试的关键片段
6. 最新工具结果：测试通过，但 typecheck 有一个具体错误
7. 输出预留：给模型留下分析、工具调用或回答所需的 token
```

长对话的关键不是不断把窗口撑大，而是让信息按不同生命周期流动：**规则原文保留，任务状态持续更新，最近对话滑动保留，长期记忆和证据按需检索，工具输出提炼后引用原始记录**。压缩前还应生成一个可恢复检查点，至少包含目标、硬约束、已验证事实及来源、已做决策、改动文件、测试结果和未完成事项；压缩后再用当前代码、`git diff` 和测试结果校验摘要，避免摘要漂移。

## LLM-05｜Context Engineering 与 Prompt Engineering 有何区别？

**关键词：** **指令**、**证据**、**状态**、**工具**、**动态装配**  
**关联：** LLM-04、AGENT-03、RAG-01

**参考答案：** 简单说，**Prompt Engineering** 更像是在研究“这句话怎么问”，而 **Context Engineering** 关心的是“这一轮到底给模型看什么”。除了指令，它还包括历史、状态、记忆、检索证据、工具 schema、工具结果和输出格式。实际做 Agent 时，很多问题不是 prompt 写得不漂亮，而是**上下文给错了、给多了，或者证据顺序不对**。

## LLM-06｜如何处理结构化输出不稳定？

**关键词：** **JSON Schema**、**约束解码**、**服务端验证**、**修复**、**有界重试**  
**关联：** AGENT-06、AGENT-07、EVAL-03

**参考答案：** 我的做法是先尽量使用模型原生的 **Structured Output** 或 **Function Calling**，再给一个尽可能窄的 **JSON Schema**。但模型返回以后，服务端还是要重新检查类型、枚举、范围和业务规则。解析失败时先做确定性修复，再把错误摘要交给模型有限重试；还不行就降级或者交给人工。尤其是有副作用的工具，绝不能因为“看起来像 JSON”就直接执行。

### 详细理解

这道题的核心不是“怎么让模型吐出 JSON”，而是：

> **怎样把概率性的模型输出，转换成可验证、可控制、可以安全进入业务系统的数据。**

#### 1. 为什么结构化输出会不稳定

普通 LLM 本质上是在逐 token 生成文本。即使提示词写了“只输出 JSON”，模型仍可能返回：

```text
以下是结果：
{"action": "refund", "amount": "100元"}
```

常见问题包括：

- JSON 外面夹带解释或 Markdown 代码块。
- 缺少必填字段，或者增加了未定义字段。
- 数字输出成字符串。
- 枚举值写成近义词，例如要求 `approved`，却输出 `approve`。
- 生成被截断，导致引号或括号没有闭合。
- JSON 语法正确，但内容在业务上错误。

所以要区分三种“正确”：

```text
语法正确：能不能解析成 JSON
Schema 正确：字段、类型、枚举是否符合约定
业务正确：这些值在当前业务中是否合法
```

例如下面是合法 JSON：

```json
{
	"action": "refund",
	"order_id": "A123",
	"amount": -100
}
```

但退款金额为负数，业务上显然不合法。

#### 2. 几种输出约束的强弱

从弱到强可以分成四层：

| 方式 | 能保证什么 | 不能保证什么 |
|---|---|---|
| 提示词要求 JSON | 只能提高按要求输出的概率 | JSON 语法和字段都可能错误 |
| JSON Mode | 通常保证返回可解析的 JSON | 不保证符合指定 Schema |
| Structured Output | 通常约束字段、类型和结构 | 不保证事实和业务逻辑正确 |
| 服务端业务校验 | 检查权限、状态和业务约束 | 仍需处理并发和外部系统失败 |

因此，生产系统应优先使用模型供应商提供的 **Structured Output** 或严格模式的 **Function Calling**，而不是只靠提示词。具体保证范围仍要以所用模型和 API 的文档为准。

#### 3. Structured Output 与 Function Calling 的区别

**Structured Output** 适合让模型返回结构化结果，例如信息抽取：

```json
{
	"intent": "refund",
	"order_id": "A123",
	"confidence": 0.92
}
```

**Function Calling** 适合让模型表达“想调用哪个工具、参数是什么”：

```json
{
	"name": "create_refund",
	"arguments": {
		"order_id": "A123",
		"amount": 100
	}
}
```

关键点是：

> Function Calling 只是模型提出调用意图，不代表服务端应该立刻执行。

模型生成参数后，应用程序仍然拥有最终控制权。

#### 4. 为什么 Schema 要尽量窄

一个退款工具可以定义成：

```json
{
	"type": "object",
	"additionalProperties": false,
	"required": ["order_id", "amount", "currency", "reason"],
	"properties": {
		"order_id": {
			"type": "string",
			"pattern": "^[A-Z][0-9]+$"
		},
		"amount": {
			"type": "number",
			"exclusiveMinimum": 0
		},
		"currency": {
			"type": "string",
			"enum": ["CNY", "USD"]
		},
		"reason": {
			"type": "string",
			"maxLength": 200
		}
	}
}
```

“窄”主要意味着：

- 能用 `enum` 就不要让模型自由发挥。
- 明确哪些字段是必填的。
- 设置数字范围、字符串长度和格式。
- 使用 `additionalProperties: false` 禁止多余字段。
- 避免过深嵌套、大量可选字段和复杂联合类型。
- 对“不知道”设计明确表示，例如允许 `null`，不要让模型猜。

Schema 越模糊，模型可选择的输出空间越大，结果越不稳定。

#### 5. 什么是约束解码

普通生成时，模型可以选择词表中的任意下一个 token。约束解码会根据 JSON Schema 或语法规则，把会导致结构不合法的下一个 token 屏蔽掉。

例如当前位置是：

```json
{"currency":
```

Schema 规定只能是 `CNY` 或 `USD`，解码器就会限制模型生成满足该结构和枚举约束的值，而不能自由输出 `人民币`、`EUR` 或一段解释。

但约束解码只能保证：

```text
输出形式符合规则
```

不能保证：

```text
模型选择的值符合真实情况
```

例如结构上允许 `USD`，模型仍可能在真实订单为人民币时错误选择 `USD`。

#### 6. 为什么服务端还要再次校验

即使输出完全符合 Schema，服务端仍需检查：

- 当前用户是否有退款权限。
- 订单是否真实存在。
- 订单是否属于当前用户或租户。
- 币种是否与原订单一致。
- 退款金额是否超过可退款金额。
- 订单是否已经退款。
- 当前状态是否允许退款。
- 是否发生重复或并发请求。

也就是说：

> JSON Schema 校验数据形状，业务校验判断这件事能不能做。

#### 7. 失败以后如何处理

推荐按错误类型分层处理：

```text
模型输出
	↓
检查拒答、超时或截断
	↓
严格 JSON 解析
	↓
JSON Schema 校验
	↓
权限与业务规则校验
	↓
确认和幂等控制
	↓
执行工具
```

**确定性修复**只处理没有歧义的问题，例如：

- 去掉明确的 Markdown 代码块包装。
- 从供应商规定的结构化字段读取参数。
- 将已经确定的 JSON 字符串解析成对象。

不要“修复”需要猜测的值。例如不能擅自把 `"一百元左右"` 改成 `100`，也不能在订单号缺失时编造订单号。

如果字段不符合 Schema，可以把精简后的错误反馈给模型：

```text
/amount 应为大于 0 的 number，实际收到 string："100元"
/currency 必须是 CNY 或 USD
```

然后最多重试一两次。必须设置次数、时延和成本上限，否则可能造成高延迟、高成本和无限循环。重试仍失败时，根据场景返回可解释错误、降级为只读流程，或者转人工处理。

#### 8. 为什么副作用工具尤其危险

查询天气失败，最多是回答不好；但退款、转账、发邮件、删除数据会改变真实世界状态。

因此副作用工具还应增加：

- 权限检查。
- 用户确认。
- 金额或操作范围限制。
- 幂等键，防止重试导致重复执行。
- Dry Run 或“先生成操作草案”。
- 审计日志。
- 高风险操作人工审批。

正确模式是：

```text
模型提出退款意图
→ Schema 校验
→ 查询真实订单
→ 校验权限和可退款金额
→ 必要时用户确认
→ 携带幂等键执行退款
```

而不是：

```text
模型返回了看起来正确的 JSON
→ 立即退款
```

面试时可以这样总结：

> 结构化输出要分四层治理：首先使用 Structured Output 或 Function Calling 配合窄 JSON Schema，通过约束解码提高格式稳定性；然后在服务端重新做语法、Schema、权限和业务校验。失败时只做无歧义的确定性修复，并根据精简错误进行有界重试。对于退款、转账等副作用工具，还必须增加确认、幂等、审计和人工兜底，因为 Schema 正确只代表格式合法，不代表操作安全。

## LLM-07｜DPO、PPO、GRPO 的核心差异是什么？

**关键词：** **偏好对**、**奖励模型**、**策略梯度**、**参考策略**、**组内优势**  
**关联：** LLM-08、EVAL-02

**参考答案：** 我会这样区分：**DPO** 直接拿偏好对训练，比较策略模型和参考模型对“好答案、差答案”的概率，所以工程上更简单，但很吃偏好数据质量。**PPO** 是根据奖励做在线策略优化，能力上限高一些，不过训练链路、稳定性和成本都更复杂。**GRPO** 会对同一个问题采样多条回答，用组内相对表现来算优势，减少对 value model 的依赖。我不会说哪一个一定更好，它们主要是**数据、成本和稳定性取舍不同**。

### 详细理解

这三个方法都用于**模型对齐**：基础模型已经会续写文本，SFT 又教会了它按指令回答，但我们还希望它更符合人类偏好，或者在数学、代码等任务上获得更高奖励。

先把几个共同概念讲清楚：

- **策略模型（Policy）**：正在训练的 LLM，记作 $\pi_\theta$。给定问题 $x$，它会给回答 $y$ 一个生成概率 $\pi_\theta(y\mid x)$。
- **参考模型（Reference Policy）**：通常是训练前冻结的一份模型，记作 $\pi_{\text{ref}}$，用于约束新模型不要偏离原模型太远。
- **奖励（Reward）**：对回答质量打出的分数。它可以来自人工偏好训练出的奖励模型，也可以来自规则、单元测试或数学答案校验器。
- **价值模型（Value/Critic）**：预测“当前生成状态最终大概能得多少奖励”，主要用于降低策略梯度的方差。
- **优势（Advantage）**：某个回答或动作比基准表现好多少。优势为正就提高其概率，为负就降低其概率。

三者最核心的区别可以先记成一句话：

> **DPO 学偏好对；PPO 学绝对奖励，并用价值模型估计优势；GRPO 也学奖励，但用同题多条回答的组内相对成绩代替独立价值模型。**

#### 1. 先看它们处在训练流程的哪里

一个常见流程是：

```text
预训练模型
	↓
SFT：用“问题 → 标准答案”教会模型按指令回答
	↓
偏好或强化学习阶段
	├── DPO：直接学习“回答 A 优于回答 B”
	├── PPO：模型在线生成回答，再根据奖励更新
	└── GRPO：同题生成一组回答，根据组内相对奖励更新
```

这里的**在线**不是指互联网在线，而是指训练过程中，当前策略模型不断生成新回答，奖励系统再对这些回答评分。DPO 通常使用提前收集好的固定偏好数据，因此常被称为**离线偏好优化**。

#### 2. DPO：直接学习“更喜欢哪个回答”

DPO 全称 **Direct Preference Optimization（直接偏好优化）**。

它的数据通常长这样：

```text
问题 x：解释为什么 0.1 + 0.2 在程序中可能不等于 0.3。
偏好回答 y_w：解释二进制浮点数无法精确表示某些十进制小数。
劣选回答 y_l：因为计算机偶尔会算错。
```

其中 $y_w$ 是 preferred/chosen answer，$y_l$ 是 rejected answer。DPO 的目标是让策略模型相对参考模型而言，**更明显地偏向好回答而不是差回答**。直观上可以写成：

$$
\left[\log \pi_\theta(y_w\mid x)-\log \pi_{\text{ref}}(y_w\mid x)\right]
>
\left[\log \pi_\theta(y_l\mid x)-\log \pi_{\text{ref}}(y_l\mid x)\right]
$$

意思不是简单地把好回答概率调高，而是比较：新策略相对于参考模型，对好、差回答的偏好改变了多少。

训练步骤可以简化为：

```text
读取一条固定偏好对 (x, y_w, y_l)
	↓
策略模型分别计算两个回答的对数概率
	↓
参考模型也计算两个回答的对数概率
	↓
如果策略模型对好回答的相对偏好还不够强，就更新参数
```

**优点：**

- 不需要单独训练奖励模型和价值模型。
- 不需要在每轮训练中在线采样，训练链路更接近普通监督学习。
- 实现相对简单，通常比 PPO 更稳定、更省资源。

**局限：**

- 很依赖偏好对的质量和覆盖范围。
- 只能直接利用“哪个更好”的比较数据，不会主动探索数据中没有出现的新回答。
- 如果偏好数据存在长度偏好、风格偏见或错误标注，模型也会学进去。

可以把 DPO 类比成：

> 老师不必给作文打 87 分或 72 分，只要告诉学生“两篇里 A 比 B 好”，学生就据此调整写法。

#### 3. PPO：根据奖励做在线强化学习

PPO 全称 **Proximal Policy Optimization（近端策略优化）**。它本来就是一种强化学习算法，应用到 LLM 对齐时，通常属于 RLHF 流程的一部分。

PPO 不一定需要成对回答。当前策略先生成回答，奖励模型或规则再给它一个分数：

```text
问题 x
	↓ 当前策略模型生成
回答 y
	↓ 奖励模型/规则评分
reward = 0.82
```

但是只知道最终得了 $0.82$ 分还不够。这个分数到底比模型原本预期高还是低？回答中的哪些 token 值得鼓励？因此 PPO 通常还训练一个 **Value Model/Critic** 来估计基准价值，再计算优势：

$$
A_t \approx \text{实际回报}_t-V(s_t)
$$

- $A_t>0$：结果比预期好，提高相关 token 的生成概率。
- $A_t<0$：结果比预期差，降低相关 token 的生成概率。

PPO 中的“Proximal”强调**每次不要更新得太猛**。它会限制新旧策略的概率比，常见的裁剪目标可抽象为：

$$
\min\left(r_tA_t,\operatorname{clip}(r_t,1-\epsilon,1+\epsilon)A_t\right),
\qquad
r_t=\frac{\pi_\theta(a_t\mid s_t)}{\pi_{\text{old}}(a_t\mid s_t)}
$$

LLM 对齐中通常还会加入相对参考模型的 **KL 惩罚**，防止模型为了追逐奖励而严重偏离原有语言能力：

$$
R_{\text{total}}=R_{\text{task}}-\beta D_{\mathrm{KL}}(\pi_\theta\|\pi_{\text{ref}})
$$

完整链路通常包括：

```text
策略模型在线采样回答
	↓
奖励模型或规则打分
	↓
价值模型估计价值并计算优势
	↓
PPO 裁剪更新策略，限制单次变化
	↓
继续用更新后的策略采样
```

**优点：**

- 可以直接优化可计算的奖励，并持续从当前策略的新回答中学习。
- 能探索固定偏好数据之外的回答，在奖励可靠时优化空间较大。

**局限：**

- 通常要同时维护策略模型、参考模型、奖励模型和价值模型，显存与工程成本高。
- 在线生成回答很耗算力，训练吞吐低于普通监督学习。
- 对奖励设计、优势估计和超参数敏感，可能出现训练不稳定或 Reward Hacking。

可以把 PPO 类比成：

> 学生现场写作文，老师逐篇打分；助教还估计这名学生正常能得多少分。高于预期的写法被鼓励，但每次改动不能过大。

#### 4. GRPO：同一道题内部比较，不单独训练价值模型

GRPO 全称 **Group Relative Policy Optimization（组相对策略优化）**。它与 PPO 一样会让当前策略在线生成回答，并根据奖励做策略优化；关键变化是：**不再依赖一个独立的价值模型估计基线，而是用同一道题的一组回答互相比较。**

例如对同一道数学题采样 4 个回答：

| 回答 | 奖励 |
|---|---:|
| A：答案和推导都正确 | 1.0 |
| B：答案正确，推导有小问题 | 0.7 |
| C：答案错误 | 0.0 |
| D：答案错误且格式不合规 | -0.2 |

先计算这一组奖励的均值和标准差，再把每个奖励标准化为组内优势：

$$
A_i=\frac{r_i-\operatorname{mean}(r_1,\ldots,r_G)}
{\operatorname{std}(r_1,\ldots,r_G)+\varepsilon}
$$

于是高于组内平均水平的 A、B 得到正优势，低于平均水平的 C、D 得到负优势。然后像 PPO 一样，提高正优势回答的概率、降低负优势回答的概率，并通过裁剪或 KL 约束控制更新幅度。

训练流程是：

```text
对同一个问题采样 G 条回答
	↓
分别用奖励模型、规则或验证器打分
	↓
根据组内均值和标准差计算相对优势
	↓
更新策略模型，不单独训练 Value Model
```

**优点：**

- 省掉独立价值模型，降低一部分显存占用和训练复杂度。
- 数学、代码等任务有明确验证器时，可以直接利用可验证奖励。
- 同题比较能削弱不同题目难度和奖励尺度差异带来的影响。

**局限：**

- 每道题必须采样多条回答，生成成本仍然很高。
- 组太小，优势估计噪声大；组内奖励都一样时，几乎没有学习信号。
- 仍然依赖奖励质量，也会发生 Reward Hacking。
- “不需要价值模型”不等于“不需要奖励函数”；奖励模型、规则或验证器仍然要负责打分。

可以把 GRPO 类比成：

> 老师让学生针对同一道题写多份候选答案，不预测每份应得多少分，而是直接按这一组里的相对名次来奖优罚劣。

#### 5. 用同一个例子看三者到底如何学习

假设目标是提升模型的数学推理能力：

**DPO：** 数据集提前准备好“正确推导”和“错误推导”的偏好对。训练时模型不生成新答案，只学习每一对中应该更偏好哪一个。

**PPO：** 当前模型现场生成一个或多个答案，验证器给奖励，价值模型估计基线，再根据优势更新策略。

**GRPO：** 当前模型针对同一道题现场生成一组答案，验证器逐个打分，用组内平均表现作为基线，再更新策略，不训练独立价值模型。

#### 6. 核心对比

| 维度 | DPO | PPO | GRPO |
|---|---|---|---|
| 主要训练信号 | 好/差回答偏好对 | 回答的奖励 | 同题一组回答的相对奖励 |
| 数据产生方式 | 通常离线固定数据 | 当前策略在线采样 | 当前策略在线分组采样 |
| 是否需要奖励模型 | 不需要单独使用 | 通常需要，也可用规则奖励 | 需要奖励来源，可用模型、规则或验证器 |
| 是否需要 Value Model | 不需要 | 通常需要 | 不需要独立 Value Model |
| 是否常用参考模型 | 是 | 常用于 KL 约束 | 常用于 KL 约束，依具体实现而定 |
| 训练复杂度 | 较低 | 最高 | 介于 DPO 与 PPO 之间 |
| 主要风险 | 偏好数据偏差、离线覆盖不足 | 不稳定、成本高、奖励投机 | 采样成本、组内信号弱、奖励投机 |
| 更适合的条件 | 有高质量偏好对，资源有限 | 奖励可靠且能承担复杂训练 | 可批量采样，任务有可靠奖励或验证器 |

#### 7. 几个容易说错的地方

- **DPO 不是 SFT。** SFT 模仿标准答案；DPO 比较好答案与差答案，学习相对偏好。
- **PPO 不是奖励模型。** 奖励模型负责打分，PPO 负责利用这些分数更新策略。
- **GRPO 不是不要奖励。** 它省掉的是独立 Value Model，而不是 Reward。
- **在线 RL 不一定比 DPO 更好。** 如果奖励模型不可靠，优化越强反而可能越会钻奖励漏洞。
- **GRPO 也不是天然只用于推理模型。** 它适合能对一组候选回答提供可靠奖励的任务，数学和代码只是典型场景。

面试时可以这样回答：

> 三者都是对齐方法，但训练信号和估计优势的方式不同。DPO 使用离线偏好对，直接让策略模型相对参考模型更偏好 chosen answer，不需要单独训练奖励模型和价值模型，链路最简单。PPO 让当前策略在线采样，通过奖励模型或规则获得奖励，再由价值模型估计优势，并用裁剪和 KL 约束做策略更新，灵活但成本和稳定性压力最大。GRPO 也做在线策略优化，但对同一个问题采样一组回答，用组内相对奖励作为优势，省掉独立价值模型；代价是每题要多次采样，而且仍然高度依赖奖励质量。因此选择时主要看偏好数据、奖励可靠性、采样成本和训练资源。

## LLM-08｜SFT、LoRA/PEFT、偏好对齐与 RAG 应如何选？

**关键词：** **知识**、**行为**、**风格**、**时效性**、**参数高效微调**  
**关联：** LLM-07、RAG-01、ENG-06

**参考答案：** 我通常先问一句：现在的问题到底是**知识没拿到，还是行为没学会**？知识经常变化、需要引用或者受权限控制，我会优先用 **RAG**；如果是格式、术语或者固定任务行为不稳定，再考虑 **SFT**；资源有限时用 **LoRA/PEFT**。如果要调整偏好、风格或拒答，再看 DPO/PPO/GRPO。我的原则是先做一个能评测的 prompt/RAG 基线，确认瓶颈以后再训练，不用微调去掩盖检索问题。

### 详细理解

这道题先要纠正一个常见误区：**RAG、SFT 和 LoRA 并不是三个完全同层级的方案。**

- **RAG** 是一种应用架构：推理时从外部知识库检索资料，再把资料放进上下文。
- **SFT** 是一种训练方式：用“输入 → 理想输出”样本继续训练模型。
- **LoRA** 是一种参数高效微调方法：做 SFT 等训练时，只更新少量新增参数，而不是更新整个模型。
- **PEFT** 是参数高效微调这一大类方法，LoRA 是其中最常见的一种。

因此实际项目里完全可以同时使用：

```text
RAG + LoRA 方式的 SFT
```

其中 RAG 负责提供最新、可追溯的知识，LoRA-SFT 负责让模型学会如何使用证据、遵守格式或完成特定任务。

可以先用一句话记忆：

> **RAG 像开卷考试，资料放在模型外面；SFT 像用示范题训练学生，能力写进模型参数；LoRA 像只加一本很薄的专项笔记，而不是重写整本教材。**

#### 1. RAG：不改模型参数，推理时临时补知识

RAG 全称 **Retrieval-Augmented Generation（检索增强生成）**。它的核心是：回答问题前，先从外部知识库中找到相关资料，再让模型基于这些资料回答。

一个基本流程如下：

```text
企业文档、数据库、网页
	↓ 清洗、切分
文档片段
	↓ 向量化并建立索引
知识库

用户问题
	↓ 检索、重排
相关文档片段
	↓ 与问题一起放入 Prompt
LLM 生成带依据的回答
```

例如用户问：

```text
我们公司 2026 年差旅报销的住宿上限是多少？
```

基础模型不可能天然知道公司内部最新制度。RAG 会先检索到：

```text
《2026 年差旅管理办法》第 12 条：
一线城市住宿标准上限为 650 元/晚……
```

再把问题和这段证据一起交给模型。模型参数没有变化，它只是本轮回答时临时读到了资料。

**RAG 适合解决的问题：**

- 私有知识：企业制度、产品手册、内部工单。
- 高频变化的知识：价格、政策、库存、最新文档。
- 需要引用来源的问答。
- 有权限边界的知识：不同用户只能检索自己有权查看的内容。
- 知识规模很大，不可能全部写入 Prompt 或模型参数。

**RAG 的优点：**

- 更新知识库即可生效，通常不需要重新训练模型。
- 可以保留文档来源、页码和版本，方便核验。
- 可以在检索阶段执行租户隔离和权限过滤。
- 相比微调，更适合处理大量、动态的事实知识。

**RAG 的局限：**

- 检索不到正确证据，模型就很难答对。
- 切分不合理可能把完整语义拆散。
- 向量召回结果相关，不一定代表它能回答问题，通常还需要重排。
- 检索到冲突或过期文档时，需要版本和可信度治理。
- 即使证据正确，模型也可能没有忠实使用证据。

所以 RAG 系统不能只评估最终回答，还要拆开评估：

```text
检索召回是否命中
→ 重排是否把正确证据放到前面
→ 上下文是否包含完整答案
→ 模型是否忠实依据证据回答
→ 引用是否真的支持结论
```

#### 2. SFT：用标准示范教模型“应该怎样回答”

SFT 全称 **Supervised Fine-Tuning（监督微调）**。它会准备大量“输入和理想输出”样本，让模型模仿理想输出。

数据通常长这样：

```json
{
	"input": "用户说银行卡被盗刷，应该如何处理？",
	"output": "先冻结银行卡，再核对交易记录，并通过银行官方渠道发起争议处理……"
}
```

训练时，模型看到输入和标准答案，通过 Teacher Forcing 学习预测答案中的下一个 token。常见损失可以写成：

$$
\mathcal{L}_{\text{SFT}}
=-
\sum_t \log \pi_\theta(y_t\mid x,y_{<t})
$$

其中：

- $x$ 是用户输入或指令。
- $y_t$ 是标准答案的第 $t$ 个 token。
- 模型要提高标准答案中每个 token 的生成概率。

与 RAG 不同，SFT 会**修改模型参数**。训练结束后，即使不把示范样本放进 Prompt，模型也更可能表现出学到的行为。

**SFT 适合解决的问题：**

- 模型不稳定地遵守固定输出格式。
- 模型不会某种任务流程，如意图分类、字段抽取或特定代码转换。
- 需要稳定使用行业术语、品牌语气或回答结构。
- Prompt 很长、示例很多，希望把重复行为内化到模型中。
- 基础模型具备相关知识，但不知道应该如何完成特定任务。

例如客服系统要求模型始终输出：

```json
{
	"intent": "refund",
	"urgency": "high",
	"next_action": "transfer_to_human"
}
```

如果只靠 Prompt 和结构化输出仍不稳定，可以用大量高质量样本做 SFT，让模型熟悉任务定义、字段含义和边界案例。

**SFT 的优点：**

- 能较稳定地塑造任务行为、格式、术语和表达风格。
- 推理时不必每次携带大量 Few-shot 示例，可以减少上下文占用。
- 对范围清晰、样本充足的垂直任务通常很有效。

**SFT 的局限：**

- 需要高质量、覆盖真实分布的训练数据。
- 新知识不会自动更新，制度变化后可能要重新准备数据和训练。
- 模型可能记住事实，却无法给出可靠来源。
- 数据错误、偏见和错误格式也会被模型学习。
- 训练过度可能造成过拟合或灾难性遗忘，损害原有通用能力。

因此不推荐把经常变化的企业事实硬塞进 SFT。例如把“当前住宿上限是 650 元”训练进参数，政策改成 700 元后很难精确删除旧知识，也难保证模型不再说旧答案。这种事实更适合放在 RAG 知识库里。

#### 3. LoRA：做微调时，只训练少量低秩参数

LoRA 全称 **Low-Rank Adaptation（低秩适配）**。它不是一种新的任务目标，而是一种**更省资源地实现微调的方法**。

全量微调会更新基础模型的大量权重。假设某层原始权重为 $W$，训练后变成：

$$
W'=W+\Delta W
$$

LoRA 冻结原始权重 $W$，不直接训练完整的 $\Delta W$，而是用两个更小的低秩矩阵表示它：

$$
W'=W+BA
$$

若 $W\in\mathbb{R}^{d\times k}$，则可以令：

$$
A\in\mathbb{R}^{r\times k},\qquad
B\in\mathbb{R}^{d\times r},\qquad
r\ll\min(d,k)
$$

原本需要训练 $d\times k$ 个参数，现在主要训练 $r\times k+d\times r$ 个参数。当秩 $r$ 很小时，可训练参数量会显著下降。

直观流程是：

```text
冻结基础模型参数 W
	↓
在部分线性层旁加入小型矩阵 A、B
	↓
用 SFT 数据计算损失
	↓
只更新 A、B
	↓
保存体积较小的 LoRA Adapter
```

这里的 **LoRA Adapter** 不是一个可以单独运行的小模型，而是一个针对特定基础模型训练出来的**权重增量包**。

基础模型原来的权重 $W$ 没有被修改，训练真正学到并需要保存的是低秩矩阵 $A$、$B$，以及少量相关配置。下次使用时再把它们与基础模型组合：

$$
W'=W+\frac{\alpha}{r}BA
$$

其中：

- $W$ 来自原始基础模型。
- $A$、$B$ 来自 LoRA Adapter。
- $r$ 是 LoRA 的秩。
- $\alpha$ 用来控制 LoRA 增量的缩放强度。

例如某个线性层的权重矩阵大小为 $4096\times4096$：

- 全量保存这一层的权重变化，需要约 $4096\times4096=16{,}777{,}216$ 个参数。
- 如果 LoRA 的秩 $r=8$，只需保存 $8\times4096+4096\times8=65{,}536$ 个参数。
- 这一层的可训练参数约为全量参数的 $0.39\%$。

实际模型有很多层，LoRA 也可能注入多个投影矩阵，所以最终 Adapter 仍可能有几十 MB、几百 MB，具体取决于基础模型大小、秩、注入层、数据类型和是否额外训练 Embedding 等参数。但它通常远小于数 GB 甚至数十 GB 的完整模型。

一个常见的 Adapter 目录可能包含：

```text
refund-assistant-lora/
	├── adapter_model.safetensors   # 训练得到的 A、B 等权重
	├── adapter_config.json         # rank、alpha、目标层、基础模型等配置
	└── tokenizer_config.json       # 仅在分词器配置也需要保存时出现
```

这里通常**不包含完整基础模型权重**。因此 Adapter 必须和训练时兼容的基础模型一起使用：

```text
基础模型：Qwen-某版本
	+
退款客服 LoRA Adapter
	↓
具备退款客服专项行为的模型
```

如果拿错基础模型、模型版本或目标层不匹配，Adapter 可能无法加载；即使勉强加载，效果也可能异常。因此发布 Adapter 时通常要记录基础模型标识、版本或提交哈希、Tokenizer、LoRA 配置和训练模板。

保存 Adapter 后有两种常见推理方式：

**方式一：动态加载 Adapter**

```text
一份基础模型常驻内存
	├── 加载客服 Adapter
	├── 加载代码 Adapter
	└── 加载摘要 Adapter
```

优点是多个任务可以共享同一份基础模型，Adapter 容易切换、回滚和独立发布。代价是推理框架必须支持 Adapter 管理，切换和并发调度也更复杂。

**方式二：把 Adapter 合并进基础模型**

```text
基础权重 W + LoRA 增量 BA
	↓ merge
新的完整权重 W'
```

合并后可以像普通模型一样部署，通常不再需要单独加载 Adapter；但保存结果会重新变成一个完整模型，失去“小文件、方便切换”的优势，而且应保留未合并版本以便回滚。

所以“保存体积较小的 LoRA Adapter”准确来说就是：

> **训练结束后不复制并保存整个基础模型，只保存这次任务学到的低秩权重增量和配置；使用时再将它加载到对应基础模型上，或者合并成新的完整模型。**

推理时可以：

- 将 LoRA 权重合并到基础模型中再部署。
- 保留独立 Adapter，根据不同任务动态加载。

**LoRA 的优点：**

- 可训练参数少，训练显存和存储成本通常低于全量微调。
- 同一个基础模型可以搭配多个小型 Adapter。
- 基础模型保持冻结，实验、回滚和版本管理更方便。
- 在许多垂直任务上能以较低成本获得接近全量微调的效果。

**LoRA 的局限：**

- 仍然需要训练数据、训练过程和严格评测，不是“低成本自动变强”。
- 能力上限受基础模型、数据质量、注入层和秩等配置影响。
- 多个 Adapter 的加载、合并和服务路由会增加部署复杂度。
- 对需要大幅改变模型能力或知识结构的任务，可能不如全量微调。

#### 4. PEFT、LoRA、QLoRA 和 SFT 是什么关系

它们可以按两个维度理解：

```text
训练目标：用什么数据、优化什么
	└── SFT：模仿输入对应的标准输出

参数更新方式：训练时更新哪些参数
	├── Full Fine-Tuning：更新全部或大部分模型参数
	└── PEFT：只训练少量参数
		└── LoRA：用低秩矩阵表示权重增量
```

因此以下说法才是完整的：

- **全量 SFT**：使用 SFT 目标，更新全部或大部分模型参数。
- **LoRA-SFT**：使用 SFT 目标，只更新 LoRA Adapter。
- **LoRA-DPO**：使用 DPO 目标，只更新 LoRA Adapter。

PEFT 全称 **Parameter-Efficient Fine-Tuning（参数高效微调）**，是一个总称，除 LoRA 外还包括 Adapter、Prefix Tuning、Prompt Tuning 等方法。

QLoRA 则通常表示：

> 将冻结的基础模型以低比特量化形式加载，同时训练 LoRA Adapter，以进一步降低训练显存。

量化主要减少基础模型占用，真正参与更新的仍然是 LoRA 参数。它能降低训练门槛，但量化配置、数值稳定性和最终效果仍需通过实验验证。

#### 5. 用同一个企业问答场景比较

假设要做一个公司制度助手。

**问题一：模型不知道最新报销标准。**

优先使用 RAG。因为报销标准会变化，需要展示原文和版本，还必须根据员工权限检索。把金额训练进模型参数既难更新，也难追溯。

**问题二：模型拿到了正确制度，却总是不按“结论、依据、来源”三段式回答。**

先优化 Prompt 和结构化输出。如果大量真实样本上仍不稳定，可以做 SFT，让模型学会固定回答流程。

**问题三：模型太大，全量 SFT 显存成本无法承担。**

使用 LoRA 或 QLoRA 来执行 SFT。训练目标没有变，只是减少需要更新和保存的参数。

**问题四：既要知道最新制度，又要稳定按公司格式回答。**

组合 RAG 与 LoRA-SFT：

```text
RAG：检索最新制度、权限过滤、提供引用
	+
LoRA-SFT：学习如何阅读证据、拒绝无依据回答、输出固定格式
```

#### 6. 三者核心对比

| 维度 | RAG | SFT | LoRA |
|---|---|---|---|
| 本质 | 推理时检索外部知识的架构 | 监督微调的训练目标 | 参数高效的微调方法 |
| 是否修改模型参数 | 否 | 是 | 只修改少量新增参数 |
| 主要解决 | 知识获取、时效、引用、权限 | 行为、任务、格式、术语、风格 | 微调成本、显存和版本管理 |
| 所需核心数据 | 可检索文档和查询 | 输入与理想输出样本 | 取决于训练目标，如 SFT 样本 |
| 知识更新方式 | 更新索引或数据源 | 重新准备数据并训练 | 重新训练或替换 Adapter |
| 是否容易引用来源 | 容易 | 困难 | 困难，除非与 RAG 结合 |
| 主要风险 | 检索错误、证据冲突、上下文干扰 | 数据偏差、过拟合、遗忘 | 容量受限、配置敏感、部署复杂 |

这张表中最重要的一点是：**LoRA 的“主要解决”不是知识或行为本身，而是如何以更低成本完成微调。**

#### 7. 实际选型顺序

可以按下面的顺序判断：

```text
1. Prompt、工作流或结构化输出能否解决？
	├── 能：先用最简单方案
	└── 不能：继续判断

2. 问题是缺少事实知识吗？
	├── 知识会变化、私有、需引用或受权限控制：RAG
	└── 不是：继续判断

3. 问题是行为、格式或固定任务不稳定吗？
	├── 是：准备高质量样本做 SFT
	└── 不是：重新定位瓶颈

4. 全量微调成本是否可接受？
	├── 否：优先 LoRA/QLoRA 等 PEFT
	└── 是：对比全量微调与 PEFT 的效果和成本

5. 是否同时存在动态知识和行为问题？
	└── 组合 RAG + SFT，SFT 可通过 LoRA 实现
```

真正做决策前，应先建立可评测基线，并把错误分类：

- **检索错误**：正确资料没有进入上下文，优先修 RAG。
- **生成错误**：证据已经给对，但模型没有正确使用，可优化 Prompt、模型或 SFT。
- **格式错误**：优先结构化输出和服务端校验，必要时再 SFT。
- **知识过期**：更新数据源和索引，不要指望 SFT 自动修正。
- **风格或偏好问题**：SFT 可先建立基本行为，更细的偏好再考虑 DPO 等对齐方法。

#### 8. 几个容易说错的地方

- **LoRA 不等于 SFT。** SFT 决定训练什么，LoRA 决定用什么参数更新方式训练。
- **RAG 不会自动消除幻觉。** 它只提供证据，仍需约束生成并验证引用忠实度。
- **SFT 不适合充当可频繁更新的知识库。** 参数中的知识难以精确更新、删除和追溯。
- **LoRA 不是只能调整风格。** 它也能用于任务学习、领域适配、DPO 等多种训练目标。
- **RAG 与微调不是二选一。** 大量生产系统会用 RAG 管知识，用 SFT 管行为。
- **微调不能修复检索缺失。** 如果答案依据根本没有进入上下文，训练模型往往是在掩盖数据链路问题。

面试时可以这样回答：

> 我会先区分知识问题和行为问题。RAG 不修改模型参数，而是在推理时检索外部资料，适合动态、私有、需要引用或权限控制的知识。SFT 使用输入和理想输出样本继续训练模型，适合让模型学习稳定的任务行为、格式、术语和风格。LoRA 则不是与 SFT 平级的训练目标，而是 PEFT 方法：它冻结基础模型，只训练低秩 Adapter，以较低显存和存储成本完成 SFT 或 DPO。实际项目中我会先建立 Prompt/RAG 基线并分类错误；缺知识先修 RAG，证据正确但行为仍不稳定再做 SFT，资源受限时用 LoRA/QLoRA。动态知识和固定行为同时存在时，通常组合 RAG 与 LoRA-SFT。

## LLM-09｜生产系统如何选择和路由模型？

**关键词：** **质量**、**延迟**、**成本**、**上下文**、**工具能力**、**降级**  
**关联：** EVAL-08、EVAL-12、ENG-05

**参考答案：** 我不会直接按榜单选模型，而是先把任务需要的**质量、工具调用、结构化输出、上下文长度、P95、吞吐、数据边界和成本**列清楚，再拿真实样本跑评测。简单分类和改写可以走小模型，复杂规划或低置信样本再升级到强模型。路由还要有预算上限、回退模型和版本记录。最终看的是**质量—成本—延迟的平衡**，不是某个模型单项分数最高。

### 详细理解：模型路由与 Harness 的关系

这段内容确实在讨论 **LLM/Agent Harness** 的一部分，但两者不能完全画等号。

> **模型路由负责决定“这一轮调用哪个模型”；Harness 负责决定“整个任务如何在模型、上下文、工具和运行规则之间执行”。**

这里的 Harness 原意是“挽具、线束”。在 LLM 工程中，可以把它理解成包裹在模型外面的**运行控制层**：它把一个只能接收 token、生成 token 的模型，接入真实应用所需的上下文、工具、状态、安全规则和观测系统。

#### 1. 模型本身与 Harness 分别负责什么

单独的 LLM 主要完成：

```text
输入 token
	↓
概率计算与生成
	↓
输出 token
```

但生产系统还需要回答很多模型本身不负责的问题：

- 系统提示词、用户消息、记忆和检索证据怎样组装？
- 当前请求应该用小模型、强模型还是专用模型？
- 模型要调用工具时，谁校验参数并真正执行？
- 工具失败以后是否重试，最多重试几次？
- 对话和任务状态保存在哪里？
- 如何限制 token、金额、工具次数和总耗时？
- 高风险操作是否需要用户确认或人工审批？
- 如何记录模型版本、Prompt、轨迹、成本和评测结果？

负责这些工作的外围系统，就是广义上的 Harness。

可以把整体关系表示为：

```text
应用入口
	↓
Harness
	├── 任务识别与模型路由
	├── Context Engineering
	├── Prompt / Tool Schema 装配
	├── Agent 循环与状态管理
	├── 工具执行与权限控制
	├── 结构化输出校验
	├── 重试、回退与预算控制
	└── 日志、Tracing、Eval 与审计
		↓
	  LLM / 多个候选模型
```

因此，**模型路由器通常是 Harness 中的一个组件**，不是 Harness 的全部。

#### 2. 一次请求在 Harness 中怎样运行

假设用户对一个编码 Agent 说：

```text
修复支付回调重复创建订单的问题，并运行相关测试。
```

Harness 可能执行下面的流程：

```text
1. 读取系统规则、用户要求和仓库规则
	↓
2. 恢复当前任务状态与最近对话
	↓
3. 判断任务类型、风险和复杂度
	↓
4. 路由到适合代码推理和工具调用的模型
	↓
5. 给模型提供文件搜索、读取、编辑和测试工具 Schema
	↓
6. 接收模型提出的工具调用并校验参数、权限和路径
	↓
7. 执行工具，把精简结果送回模型
	↓
8. 循环，直到完成、超预算或需要人工介入
	↓
9. 运行验证，记录模型、Prompt、工具轨迹、耗时和结果
```

模型负责在每一步判断“接下来做什么”，Harness 则负责维护循环、提供环境并执行控制。不同系统的边界会不同：有些 Harness 内含工作流编排器，有些会把路由、记忆或工具网关拆成独立服务。

#### 3. 模型路由具体在做什么

模型路由通常根据请求特征和运行状态，选择模型或升级路径。

例如：

| 请求 | 初始路由 | 可能的升级条件 |
|---|---|---|
| 意图分类、关键词抽取 | 小模型 | 结构校验连续失败 |
| 普通摘要和改写 | 中小模型 | 输入超长或质量分过低 |
| 跨文件代码修改 | 强工具模型 | 测试失败后需要更强推理 |
| 复杂系统设计 | 强推理模型 | 通常直接使用强模型 |
| 敏感数据处理 | 私有部署模型 | 不允许回退到外部 API |

路由依据通常包括：

- **任务类型**：分类、生成、代码、视觉、规划或工具调用。
- **质量要求**：错误是否可接受，是否需要强推理。
- **能力约束**：上下文长度、Function Calling、Structured Output、多模态。
- **运行指标**：P95 延迟、吞吐、限流和模型可用性。
- **成本预算**：输入输出 token 价格、每任务最高成本。
- **数据边界**：数据能否发送给外部供应商，模型部署在哪个区域。
- **当前状态**：置信度、工具失败次数、校验结果和剩余预算。

路由不一定只在请求开始时发生，也可以在执行途中升级：

```text
小模型先处理
	↓
结果通过校验？
	├── 是：直接返回
	└── 否：升级到强模型
		↓
	仍失败或超预算？
	├── 使用回退流程
	└── 转人工
```

不过“低置信度”不能只让模型自己说一个置信分。更可靠的信号包括结构校验失败、答案与证据矛盾、单元测试失败、多次采样不一致、外部验证器未通过等。

#### 4. Harness 中常见的核心模块

**上下文装配器**

按优先级和 token 预算装配系统规则、任务状态、最近对话、长期记忆、RAG 证据和工具结果。它决定模型这一轮实际能看到什么。

**模型网关与路由器**

统一不同供应商的接口，根据策略选择模型，并处理限流、超时、回退、熔断和版本固定。

**Agent 运行循环**

维护“模型判断 → 工具调用 → 返回观察结果 → 再判断”的循环，同时设置最大步数、截止时间和终止条件。

**工具执行层**

注册工具 Schema，校验参数，执行真实操作，并实施权限、沙箱、幂等、确认和审计。模型只能提出调用意图，不能绕过这一层直接产生副作用。

**状态与记忆层**

保存会话消息、任务进度、已验证事实、工具结果和跨会话记忆，避免每一轮都从头开始。

**验证与护栏**

检查 JSON Schema、业务规则、引用忠实度、代码测试、安全策略和敏感信息。验证失败时决定修复、重试、降级还是拒绝。

**可观测与评测层**

记录模型名称和版本、Prompt 版本、输入输出 token、延迟、成本、工具轨迹、错误类型与最终成功率，用于离线 Eval 和线上监控。

#### 5. 为什么同一个模型换 Harness 后效果会不同

用户看到的最终能力不只由模型权重决定，可以粗略写成：

$$
	ext{系统效果}
=f(\text{模型},\text{上下文},\text{工具},\text{Harness 策略},\text{数据},\text{验证})
$$

同一个模型接入不同 Harness，可能出现明显差异：

- 一个 Harness 能检索到正确代码，另一个只给模型文件名。
- 一个会在编辑后自动运行测试，另一个生成代码后就停止。
- 一个保留用户最新约束，另一个在长对话压缩时把约束丢了。
- 一个会校验工具参数和幂等键，另一个直接执行模型输出。
- 一个失败后依据测试结果修复，另一个无条件重复同一个请求。

因此编码 Agent、研究 Agent 等产品的差异，不只是底层用了哪个模型，也来自 Harness 如何设计上下文、工具和反馈循环。

#### 6. Harness 与工作流、Agent、SDK 的区别

这些词在业界没有完全统一的边界，但可以这样理解：

| 概念 | 重点 |
|---|---|
| LLM SDK | 提供调用模型 API 的客户端能力 |
| Workflow | 按预定义步骤和分支编排任务 |
| Agent | 让模型根据当前状态动态决定下一步行动 |
| Harness | 为模型或 Agent 提供完整运行环境与控制机制 |
| Model Router | 在多个模型之间执行选择、升级和回退 |

一个 Workflow 或 Agent Runtime 往往就是 Harness 的核心部分；有时产品也会直接把整套 Agent Runtime 称为 Agent Harness。面试时不必纠结术语归属，最好先说明你所说的 Harness 边界。

#### 7. Harness 怎么评估

不能只拿单轮问答准确率评价 Harness，因为它控制的是完整任务执行。更合适的指标包括：

- **Task Success Rate**：任务最终是否真正完成。
- **Tool Call Success Rate**：工具选择和参数是否正确。
- **Validation Pass Rate**：结构校验、测试或业务规则通过率。
- **平均步骤数**：完成任务需要多少轮模型和工具调用。
- **P50/P95 延迟**：典型和长尾任务耗时。
- **每成功任务成本**：总模型与工具成本除以成功任务数。
- **升级率与回退成功率**：小模型有多少请求升级，回退后能否恢复。
- **安全事件率**：越权调用、敏感信息泄露和未确认副作用的比例。

评估模型路由时，尤其要看**每成功任务成本**，而不是只看单次调用便宜。小模型虽然单次便宜，但如果频繁失败、重试并升级，最终可能更贵、更慢。

#### 8. 一个简化的生产 Harness 策略

以企业知识助手为例，可以设计成：

```text
收到问题
	↓
权限识别与敏感数据检查
	↓
按用户权限执行 RAG
	↓
任务路由
	├── 简单事实问答：小模型
	├── 多文档综合：强模型
	└── 数据不得出域：私有模型
	↓
生成带引用的结构化答案
	↓
Schema、引用与业务规则校验
	├── 通过：返回答案
	├── 可修复：有限重试或升级模型
	└── 高风险/无依据：拒答或转人工
	↓
记录版本、证据、延迟、成本和结果
```

这里模型路由只是其中的“任务路由”节点；RAG、权限、校验、重试和观测同样属于 Harness。

#### 9. 几个容易说错的地方

- **Harness 不是 Prompt 的另一个名字。** Prompt 只是 Harness 装配给模型的一部分输入。
- **Harness 不是模型。** 它通常不改变模型权重，而是控制模型如何被调用和执行任务。
- **模型路由不等于 Harness。** 路由是 Harness 的一个子模块。
- **换强模型不能替代 Harness。** 缺少正确证据、权限校验或工具反馈时，更强的模型仍可能失败。
- **Harness 也不能凭空补足模型能力。** 如果基础模型不支持所需语言、模态或工具调用，应更换模型或调整任务设计。
- **回退不一定意味着换弱模型。** 它也可能是切换供应商、关闭非必要工具、改用只读流程或转人工。

面试时可以这样回答：

> 这道题涉及 Harness，但重点只是其中的模型选择与路由。模型路由决定每个请求使用小模型、强模型、专用模型还是私有模型，并根据验证失败、预算和可用性进行升级或回退。Harness 的范围更大，它是模型外部的运行控制层，还负责上下文装配、Agent 循环、工具执行、状态管理、权限、安全校验、重试和可观测。生产系统最终应评估模型与 Harness 的组合效果，重点看真实任务成功率、P95、每成功任务成本和安全边界，而不是只比较模型榜单分数。
