# 03｜Agent 架构与工具调用（13 题）

记忆链：**是否需要 Agent → 如何决策 → 如何执行工具 → 如何恢复 → 如何受控结束**。

## AGENT-01｜Chatbot、Workflow、Agent、Multi-Agent 如何区分？

**关键词：** 固定路径、动态决策、环境反馈、角色边界  
**关联：** AGENT-02、AGENT-11、AGENT-13

**参考答案：** Chatbot 主要生成对话；Workflow 的步骤和分支由代码预先定义；Agent 根据状态与观察动态选择下一步；Multi-Agent 把职责和上下文拆给多个决策主体。判断标准不是“调用了 LLM”，而是执行路径是否由模型在运行时改变。能用确定性流程解决时优先 Workflow。

## AGENT-02｜ReAct 的核心机制是什么？

**关键词：** reason-act-observe、反馈闭环、停止条件、可观测  
**关联：** AGENT-03、AGENT-08、PROJ-14

**参考答案：** ReAct 让模型在“分析当前状态—选择动作—读取观察—更新计划”的循环中完成任务。价值是能根据工具结果自适应，风险是循环、成本、提示注入和不可复现。生产实现不应暴露私有思维链，而应记录结构化 decision summary、动作、观察和停止原因，并设置轮数、时间、token 和权限预算。

## AGENT-03｜Agent Runtime / Harness 应包含哪些组件？

**关键词：** state、planner、tool registry、policy、memory、trace、eval  
**关联：** LLM-05、AGENT-04、EVAL-04

**参考答案：** 至少包括模型网关、上下文构建、状态机/编排器、工具注册与执行、权限策略、记忆、重试/恢复、流式事件、trace、预算和 Eval 接口。Harness 的核心不是包一层 prompt，而是把非确定模型放进可验证、可观测、可限权、可恢复的工程边界。

## AGENT-04｜一个新工具从定义到执行的完整链路是什么？

**关键词：** schema、发现、选择、校验、授权、执行、observation  
**关联：** AGENT-05、AGENT-06、MCP-02

**参考答案：** 开发者定义名称、用途、输入输出 schema、权限和副作用；Host 把允许的工具暴露给模型；模型返回结构化调用；Runtime 做 schema/业务/权限校验与审批；执行器设置超时、幂等键和隔离，得到结果后裁剪脱敏为 observation，再决定继续、重试或结束。每步要带 trace ID，不能直接信任模型参数。

## AGENT-05｜Agent 如何判断是否调用工具？

**关键词：** 能力边界、新鲜信息、外部动作、置信度、策略  
**关联：** AGENT-04、AGENT-13

**参考答案：** 系统先定义哪些信息必须通过工具获得、哪些动作需要工具和审批，再让模型在这些边界内选择。对实时数据、用户私有数据、精确计算和外部副作用，应强制工具；对模型已知且低风险的解释可直接回答。关键任务可用分类器/规则做前置路由，并用 tool selection accuracy 和 unnecessary call rate 评测。

## AGENT-06｜如何设计 Tool / Function Calling 的 schema？

**关键词：** 单一职责、强类型、枚举、描述、最小参数、版本  
**关联：** LLM-06、AGENT-04、MCP-03

**参考答案：** 一个工具只做一件可验证的事；参数名和描述明确，尽量使用枚举、范围、必填和互斥约束，避免自由文本承载复杂协议。输出返回稳定业务 ID、状态和可诊断错误；schema 需要版本化和兼容策略。副作用参数与检索参数分开，高风险工具不应被模糊描述诱导调用。

## AGENT-07｜工具失败时如何恢复？

**关键词：** taxonomy、retryable、backoff、fallback、best-so-far  
**关联：** AGENT-08、EVAL-05、PROJ-14

**参考答案：** 先区分参数错误、鉴权、限流、瞬时网络、业务拒绝和不可恢复失败；只有可重试错误才按退避和 jitter 重试。参数问题可让模型基于结构化错误修正一次，服务故障走备用工具或降级，副作用调用用幂等键避免重复。达到预算后返回 best-so-far 和明确未完成项，而不是无限循环。

## AGENT-08｜如何避免无限循环和过度调用工具？

**关键词：** max steps、预算、状态指纹、stale retry、停止原因  
**关联：** AGENT-02、AGENT-07、PROJ-14

**参考答案：** 同时限制最大轮数、wall-clock、token、费用、同一工具次数和并行 fan-out；对参数、结果 ID 集合和关键状态做指纹，连续无新信息即停止；维护 best-so-far，预算接近上限时降级或澄清。终止条件应由 Runtime 强制，不能只在 prompt 中写“不要循环”。

## AGENT-09｜规划失败时有哪些回退策略？

**关键词：** replan、decompose、clarify、workflow fallback、human-in-loop  
**关联：** AGENT-10、AGENT-13

**参考答案：** 先验证目标、约束和可用工具；计划过大时拆成可验证子任务，观察与假设冲突时局部重规划，信息不足时向用户澄清。高风险或反复失败的任务切回固定 Workflow 或人工审批。回退动作要由失败类型触发，而不是每次重新生成一份完全不同的长计划。

## AGENT-10｜什么时候该用 LangGraph/状态机，而不是普通函数编排？

**关键词：** 显式状态、分支、持久化、恢复、人审、复杂度  
**关联：** MCP-08、PROJ-03

**参考答案：** 固定少量步骤和一个短重试环用普通函数更透明；当存在动态分支、长任务持久化、暂停恢复、人审节点、多次回放或跨进程状态时，显式图有明显收益。框架的价值是状态和运行语义，不是让 Agent“更智能”。选型前应画状态转移图并比较调试、依赖和迁移成本。

## AGENT-11｜多 Agent 为什么可能不如单 Agent？什么时候值得用？

**关键词：** 协调成本、上下文丢失、角色重叠、并行、隔离  
**关联：** AGENT-01、AGENT-12、MCP-05

**参考答案：** 多 Agent 会增加调用次数、状态同步、冲突合并和错误归因，角色定义不清时只是重复思考。只有任务天然可并行、需要权限/模型隔离、上下文过大或可独立验证的专业角色时才值得拆分。先用单 Agent + 工具做 baseline，再比较成功率、延迟和成本，而不是按角色名称证明架构。

## AGENT-12｜多 Agent 的状态如何传递？

**关键词：** shared state、message、artifact、schema、ownership  
**关联：** AGENT-11、MCP-05、EVAL-04

**参考答案：** 把共享状态设计为版本化 schema：任务目标、约束、输入引用、阶段产物、证据 ID、错误和状态版本；大内容放对象存储/数据库，只在消息里传引用。明确每个字段的写入者、合并规则和幂等键，并防止不同 Agent 同时覆盖。传递结论时保留证据和不确定性，避免只传自然语言摘要。

## AGENT-13｜什么时候不该用 Agent？

**关键词：** 确定性、高风险、低容错、可测试、成本  
**关联：** AGENT-01、AGENT-05、ENG-08

**参考答案：** 规则稳定、路径短、错误代价高且输入结构化的任务，优先规则、SQL、普通服务或 Workflow；批量高吞吐、强事务和严格实时场景也不适合把核心控制交给自由决策模型。Agent 更适合开放输入、步骤不可预先穷举、需要工具反馈且允许在受控边界内探索的任务。
