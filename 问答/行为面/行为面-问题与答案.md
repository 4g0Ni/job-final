# 行为面 / 项目复盘问题与答案

> 使用 STAR/CAR，但不要背成流水账。每题准备 60–90 秒版和 3 分钟深挖版；数字、主语和完成度必须与简历一致。

### 1. 请做 2 分钟自我介绍。
我是刘启仁，本硕毕业于电子科技大学，过去四年在 Microsoft Advertising 做软件工程。我的工作有三条主线：第一是 AI 应用工程，我设计并实现了面向多仓库历史变更与回归调查的 Commit AI Resolver。数据面用 Direct SHA、FTS5、dense、metadata 与 RRF 生成候选；控制面由 Incident Commander 动态委派 Retrieval、Diff Investigator 和 Evidence Critic；外围 Harness 强制执行证据授权、工具权限、预算、校验与回退。我还用公开 React 数据建立分层 Eval，并跑通一条读取真实 GitHub Diff 的 gold RCA。第二是大型广告 UI，我长期负责素材、监测、Deal、推荐和质量工程，并参与将关键向导 P95 降低 40%–72%。第三是广告后端项目，包括图片资产生命周期治理、Deal 自动同步、推荐视频批处理和第三方测量服务。下一步我希望把大型系统交付经验与可评估、可观测的 Agent 工程结合起来，负责真正能进入生产闭环的 AI 应用。

### 2. 你为什么想换工作/选择 AI 应用方向？
不要说“传统开发没前途”。可答：我已有大型系统、数据和产品交付基础，Commit AI Resolver 让我看到，Agent 系统真正难的不是接入模型，而是让检索证据、拒答边界、工具调用、评测、延迟和成本形成可靠闭环，这正好与我的工程优势重合。下一步希望继续在真实用户和生产约束下深入 AI 应用与 Agent 工程。

### 3. 你最有代表性的 AI contribution 是什么？
优先讲 Commit AI Resolver。我的核心贡献不是“接了一个向量库”，而是把历史 Commit 调查拆成可验证的数据面和控制面。数据面以 JSON source of truth 和版本化索引保证可审计、可重建；通用查询使用 Direct SHA、FTS5、Dense、Multi-query 与 weighted RRF，Issue-grounded RCA 则用生命周期时间窗、四路候选和本地 LTR。控制面使用 OpenAI Agents SDK，由 Incident Commander 根据证据动态委派 Retrieval、Diff Investigator 和 Evidence Critic；SDK 外的 Harness 负责 Candidate Ledger、工具白名单、多维预算、去重、超时、输出校验和 fallback。75-case 工程回归集与 461 条真实 Issue/closing PR/fix commit cases 用于分层 Eval 和 badcase 诊断。一次真实 gold RCA 中，系统读取 3 个 GitHub Diff 后命中目标修复 Commit，Critic 又因为没有找到 introducing commit，把结论降为 PARTIAL。最后通过 6 个 MCP 工具把共享检索和 Diff 能力提供给 IDE Agent。Gate v2 仍需 hard negative/OOD 标定后接入；不把设计稿或单次 live case 包装成生产准确率。

### 4. 讲一个最难的性能问题。
Situation：广告组向导 P95 8–10 秒。Task：判断 UI、网络还是后端瓶颈并在不破坏复杂业务规则下提速。Action：增加分段遥测，用 React Profiler 找重渲染；懒渲染隐藏 Backbone 面板、稳定 props/state；预热和拆分可缓存请求，绕过非必要初始 API，并与 MT/MDS 协作。Result：编辑 10s→2.8s，创建 8s→2.7s，Native 创建 6s→3.6s。复盘要强调团队成果与个人负责项。

### 5. 讲一次从 0 到 GA 的项目。
选第三方监测。按需求背景→厂商/广告形态组合复杂度→数据模型与校验→和 MT 的错误码契约→测试矩阵→pilot 灰度→遥测与 GA 展开。不要只罗列 IAS/DV/ISPOT 名字，要讲如何控制组合爆炸和线上误伤。

### 6. 讲一次你犯的错误或方案不足。
可讲 Commit AI Resolver 最初把 date、author、risk 与语义文本一起 embedding，过滤又发生在全局 KNN 之后；在早期约 2,300 条数据上不明显，但扩大到 27,646 条公开历史语料时会造成语义污染和过滤漏召回。我随后把结构化字段移回 metadata，加入 FTS5 通道、窄条件先过滤后精确 cosine、索引契约和 Eval Harness。补齐长 commit body 与 path 后，又通过同 case 对比发现 Dense title query 会被长文档稀释，说明“信息更完整”不等于“单向量排序一定更好”。复盘重点是：小规模“能跑”不代表检索语义正确，索引设计必须从失败模式和可重建性出发。

### 7. 讲一次线上故障/高压处理。
用 DRI 案例：先明确影响面和是否需要止血；Kusto 看错误趋势、受影响 tenant/版本；关联发布与 commit；用 feature flag/回滚控制影响；复现、修复、验证后逐级恢复；最后补监控和测试。回答重点是冷静、证据链和沟通节奏，而不是英雄主义。

### 8. 如何处理和后端/数据团队的分歧？
先把争议转为共同目标和可测指标。例如性能问题用分段 trace 区分 UI、MT、MDS 时间；契约分歧用错误码、schema 和兼容策略落文档；无法一次统一时用 feature flag/A-B 小流量验证。描述一个你改变观点或折中方案的实例更加分。

### 9. 你如何确定优先级？
按用户/业务影响、风险、紧迫性、依赖和投入排序。P0 先止血；AI 功能优先做评测和安全边界再增加自主性；性能先攻关键路径和 P95，不在低影响组件过度优化。对外明确不做什么以及重新评估时间。

### 10. 你如何保证自己没有夸大团队成果？
用三层主语：平台规模用“项目/团队”；自己负责用“我实现/主导的模块”；协同成果用“我们共同交付”。准备 commit/设计/指标证据。比如 90+ 作业是仓库规模，性能总体数字是团队生产结果，而 partial render、具体遥测和 A11y 修复是个人贡献。

### 11. 讲一个你推动质量改进的例子。
可讲 Enzyme 到现代测试框架迁移、A11y 焦点治理或数据幂等回填。结构：原有失败模式→为什么单点修补不够→沉淀规则/工具/测试→如何验证和推广。展示你不仅修 bug，还降低同类问题复发率。

### 12. 你如何快速熟悉十万文件级 monorepo？
先从用户入口和运行时链路定位 package；读路由、组件、数据 hook/API、后端契约和遥测；用 git 历史找领域 owner 和设计演化；缩小到具体 package 后再构建/测试，避免全仓扫描。先形成架构图与验证假设，再改代码。

### 13. 讲一次技术选型。
选 SQLite FTS5 + sqlite-vec：当前离线 Demo 已对 27,646 条公开 Commit 完整建库，嵌入式单文件便于本地打包、审计和从 JSON 重建；关键词与 dense 召回通过 RRF 融合，窄 metadata 条件先过滤再精确排序。在单机 Demo 和当前数量级下，专业向量库会增加部署与运维复杂度；当候选达到数十万以上、暴力扫描 P95 不达标，或出现多租户、高并发、复杂 pre-filter 与高可用需求时，再以 Recall—P95—内存 benchmark 决定是否迁移 ANN/HNSW，而不是只按数据条数选型。

### 14. 如果面试官指出你的项目不是真正的 Agent，怎么回答？
先承认历史版本确实是固定阶段加 Evaluator 反馈循环的 agentic workflow，然后说明现在已经完成控制面重构。Incident Commander 通过 agents-as-tools 看到 Retrieval、Diff Investigator 和 Evidence Critic，它根据问题、Observation 和剩余预算决定下一步，不是 JavaScript 固定调用顺序；不同查询可以只检索、继续查 Diff、调用 Critic、澄清或停止。三个 Specialist 有独立 prompt、tool allowlist 和结构化输出。与此同时，Harness 保留 Candidate Ledger、权限、预算、超时和引用校验。我的判断标准不是类名数量，而是模型是否真正改变运行路径，以及这个决策是否能从 trajectory 中验证。

### 15. 讲一个失败或未达到预期的项目。
可以讲 Eval 可信度和 Recall 优化的多轮迭代：离开原公司后不能继续使用内部 case，我先基于公开 React Commit 重建 75-case 验证集；但它包含程序生成和标题派生正例，即使 frozen test 达到 100%，也不能包装成严格外部盲测，因此重新定位为工程回归集。随后构建 461 条真实 Issue/closing PR/fix commit RCA cases（模型预审版），早期等权 RRF 出现“救回 9 条、挤出 27 条”的负收益；修完融合后，第一版四路 Top-100 candidate availability 仍只有 85.82%，证明继续换 reranker 不可能达到 90% Recall@20。我再利用 Issue 生命周期 metadata 和本地 LTR，将 grouped 134-case held-out test Recall@20 从 70.90% 提高到 94.78%。接着复查下游并设计三层 Gate v2。最近真实 multi-agent RCA 虽然命中 gold fix，却用了 92.4 秒和 3 个同源 Diff，因此下一步重点是 Gate v2 标定、paired batch eval、同源去重和延迟成本优化。这个故事的重点是承认边界、分层定位、用负结果改变方案。

### 16. 你收到过最有价值的反馈是什么？
建议准备真实反馈。回答应包含：反馈内容、你最初的反应、采取的具体变化、后续可观察结果。不要答“太追求完美”这种伪缺点。

### 17. 你的优势是什么？
“一纵两横”：纵向能在大型广告产品把复杂功能做到 GA；横向一是数据/指标，能用遥测和统计验证效果；二是 AI/Agent，能做 RAG、编排和 MCP。用三个证据分别支撑，不要只列形容词。

### 18. 你的短板是什么？
可诚实说：没有基础模型训练/大规模 GPU 训练的生产经验，强项是 AI 应用工程而非算法研究；在 Agent 方向已经完成 27,646 条公开 corpus、75-case 工程回归集、461 条 RCA gold cases 模型预审版及其全量 retrieval Eval，并在 Issue-grounded 条件下用时间窗和本地 LTR 将 134-case held-out test Recall@20 做到 94.78%。但 461 条仍需完成人工 rubric 才能成为 release-gate gold；该指标也不适用于普通 text-only 查询，且还缺开放 Issue、真实模型全链路、生产流量与长期反馈闭环验证。随后说明会通过人工标注、灰度流量和质量—成本—延迟持续校准补齐，不把“第一版工程完成”包装成成熟平台。

### 19. 未来 2–3 年规划？
成为能对 AI 应用效果与生产可靠性共同负责的工程师：不仅接模型 API，还能定义 eval、检索/工具架构、观测、安全和成本，并带动团队把原型变成可持续产品。

### 20. 为什么选择我们？
必须按公司定制：产品是否有真实 Agent 使用场景；团队是否拥有数据闭环和评测基础；岗位是否需要大型工程与 AI 的结合。引用 JD/产品的具体一两点，再说明你的经历如何补位，避免泛泛夸行业前景。

### 22. 如果给你一个月改善现有 Agent，你怎么做？
第一周冻结 workflow 与 multi-agent 基线，建立任务成功、路由、P95、调用量和每成功任务成本指标；第二周补 gold trajectory、工具故障、Prompt Injection、超时和 malformed output 用例；第三周按 Top badcase 修改检索、工具或 Harness 策略，通过 feature flag 做 paired/shadow 验证；第四周观察质量与成本阈值，演练 fallback/kill switch 并沉淀文档。Commit AI Resolver 已有四 Agent vertical slice、Candidate Ledger、多维预算、JSON/SSE trace 和真实 RCA 样例，所以我会优先扩大人工复核与批量全链路评测，而不是继续增加 Agent 数量。
