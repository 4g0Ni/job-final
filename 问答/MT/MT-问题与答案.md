# MT / 后端 / 中间层问题与答案

> 从用户提供的 110+ 题 HTML 全量提取；覆盖 C#/.NET、SQL、异步任务、API、灰度、系统设计与行为面。

## 板块一 · MS Deals 程序化交易

### 1. 什么是程序化 Deal(Programmatic Deal)?你为什么要做这个系统?

程序化 Deal 是广告主和媒体之间的一种预先协商的私有交易:媒体把优质库存(比如某些优质版位、特定受众)打包成一个 Deal,广告主可以通过程序化的方式优先、以约定价格购买。它介于公开竞价(RTB)和纯手动直采之间,兼顾了效率和优质流量。我们做这个系统,是因为 Deal 的源数据在第三方平台 Xandr,需要把它同步进微软广告自己的投放系统,让广告主能像管理普通 Campaign 一样使用 Deal。我负责的是整条同步管道 + 数据建模 + 定向约束在中间层的落地。

### 2. Xandr Deal 到 MS Deal 的同步管道具体怎么设计的?

整体是一个定时拉取 + 映射 + 落地的离线管道。第一步,调用 Xandr 新版 Deal API 分页拉取所有 Deal(数据量大,必须 pagination,否则超时/内存爆)。第二步,把 Xandr 的 Deal 实体映射转换成我们内部的 Deal 模型,这一步有大量字段对齐工作,比如年龄区间、性别、地域、genre、KR/JP 特殊字段。第三步,做校验,过滤掉不合法或不需要的 Deal(比如按 seller name 过滤)。第四步,通过内部 WCF 接口刷新系统级实体,写入我们的存储。整个流程挂成一个定时离线任务,失败有重试和监控告警。我做了好几个版本迭代(Mapper V1→V4),不断修正映射规则。

### 3. 为什么用 BitMask 特性位来标记 IsDealCampaign?直接加个布尔字段不行吗?

这是个很实际的权衡。我们的 Campaign 实体上已经有一个 Feature BitMask 字段,用来表示 Campaign 的各种布尔特性。用一个已有 BitMask 里的一位来表示 IsDealCampaign,好处是:一,不用改表结构——加新列在分库分表的大表上是很重的操作,要改 schema、要迁移、要改多处读写;用现有 BitMask 位是零 schema 变更。二,读取路径已经现成——CampaignInfo、AdGroup fetcher 这些地方本来就在读 BitMask,加一位天然就被带出来了,不用改查询。三,多入口一致性——SOAP、Bulk、WCF 都读同一个 BitMask,不会出现某个入口漏读的问题。代价是可读性稍差、位要专门预留和文档化,所以我专门提了个 PR 去 reserve 这一位,避免和别人冲突。

### 4. Deal 的定向约束规则你是怎么实现的?举个具体例子。

Deal 有很强的合规约束,比如只能投在 Deal 公告的国家。实现上,我在广告组(Ad Group)和 Campaign Criterion 的校验层(Validator)加规则:当检测到这是个 Deal Campaign(读 IsDealCampaign 位),就限制它的地域定向只能是 Deal 声明的那个国家 GEO,其它地域直接拒绝或忽略。类似地,我禁用了年龄、性别、受众、设备等定向(banned targeting),因为 Deal 的定向由媒体侧决定,广告主不能再叠加。还有一个有意思的是视频时长约束:Deal 广告的视频时长不能超过 Deal 创意本身的时长,我在视频校验里加了这个 check。这些规则都要同时覆盖 add 和 update 场景。

### 5. Deal 上线时你踩过什么坑?怎么解决的?

最典型的是误判问题:上线灰度时发现有些普通的 Brand Awareness Campaign 被错误识别成了 Deal Campaign,直接 block 了用户操作,这在 GA 前是致命的。我做了两件事:一是紧急放开(unblock)误判场景,把 Smart Ad Group Id invalid、Brand Awareness 误判这些 case 加白名单快速解锁,先保证不影响正常广告主;二是回头修根因的检测逻辑。另一类坑是测试环境没有对应数据——比如 SI 环境里没有 FR 地域的 Deal,导致测试挂,我就把这些测试改成 CI-only 或调整测试数据。这段经历让我养成一个习惯:任何新的拦截规则,上线前先想清楚它的误伤面,并准备好快速解锁的开关。

### 6. Deal V1 到 V2 的迁移,以及最后 deprecate V1,你是怎么做的?

这是一个安全下线的过程。原则是先并行、再切流、最后删码。V2 上线后,V1 和 V2 有一段共存期,用动态配置控制走哪条路径。等 V2 在生产稳定、覆盖所有市场后,我先切断 V1 的流量入口(关掉相关 pilot/config),观察一段时间没有依赖后,再清理 V1 的代码和管道(deprecate auto-create campaign、清 V1 deal code)。删码前我会搜索所有引用,确认没有活跃调用。最近我还做了 Xandr Deal → MS Deal refresh 管道的整体 deprecation,把已经不需要的 RefreshDeals 改成 no-op。下线比上线更需要谨慎,因为出问题往往是静默的。

### 7. Deal 数据同步是最终一致的,如果 Xandr 那边的 Deal 变了但还没同步过来,广告投放会有问题吗?

会有短暂的数据滞后窗口,这是异步同步管道的固有特性。我们的缓解措施有几层:一是控制同步频率,定时任务跑得足够勤,把窗口压到可接受范围;二是加了 Deal sync time 的检查,如果发现某个 Deal 很久没同步成功,会告警,避免用陈旧数据静默投放;三是对于Deal 失效(not active)的场景做了容错——因为 Deal 过期是每天都会发生的正常现象,我特意把这类日志降级,不当错误处理,避免告警噪音。核心思路是:接受最终一致,但要有可观测性知道滞后有多严重,以及对已知的正常态降噪。

### 8. 如果让你重新设计这套 Deal 同步,你会怎么改进?

几点:一,从全量拉取转向增量/事件驱动。现在是定时全量分页拉,数据量大时浪费。如果 Xandr 能提供变更事件或增量 API,改成增量同步能大幅降负载、缩短滞后。二,映射逻辑配置化。我迭代了 Mapper V1 到 V4,说明字段映射变化频繁,如果把映射规则做成配置/DSL,而不是硬编码,迭代会更快、更安全。三,更强的对账机制。定期跑一个对账任务,比对我方和 Xandr 侧的 Deal 数量和关键字段,主动发现同步漏洞,而不是等广告主报障。四,BitMask 的可读性,长期看可以配一个强类型的 feature accessor 层,避免直接操作位。

## 板块二 · AIGC 视频推荐 & 限流

### 9. Video Recommendation 功能的整体流程讲一下?

目标是给广告主自动生成推荐的视频创意。流程是:触发 → 挑选策略 → 调用生成 → 回写。触发端用 Cosmos DB Trigger——当某些条件满足(比如广告有合适的图片素材)时,触发器拉起一个离线任务。任务里我按 排名(Rank)、预算、模板 ID 来决定用什么策略、生成什么样的视频,然后调用 ClipChamp 的视频生成服务(AIGC)。生成完拿到视频 URL,再把结果回写成一个视频推荐机会(opportunity),最后透出给广告主。整个链路是异步的,因为视频生成很慢。

### 10. 你提到用 Azure Queue 做限流,能详细讲讲这个技术难点吗?

这是这个项目最硬的点。问题是:外部的 AIGC 视频导出/生成 API 又贵又脆,不能高并发直接打——并发一高,对方限流甚至挂,我们这边还会因为凭据过期大面积失败。我的方案是在中间加一层 Azure Queue 做削峰(throttling):所有导出请求不直接调 API,而是先入队,再由消费端按受控的速率出队去调外部 API。这样把突发的流量尖峰摊平成平稳的调用速率。配套还做了:凭据问题的重试处理、批量降级(downgrade batch size)——一次处理不了那么多就调小批量,以及部分成功处理(partial handle)——一个批次里失败几个不 fail 整个任务。这套下来稳定性明显改善。

### 11. 为什么选 Azure Queue 而不是别的方案,比如令牌桶限流或者信号量?

好问题。进程内的令牌桶/信号量只能限单实例的并发,但我们的任务跑在多个分布式 worker上,需要的是全局速率控制。Azure Queue 天然提供了:一,分布式解耦——生产和消费分离,多个消费者按自己的节奏拉,天然平滑;二,持久化和重试——消息不会因为某个 worker 挂了就丢,visibility timeout 机制自带重试;三,削峰缓冲——突发请求先堆在队列里,不会瞬间压垮下游。相比自己搞分布式令牌桶(要引入 Redis 之类的共享状态),用现成的 Azure Queue 更简单、更可靠。代价是引入了异步和最终一致,但视频生成本来就是异步慢操作,完全能接受。

### 12. 你在这个项目修了很多线上 bug,印象最深的 P0 是哪个?

有一个 P0/P1 优先级冲突的 bug 印象很深。我们有 P0(高优先)和 P1(低优先)两类视频推荐场景,它们在某个共享路径上互相干扰、状态碰撞,导致任务错乱。还有一个 URL 黑名单的 P0——某些源 URL 会导致生成失败或不合规,必须在生成前拦掉。这些都是灰度放量后才暴露的,因为只有真实流量才能触发这些边界。我的处理方式是:先用动态配置快速止血(比如临时关掉某个场景),再定位根因修复,最后补测试防回归。这段经历让我对灰度期间的快速响应和容错设计理解很深。

### 13. 视频生成是耗时操作,任务超时或卡住怎么办?

几个层面:一,任务本身设计成可重入/幂等,超时后重试不会产生重复的视频或脏数据。二,用 checkpoint/状态机——任务在关键步骤保存进度,重试时能从断点继续,而不是从头再来。三,合理的过期策略——给任务设过期时间,长期卡死的任务会被清理而不是无限占资源。四,监控——对任务的成功率、耗时做遥测,异常升高就告警。我后来还专门做过一个 PR 是把视频推荐任务在失败时改成 complete 而不是 fail——因为某些失败是预期内的(比如源素材不满足),不该反复重试和告警,直接完成掉更干净。

### 14. AIGC 生成的视频质量不可控,产品上怎么保证不会把差的创意推给广告主?

这更多是产品+工程结合的问题。工程侧我做的保障有:一,前置校验——源素材(图片、URL)先过校验和黑名单,不合格的根本不进生成。二,模板约束——生成基于预定义的模板 ID,而不是完全自由生成,质量下限有保证。三,推荐而非自动应用——生成结果是作为推荐机会(opportunity)透出,广告主可以选择采纳或忽略,不会自动上线,人在环路里。四,灰度——先小流量白名单账户验证效果,再逐步放开。整体思路是:工程保证下限和安全,产品和用户决定采纳。

## 板块三 · Impression Tracking & 第三方测量

### 15. Ad Impression Tracking 是做什么的?为什么要迁移到 Task Engine?

Impression Tracking 是广告展示监测:广告每次被展示,要按配置去触发对应的监测(比如通知第三方像素、记录展示)。原来的实现耦合在同步流程里,有性能和扩展问题。迁移到 Task Engine 的动机是:一,异步解耦——展示监测不该阻塞主流程,放到离线任务里跑;二,统一调度和重试——Task Engine 提供了成熟的任务调度、重试、限流、监控框架,不用自己造轮子;三,可扩展——支持多格式(多格式展示广告、视频广告)时,新增处理器很方便。迁移后还支持了用动态配置的开关决定是否为某个设置排队离线任务,灵活可控。

### 16. 迁移到 Task Engine 时,怎么保证展示监测不打爆下游?

这是个真实痛点。我用了两个机制:一,计数器 + 动态配置控制刷新节奏——不是每次都去刷新动态配置,而是加了个计数器,累计到一定次数才刷,降低对配置服务的压力。二,处理单账户任务过载——某些大账户会瞬间产生海量监测任务,我专门加了逻辑检测"账户内任务太多"的场景,做限制或平滑,避免一个账户拖垮整个任务队列。核心思想是速率控制 + 隔离,不让单点热点影响全局。

### 17. IAS、MOAT、ISPOT、DoubleVerify 这些第三方测量厂商,集成时最大的挑战是什么?

最大的挑战是每家协议和规则都不一样,而且都很严格。以 IAS 为例,我要实现 Xandr 第三方像素 API 的增删(add/delete pixel),要处理原生广告(native ad)和展示广告不同的 IAS 设置,还要支持 Campaign 级别的 3P 追踪。每一个都涉及:数据模型扩展(给 Xandr Web DataModel 加属性)、SOAP API 支持、严格的校验规则(什么广告类型允许什么设置)。MOAT 还有和 bulk edit 场景结合的问题。这类工作对协议细节的精确性要求极高,一个字段错了第三方就不认。我的做法是大量写针对性的测试,把各种组合场景覆盖住。

### 18. 为什么第三方测量设置要支持 Change History?

因为第三方测量直接关系到广告计费和合规审计。广告主和第三方之间可能对"广告到底有没有被有效展示"产生争议,这时候谁在什么时候改了哪个测量设置就非常关键。Change History 记录了这些设置的每一次变更(谁、何时、改了什么),提供了审计追溯能力。实现上,我把第三方测量设置的变更接入了系统已有的 Change History 机制,在设置变化时写一条历史记录。这也是广告系统里很多敏感配置的通用要求——可审计性。

### 19. 3P tracking 和 MOAT 结合时你修过一个 bug,是什么?

是 3p measurement 和 MOAT 场景一起用时的 bug。具体是两个测量设置叠加时,某些字段的处理逻辑冲突,导致追踪不生效或数据不对。这类 bug 的根因通常是:两个特性各自开发时没考虑对方,组合场景没测到。我修复后专门补了组合场景的测试。这也印证了前面说的——第三方测量这块,组合爆炸是最大的测试难点,你有 N 个厂商 × M 种广告类型 × K 种操作,必须系统性地覆盖关键组合。

## 板块四 · Task Engine / 异步任务框架

### 20. 你们的 Task Engine 是什么?它解决了什么问题?

Task Engine 是我们内部的分布式异步任务框架。广告系统里有大量不能放在同步请求里做的重活儿:视频生成、图像处理、批量回填、展示监测、性能评分等等。Task Engine 提供了统一的能力:任务的排队、调度、分发到多个 worker、重试、限流、优先级、过期、监控告警、checkpoint。开发一个新的异步能力,我只需要定义一个新的任务类型(task type)和对应的处理器(processor),注册进容器,剩下的调度和可靠性由框架保证。它本质上和开源的分布式任务队列(如 Celery、Temporal)解决的是同类问题,只是深度耦合了我们的广告数据层。

### 21. 新增一个 task type 具体要做哪些事?以 OfflinePerformancePredictionScore_V2 为例。

以我做的 PPS V2 为例,分中间层和数据层两部分:数据层——注册新的任务类型枚举、写一个调度存储过程(比如 prc_QueuePerformancePredictionBackfillTaskV2)负责按条件把任务塞进队列表、注册对应的 SystemParameter、把这些注册进 Hotfix 部署列表(.lst 文件)。中间层——实现任务的 Processor(处理逻辑),在 DI 容器里注册,处理 checkpoint、诊断信息、请求上下文(比如用 request 的 CustomerId)。然后配限流(ExecutionThrottlingConfig)——dequeue 限制、Lookback 窗口。最后加单元测试和功能测试,先 CI-only 稳定后放开。整个是一个横跨两层的完整闭环。

### 22. Backfill(回填)任务是什么?为什么需要专门的回填?

回填是给存量数据补算/补数的批处理。比如上线一个新的评分特性,增量流量会自动算,但历史上已经存在的海量广告没有分数,需要专门跑一遍。回填的挑战在于量大、要控速、不能影响线上。我们的做法是:一,专门的调度器按批把回填任务塞进队列,而不是一次性全塞爆;二,批量粒度控制——比如一个任务处理 N 个 campaign,而不是一个 campaign 一个任务,减少任务数;三,频率/限流可调——SI 和 Prod 用不同频率,能随时调整甚至暂停;四,幂等——回填可能要重跑,必须保证重复执行不出错。回填做不好很容易把生产 DB 压垮,所以限流和可暂停是关键。

### 23. Task Engine 的任务优先级是怎么回事?为什么需要?

因为不同任务的时效要求不同。用户实时触发的评分(比如刚创建广告,要马上给反馈)是高优先,而后台的批量回填是低优先,可以慢慢跑。如果不分优先级,回填的海量任务会把队列堵死,高优先任务饿死,用户体验就崩了。我们支持了优先级队列,高优先任务插队先跑。我参与的场景里,就有把 PPS 评分通过高优先任务排队的需求。这本质是资源调度里的 QoS(服务质量)保证——把有限的处理能力优先给延迟敏感的任务。

### 24. Cosmos DB Trigger 在你们架构里扮演什么角色?

Cosmos DB Trigger 是我们事件驱动触发离线任务的一种方式。简单说,某些数据写入 Cosmos 后,会通过 change feed / trigger 机制拉起对应的处理任务,而不需要主动轮询。我在视频推荐、隐私检查等场景都用过这个模式:数据变更 → 触发器 → 排队 Task Engine 任务 → 处理器执行。它的好处是解耦和实时性——生产者只管写数据,消费者由触发器自动拉起。不过它也有坑,我修过触发文件重命名、触发条件、cron schedule 校验相关的 bug,这类事件驱动系统的触发时机和幂等特别要小心。

### 25. 如果一个任务反复失败,会无限重试吗?怎么避免任务风暴?

不会无限重试。框架有最大重试次数和退避(backoff)。超过上限的任务会被标记为最终失败(或按业务需要 complete 掉),进入死信/告警,而不是无限循环。我实际处理过这类问题:把预期内的失败直接 complete 而不是 fail,避免它反复重试制造噪音和负载。另外防任务风暴还靠限流(dequeue limit)和账户级隔离——即使某类任务大量失败,也被限速,不会瞬间放大成风暴打垮下游。核心原则:失败要有上限、要能降级、要可观测。

## 板块五 · SQL Server & 数据层 / 分库分表

### 26. 你们的数据层为什么要分库分表(Sharding)?怎么分的?

因为广告数据量极大——账户、Campaign、AdGroup、Ad、Criterion 层层展开,单库单表根本扛不住。我们按业务维度分片,能看到像 CampaignAdGroupShardDB、DSPAdGroupShardDB、AdminMainShardDB 这样的分片库,以及对应的 Shard schema 和 UT_Shard 单元测试。分片的核心是选一个好的分片键(通常和账户/Campaign 相关),让同一个逻辑单元的数据落在同一片,避免跨片查询。我在数据层的工作包括写分片库的 Schema、存储过程、单元测试,以及保证新特性的存储过程在分片环境下正确。分库分表最大的复杂度是跨片操作和一致性,所以设计时尽量让操作局限在单片内。

### 27. 你写过哪些有代表性的存储过程?

几个:一,PPS 的调度存储过程 prc_QueuePerformancePredictionBackfillTaskV2——按条件批量把回填任务塞进任务队列表。二,EntityStrengthMerge——把广告强度数据合并更新进 AdStrengthData 表,这里 merge 语义要处理插入和更新。三,Orphan Image 清理的存储过程——支持多账户批量清理和激活素材。四,offline task 的获取存储过程(prc_PublicOffLineTaskGet)。我也熟悉Change History 相关的存储过程。写存储过程我关注:批量而非逐行、正确的事务边界、避免锁竞争、幂等。

### 28. 大表上加一个新列,你会怎么操作?有什么风险?

在分库分表的大表上加列是高风险操作。风险主要是:加列可能锁表(尤其带默认值或非空约束时),在生产大表上会造成阻塞甚至事故。我的原则:一,尽量避免——像前面讲的 IsDealCampaign,我就用现有 BitMask 位而不是加新列。二,如果必须加,加可空列且不带默认值(这样通常是元数据变更,快),然后分批回填数据,最后再按需加约束。三,分片环境要每个分片都执行,通过部署流水线统一发布。四,先在 SI 验证,再灰度到生产。总之能不动 schema 就不动,要动就用最轻量的方式并且分步走。

### 29. .lst 文件和 Hotfix 部署列表是什么?

这是我们数据层的部署清单机制。数据库对象(存储过程、系统参数等)的部署不是随便跑脚本,而是要注册进对应的清单文件(.lst),由部署流水线按清单来发布。比如我新增了 PPS V2 的存储过程和 SystemParameter,就要把它们注册进 CampaignDB_Hotfix.lst,这样 hotfix 部署时才会带上它们。这个机制保证了部署的可控和可追溯——哪些对象在哪次部署上线,清清楚楚,不会漏发或乱发。对我来说,做完数据层改动后记得更新 .lst 是一个必须的步骤,漏了会导致代码合了但生产没生效。

### 30. 数据层的单元测试(UT_Main / UT_Shard)怎么做?数据库逻辑也能单测?

可以。我们对存储过程有专门的SQL 单元测试,分主库测试(UT_Main)和分片库测试(UT_Shard)。做法大致是:准备测试数据 → 调用存储过程 → 断言结果表/返回值符合预期,并且能在 CI 里针对一个测试数据库自动跑。这样存储过程的逻辑变更能被回归测试保护住。它和应用层单测理念一样,只是断言的是 SQL 行为。这块对保证数据层质量很关键,因为存储过程一旦出错影响面极大,而且线上很难调试。所以我改存储过程一定配套改/加 UT。

### 31. Datamart(FDP)和 ClickHouse 在你们体系里是干什么的?

这是数据/BI 分析侧。Datamart(内部叫 FDP)是把广告投放的数据抽取、加工成便于分析和报表的数据集市,支撑各种报表和指标。我做过给 FDP 的文章(article)加行、给 C2C 的视频表加属性列这类数据模型扩展。ClickHouse 是列式 OLAP 数据库,用于大规模分析查询(比如监控看板、性能分析),团队在上面建了不少监控 dashboard。我在 MT 侧也接触过 ClickHouse 的部署监控相关内容。整体上,OLTP(SQL Server 分片)扛在线投放,OLAP(ClickHouse)+ Datamart 扛分析,职责分离。

## 板块六 · API 设计(SOAP / WCF / Bulk / OData)

### 32. 你们同一个功能要支持 SOAP、Bulk、OData 多种 API,为什么?怎么保证一致性?

因为不同客户用不同的接入方式:SOAP/WCF 是传统的强类型 API,很多老客户和内部服务在用;Bulk API 是给需要批量上传下载大量实体的客户(比如一次改几万个广告),用 TSV/CSV 文件;OData REST 是更现代的 RESTful 接入。同一个特性(比如 Deal、Disclaimer、IAS)往往要在这几个入口都支持。保证一致性的关键是:把核心业务逻辑下沉到共享层(校验、映射、EO 实体操作),各 API 入口只做协议适配,复用同一套底层逻辑。像 IsDealCampaign 用 BitMask,就是为了让所有入口读同一个数据源。如果每个入口各写一套逻辑,必然会出现某个入口漏改的 bug——我实际就修过 Bulk 和 SOAP 行为不一致的问题。

### 33. WSDL / XSD 在你们的 API 里起什么作用?改动它要注意什么?

WSDL 定义 SOAP 服务的接口契约,XSD 定义数据类型的 schema。它们是API 的强类型契约,客户端根据它们生成代码。改动它们要极其小心,因为是对外契约,牵一发动全身:一,只能向后兼容地加——加可选字段没问题,改现有字段类型或删字段会破坏老客户。二,加字段要同步更新序列化、映射、校验。我做 IAS、Deal、视频广告这些特性时都改过 XSD 加属性(比如给 Ad entity、XandrTargeting 加字段)。原则是加法而非改法,可选而非必填,保证老客户不受影响。

### 34. Bulk API 的 delete_value 场景你处理过,能讲讲吗?

Bulk 是基于文件的批量编辑,有个特殊语义:用户怎么表达"我要把这个字段清空"?这就是 delete_value——一个特殊标记,表示"删除这个值/置空",区别于"不修改这个字段"(留空通常表示不动)。我处理过让 mapper 正确解释 delete_value 的问题,比如图片广告扩展、Ad Impression Tracking URL 的增改场景。坑在于:"字段留空"和"显式删除"是两个完全不同的意图,mapper 必须能区分,否则要么误删用户数据,要么删不掉。这是 Bulk API 一个很典型的、容易出 bug 的细节。

### 35. Bulk 上传的一个批次里,部分成功部分失败,你们怎么处理?

Bulk 的核心诉求就是部分成功——用户传几万行,不能因为其中几行错就全部回滚。所以处理是逐行独立校验和应用:每一行有自己的成功/失败状态和错误信息,失败的行返回具体错误,成功的行正常生效。这要求行与行之间尽量隔离,一行的失败不污染其他行。实现上要注意错误信息要精确到行、要可读(用户要能看懂哪行为什么错),我做过enrich error message 的工作就是为了让错误更明确。另外要注意批次内的顺序依赖(比如先加 Campaign 再加它下面的 AdGroup),这类依赖要正确处理排序。

### 36. OData API 你了解吗?和 SOAP 比有什么取舍?

了解,我们新的一些接口走 OData REST(.NET Core 那套 BingAds.Api 里)。对比:SOAP 强类型、契约严格(WSDL)、工具链成熟,但重、啰嗦、对 web/移动端不友好;OData 是 RESTful,基于 HTTP,支持标准的查询语义($filter、$select 等),更轻、更现代、更适合新客户端。取舍上,存量和内部强类型场景保留 SOAP,新特性和对外现代接入用 OData。我也做过给 Ad Strength 加 OData API。趋势是往 REST/OData 和 .NET Core 迁移,但因为存量巨大,SOAP 会长期共存。这也是大型遗留系统的常态——多协议并存,逐步演进。

## 板块七 · 灰度发布 & 上线安全

### 37. 你反复提到 dynamic config 灰度,能系统讲一下你们的发布流程吗?

我们的大特性几乎都走动态配置(Dynamic Config)控制的灰度发布。流程大致是:一,代码带开关上线——新逻辑用一个 dynamic config flag 包起来,默认关闭,所以代码合进主干、部署到生产,但功能不生效(dark launch)。二,SI 环境验证——先在集成测试环境打开,跑功能测试。三,生产 pilot 小流量——用白名单账户或百分比放量,比如先 1%。四,逐步放量——1% → 5% → 15% → 35% → 70% → 100%,每一档观察监控和指标。五,GA——全量后,稳定一段时间再清理开关和旧代码。好处是任何一步出问题都能秒级关闭 config 回滚,不用重新部署。我做 Privacy Check 时就是这么一档档往上放的。

### 38. 动态配置回滚和代码回滚(重新部署)相比,好在哪?

核心是速度和风险。代码回滚要重新构建、走部署流水线、可能几十分钟甚至几小时,而且部署本身有风险(可能引入新问题)。动态配置回滚是改一个配置值,秒级生效,不动代码不重启。生产出事故时,止血速度就是一切——能在 1 分钟内关掉问题特性,和要等 1 小时部署,影响面差几个数量级。所以我们的原则是:高风险特性一定带 config 开关上线,把"能不能快速关掉"作为设计的一部分。代价是代码里会有一堆 if-flag 分支,GA 后要记得及时清理,否则技术债累积。

### 39. 灰度放量到某一档发现指标异常,你的处理流程是什么?

标准动作:一,立即回退档位——先把 config 调回上一个安全档位(或直接关闭)止血,不纠结根因。二,确认止血生效——看监控指标是否回落。三,定位根因——拉日志、看遥测(Kusto)、复现问题。四,修复 + 补测试——改代码,补上能覆盖这个场景的测试防回归。五,重新灰度——修复上线后,再从小流量重新往上放。关键是先止血后查因,不要在生产带着问题继续排查。我在视频推荐灰度时就是这么处理 P0 的——先关场景,再修 bug。

### 40. 什么是 CI-only 测试?为什么要先设成 CI-only?

CI-only 是指某些测试只在 CI(持续集成)里跑,不进 gated(合入门禁)。为什么这么做?因为有些功能测试/端到端测试天然不稳定(flaky)——依赖外部服务、时序、测试数据,偶尔会误报。如果直接放进 gated,flaky 测试会频繁 block 所有人的 PR,严重拖慢团队。所以新写的 E2E 测试或依赖外部的测试,我们先设成 CI-only 观察一段时间,确认稳定后再提升为 gated。我很多 Deal、视频的测试都经历过这个过程。这是在测试覆盖率和团队速度之间的务实平衡——既要有测试,又不能让不稳定的测试拖垮 CI。

### 41. 你提到的监控告警(ICM)是怎么用的?

ICM 是微软的事故管理系统——当监控规则触发时,自动创建 incident 并按严重级别(Sev)通知/呼叫值班工程师。我做过不少监控告警规则:比如 Deal 生成过程的监控、Impression Tracking 的监控、Orphan Image 邮件的监控、PPS/Ad Strength 的 FDP 告警。设计告警的关键是平衡灵敏度和噪音:太灵敏会疲劳轰炸(狼来了),太迟钝会漏报事故。我处理过降噪——比如把"Deal 每天正常过期"这种预期日志降级,不触发告警。好的告警应该只在真正需要人介入时才响,并且信息足够让人快速定位。

### 42. backfill 回填任务在生产上跑,你怎么保证不影响线上投放?

回填和线上投放共享 DB 和任务系统,必须小心。我的手段:一,限流和低优先级——回填走低优先任务,不和用户实时任务抢资源。二,可调频率 + 可暂停——回填频率做成配置,发现 DB 压力大就调低甚至暂停,SI 和 Prod 用不同频率。三,批量粒度控制——一个任务处理多个实体,减少任务数和调度开销。四,错峰——尽量在低峰期跑。五,监控 DB 指标——盯着 DB 的 CPU、锁、队列长度,异常就退。核心是把回填当成可以随时让路的后台低优先作业,线上永远优先。

## 板块八 · Orphan Image / PPS / Ad Strength

### 43. Orphan Image 治理这个项目,端到端讲一下?

背景:广告系统里累积了大量孤立图片素材——上传了但已经没有任何广告引用的图片,长期占用存储且是治理隐患。我做了一条完整的清理链路:数据层——写存储过程支持多账户批量识别和清理/激活素材。中间层——用 Kubernetes Cron Job 定时跑清理任务;把素材管理服务(OSManagementDAM)迁移进中间层;实现图片校验逻辑(广告扩展、Smart Page 的图片是否还在用)。通知——做了邮件通知服务,提供 WCF API 获取要通知的账户,配合邮件模板,在清理前/后通知相关方。还处理了误报(false alarm)和失败告警。这个项目让我完整走了一遍数据层 + 中间层 + 定时任务 + 通知的全栈后端链路。

### 44. 删除素材是危险操作,怎么保证不误删还在用的图片?

这正是这个项目最需要谨慎的地方。防误删的措施:一,严格的引用检查——清理前要确认图片确实没有任何活跃广告/扩展/Smart Page 引用,校验逻辑要覆盖所有引用来源,漏一个就可能误删。二,先通知后删除——通过邮件提前通知账户,给缓冲期。三,软删除/可恢复——倾向先标记不可用而非物理删除,有回旋余地。四,灰度 + 白名单——先在少量测试账户/SI 上验证,确认识别准确再放开。五,处理误报——上线后紧盯 false alarm,一有误判立即收紧规则。核心原则:破坏性操作宁可保守,先可逆再不可逆,先小范围再全量。

### 45. Performance Prediction Score(PPS)是什么?你负责哪部分?

PPS 是离线性能预测评分——用模型/API 给广告或资产组打一个预测的表现分数,帮助广告主优化。这是我负责的一个大项目:我搭了整体的评分框架(AIGC 评分 API 集成、图像 recontextualization 异步处理、campaign 级批量),也做了任务调度和数据层的落地:引入 OfflinePerformancePredictionScore_V2 task type、实现回填调度任务 QueuePerformancePredictionBackfillTaskV2、数据层的迁移存储过程和 SystemParameter 注册、以及执行限流配置的调优(dequeue 限制、Lookback 窗口、跳过 PerformanceMaxApp 场景、给子任务标注 TriggerSource)。从算法 API 对接到任务管道再到数据落地,是一条完整的端到端特性线。

### 46. Ad Strength / Entity Strength 你做了什么?

Ad Strength(广告强度)是给广告/资产组一个质量强度评分(比如 Poor/Good/Excellent),引导广告主补全素材、提升质量。我做了中间层的强度计算逻辑和数据层落地两块:数据层上,一,新增 Ad Strength 的 DB 属性类型——让强度数据能存储;二,写 EntityStrengthMerge 存储过程——把计算出的强度数据合并更新进 AdStrengthData 表(merge 语义,已有则更新、没有则插入);三,配置 FDP 告警——给 Pmax 和 MMA 场景加 Ad Strength 的告警监控。中间层则负责根据素材数量、质量等因素计算出强度分值。

### 47. EntityStrengthMerge 用 MERGE,并发更新会不会有问题?

会,SQL Server 的 MERGE 在高并发下有已知的坑——比如竞态导致的主键冲突或死锁,如果不加合适的锁提示。处理方式:一,合适的隔离级别和锁提示(如 HOLDLOCK/SERIALIZABLE 配合)保证 merge 的原子性,避免两个并发 merge 都判断"不存在"然后都插入。二,保证幂等——即使重复执行,结果一致。三,批量而非高频单行——减少并发冲突面。四,考虑用 upsert 模式(先 update,影响 0 行再 insert)作为 MERGE 的替代,某些场景更可控。实际中要根据这个表的并发写入模式来选。关键是意识到 MERGE 不是天然并发安全的,要显式处理。

## 板块九 · C# / .NET 语言 & 并发

### 48. .NET Framework 和 .NET Core 你都用,迁移时遇到过什么问题?

我们系统是典型的遗留大单体逐步向 .NET Core 迁移。存量大量 .NET Framework(WCF 强依赖),新代码走 .NET Core(BingAds.Api.NetCore 那套)。迁移的常见问题:一,WCF 在 .NET Core 上支持有限——服务端 WCF 基本要换成 gRPC/REST/OData,这也是我们往 OData 走的原因之一。二,API 差异——一些 Framework API 在 Core 里没有或改了。三,依赖注入和配置模型不同——Core 有内建 DI 和新的配置系统。四,包管理——迁到 PackageReference。策略是新功能用 Core、存量保持、接口层做适配,不搞一刀切大迁移(风险太大),而是模块化渐进迁移。

### 49. 你的任务处理器要处理并发,怎么保证线程安全?

几个层面:一,尽量无状态——处理器本身不持有可变共享状态,每个任务用自己的上下文(比如我做 V2 时特意用 request 的 CustomerId 而不是共享变量),天然避免竞态。二,幂等设计——即使同一任务被并发或重复执行,结果一致,不依赖执行次数。三,数据层用乐观并发或合适的锁——冲突在 DB 层用版本号/事务解决。四,不可变数据优先。五,需要共享状态时用线程安全容器或显式锁,但尽量避免。原则是能无状态就无状态,能幂等就幂等,把并发安全前移到设计层面,而不是到处加锁。加锁多了既容易死锁又难维护。

### 50. async/await 在你们代码里常用吗?用不当会有什么问题?

常用,尤其调外部服务(Xandr、AIGC API、DB)这些 IO 密集操作,用 async 能释放线程、提升吞吐。常见坑:一,同步阻塞异步(.Result / .Wait())——在某些同步上下文会死锁,而且浪费线程,应该一路 async 到底。二,async void——除了事件处理器都不该用,异常无法捕获。三,忘了 ConfigureAwait(false)——在库代码里可能因为捕获同步上下文导致性能问题或死锁。四,并发调用没控制度——一把 Task.WhenAll 几千个请求打爆下游(这正是我用 Azure Queue 限流解决的问题)。用 async 要理解它是为 IO 并发服务的,不是并行计算,而且要注意异常传播和取消(CancellationToken)。

### 51. 依赖注入(DI)在你们项目里怎么用?你注册过组件吗?

用得很多,是我们中间层的骨架。所有的服务、处理器、DAO、client 基本都通过 DI 容器注册和解析。我做新特性时经常要在容器里注册新组件——比如注册新的视频推荐处理器、PPS 处理器。DI 的好处:一,解耦——依赖接口而非实现,便于替换。二,可测试——单测时能注入 mock,这对我们大量用 mock 的测试至关重要。三,生命周期管理——容器管 singleton/scoped/transient。我做 Privacy Check 时还专门改用 DI 获取 client 来提升可测试性。DI 是写可测试、可维护的大型系统的基础。

### 52. C# 里处理大批量数据,怎么避免内存和 GC 问题?

几个实践:一,流式处理而非全量加载——比如 Xandr Deal 分页拉取,不一次性把所有 Deal 读进内存,而是分页/分批处理。二,IEnumerable 惰性求值——用 yield/流式管道,避免中间大 List。三,分批(batch)——回填、bulk 处理都按批,控制单次内存占用。四,及时释放——大对象用完尽快脱离引用,using 释放非托管资源。五,避免大对象堆(LOH)碎片——超过 85KB 的对象进 LOH,大字符串/大数组要留意。六,注意闭包和事件订阅导致的内存泄漏。核心思路是不要把海量数据一次性物化到内存,而是流式、分批处理——这也是我处理广告大数据量的一贯做法。

## 板块十 · 系统设计 & 架构权衡

### 53. 设计一个"广告展示监测"系统,你会怎么设计?(系统设计题)

我会分几步:一,明确需求——广告每次展示要触发监测(通知第三方像素/记录),量级是每天数十亿级展示,要求高吞吐、可容忍秒级延迟、不能丢关键数据但可容忍少量重复。二,架构——展示事件不走同步,进消息队列/任务系统异步消费;消费端按配置去调第三方像素或落库。三,削峰限流——用队列缓冲突发,消费端限速,避免打爆第三方(我实际就是这么做的)。四,可靠性——至少一次投递 + 幂等消费,重试有上限和退避。五,隔离——按账户/租户隔离,防单个大账户拖垮全局。六,可观测——监控成功率、延迟、队列积压,告警。七,配置化——用动态配置控制开关和速率,便于灰度和止血。这基本就是我在 Impression Tracking 迁移 Task Engine 时的真实设计。

### 54. 同步调用第三方 API 和异步任务化,怎么权衡?

看几个维度:延迟要求——如果用户在等结果(实时校验),只能同步或短轮询;如果能接受最终一致(视频生成、监测),异步更好。下游能力——第三方脆弱/有限流的,必须异步 + 队列削峰,同步会被拖垮或拖垮对方。可靠性——异步 + 持久化队列能重试、不丢,同步失败就失败了。耦合——异步解耦,一方故障不直接传导。我的经验是:凡是调外部慢服务、又不要求实时的,一律异步任务化——视频推荐、PPS、Impression Tracking 全是这个模式。代价是引入了异步复杂度(幂等、最终一致、可观测),但对广告这种大流量系统是值得的。

### 55. 你们是大单体架构,如果让你评估拆微服务,你怎么看?

我会务实看待,不盲目拆。单体的优势:强类型跨模块调用、单次部署、事务简单、重构方便,对紧耦合的广告核心逻辑其实有好处。痛点:构建慢、部署耦合、团队间互相影响、技术栈难升级。我们实际的演进不是激进拆微服务,而是渐进式:把明确可独立的部分抽出去(比如某些服务走 AKS 独立部署、.NET Core 化、独立的离线任务处理),核心投放逻辑保持内聚。评估拆分我会看:这个模块是否有独立的伸缩需求、独立的发布节奏、清晰的边界和低耦合的接口。满足才拆,否则拆出来的是分布式单体,更糟。康威定律也要考虑——拆分要匹配团队边界。

### 56. 最终一致性在你们系统里无处不在,怎么向产品/用户解释延迟?

技术上我们接受最终一致(Deal 同步、评分、监测都是),但要管理好可观测性和预期。对内:加滞后监控,知道延迟有多大、有没有超出 SLA,超了就告警。对产品/用户:设定合理的 SLA 承诺(比如"X 分钟内生效"),并让状态可见(任务状态、同步时间)。对于用户敏感的操作,尽量给即时反馈(比如"处理中")而不是让用户以为没生效。我做 Deal 时就加了 sync time 检查,就是为了能发现和暴露异常滞后。核心是:最终一致不等于不可知,要让延迟可测量、可预期、对已知正常态降噪。

### 57. 如果 Xandr(第三方)整个挂了,你的系统会怎样?怎么设计降级?

Xandr 挂了主要影响 Deal 同步和部分 Xandr 相关调用。降级设计:一,隔离故障——Xandr 调用要有超时和熔断,不能因为它挂了把我们的线程/任务全部阻塞拖死。二,用缓存/存量数据继续服务——Deal 数据我们已经同步落地了,Xandr 短暂不可用时,广告投放继续用已有的 Deal 数据,只是新的变更暂时同步不过来(可接受的最终一致)。三,任务重试而非丢弃——同步任务失败进重试队列,等 Xandr 恢复自动追上。四,告警但不误报——区分"Xandr 短暂抖动"和"长时间宕机",避免噪音。核心是本地有数据副本 + 故障隔离 + 自动恢复,让第三方故障降级为"数据滞后"而不是"服务不可用"。

### 58. 设计幂等的离线任务,你的具体做法?

幂等是异步系统的命根子(至少一次投递必然有重复)。做法:一,业务唯一键 + 去重——每个任务有幂等键,执行前检查是否已处理过,处理过就跳过。二,状态机——任务有明确状态(Pending/Processing/Done),用状态流转保证不重复处理,checkpoint 记录进度。三,数据层用 upsert/merge 而非 blind insert——重复执行不会产生重复行(我的 EntityStrengthMerge 就是这思路)。四,外部副作用要幂等或可去重——调第三方 API 带幂等 token,发邮件要去重防重复发送。五,把"已完成"设计成可安全重放。核心口诀:同一个任务执行一次和执行 N 次,系统最终状态必须一致。

## 板块十一 · 测试 / 调试 / 线上故障

### 59. 你怎么处理 flaky(不稳定)测试?

Flaky 测试是大团队的顽疾,我处理过很多。先定位根因分类:一,时序/异步——测试没等异步完成就断言,改成正确的等待/轮询而非 sleep。二,测试数据依赖——依赖了会变的共享数据或外部环境(比如 SI 里某地域没有 Deal),改成自己造独立数据或 mock。三,顺序依赖——测试间互相污染状态,做好隔离和清理。四,外部服务抖动——mock 掉或加重试。缓解策略:实在难根治的先降级为 CI-only 不阻塞门禁,加日志观察,稳定后再提回 gated。我做过给 flaky 测试加更多日志定位、提高 AdGroup bid 防止竞价类 flakiness、rename/隔离 等具体修复。原则:flaky 测试比没测试更坏(它让人不信任测试),必须认真治。

### 60. 生产上一个 bug 只在部分账户复现,你怎么调试?

步骤:一,缩小范围——对比出问题和正常的账户,找差异特征(某个配置、某个 Campaign 类型、某个地域、数据规模)。二,看遥测和日志——用 Kusto 查这些账户的调用链、错误、关键分支,很多时候我做 bug 修复前会先加日志(我大量 commit 就是 add log),把线上现场看清楚。三,本地/SI 复现——用问题账户的数据特征在测试环境复现。四,形成假设并验证——比如"是不是这类广告走了某个未覆盖的分支"。五,修复 + 补测试 + 灰度验证。像我修的"重复 ad id"、"legacy ad 文本资产获取"、"图片广告扩展 Bulk 不一致"这些,都是边界/特定数据触发的,靠日志和数据对比定位。关键是先增加可观测性,再基于证据推断,而不是猜。

### 61. 你的 commit 里有很多 "add log",是不是说明设计不足?

我理解这个质疑,但我认为恰恰相反,这体现了对大型分布式系统可观测性的重视。原因:一,广告系统规模巨大、异步链路长,很多问题只在生产真实流量下暴露,本地无法复现,日志是唯一的现场。二,灰度期间主动加日志——放量前先埋好观测点,这样一旦有问题能立即定位,是预防性而非补救。三,加日志本身是低风险高回报的手段——不改逻辑就能提升排障能力。当然我也注意不过度日志(会有性能和噪音成本),关键路径埋、降噪预期内的日志(我做过把 Deal 正常过期日志降级)。所以这不是设计不足,而是务实的运维意识——你没法在写代码时预见生产的所有边界。

### 62. 你们的 mock 测试怎么写?过度 mock 有风险吗?

我们中间层测试大量用 mock(比如 mock 掉 Xandr client、外部服务、DAO),配合 DI 注入。好处是单元测试快、隔离、不依赖外部。但过度 mock 确实有风险:一,测了 mock 而非真实行为——如果 mock 的假设和真实服务不符,测试全绿但线上挂(我修的很多"组合场景"bug 就是单测 mock 覆盖不到的)。二,重构脆弱——mock 绑死了实现细节,改实现就得改一堆 mock。缓解:关键路径配套功能测试/集成测试(真实调用),不只靠单测;mock 的契约要和真实服务对齐;端到端场景用 E2E 覆盖。我的实践是单测保逻辑分支 + 功能/集成测试保真实交互,两者结合。团队也在从 Rhino Mocks 这类老框架迁移。

### 63. 讲一次你定位并解决的最难的线上问题。

视频推荐灰度期的 Azure Queue 凭据 + 流量问题比较有代表性。现象是导出 AIGC 视频时大面积失败,灰度指标很差。定位过程:先看日志发现失败集中在调外部 API,错误既有凭据(cred)相关又有超时/限流相关。根因是两层:一,高并发直接打外部 API 触发对方限流;二,凭据在高并发下的获取/过期处理有问题。解决:引入 Azure Queue 削峰把并发降下来,同时修凭据获取逻辑加重试,再加批量降级和部分成功处理。修完重新从小流量灰度,稳定后放开。难点在于是多因叠加、只在真实流量并发下出现,本地根本复现不出来,全靠日志+遥测一层层剥。这也让我坚定了"高风险外部调用必须限流 + 可观测 + 灰度"的信条。

## 板块十三 · 广告业务领域知识

### 71. 简单讲讲一个广告投放系统里,Account / Campaign / AdGroup / Ad / Criterion 的层级关系?

这是广告系统的核心实体层级,自上而下:Account(账户)——广告主的顶层容器,管账单和权限。Campaign(广告系列)——一次营销活动,设预算、投放目标、整体设置。AdGroup(广告组)——Campaign 下的分组,通常对应一组相关的定向和出价。Ad(广告)——具体的创意(文本、图片、视频)。Criterion(定向条件)——挂在 Campaign 或 AdGroup 上的定向,比如地域、年龄、性别、受众、设备、关键词等。我做的很多工作就是围绕这套层级:比如 Deal 的定向约束是在 AdGroup / Campaign Criterion 层面加规则,IsDealCampaign 是 Campaign 层面的特性位。理解这个层级是做广告中间层的基础。

### 72. MSAN、DSP、PMax 这些术语分别是什么?

MSAN(Microsoft Audience Network)——微软的受众广告网络,是原生广告(native ad)的展示网络,我做的 Disclaimer、IAS、ISPOT 很多是 MSAN 场景。DSP(Demand-Side Platform)——需求方平台,广告主通过它程序化购买展示广告库存,和 Deal、Xandr 强相关。PMax(Performance Max)——全渠道自动化广告类型,系统自动跨渠道优化投放,我在 PPS、Image Fitting 里都处理过 PerformanceMax/PerformanceMaxApp 的特殊逻辑(比如跳过某些场景)。这些是微软广告的主要产品线,做中间层要清楚每种广告类型的特性和约束差异。

### 73. 什么是 Disclaimer 广告?你做了什么?

Disclaimer(免责声明)是某些行业(比如金融、医药)法规要求广告必须带的免责声明文本。在 MSAN 原生广告场景,我实现了 Disclaimer Ad Extension 的支持:让广告能挂免责声明扩展,并在 Bulk 上传和 WCF API 里支持增改。技术点包括:编辑状态(editorial status)校验——免责声明内容要过审核;更新规则——什么情况允许改;以及处理原生广告 disclaimer 的 campaign setting 更新。这是典型的合规驱动的功能,细节多、校验严,我配套写了不少 SOAP 和 Bulk 的测试。后来这个特性 GA 了,我还清理了 GA 前的临时测试。

### 74. Genre Targeting(类型定向)是什么?你处理过什么问题?

Genre Targeting 是按内容类型定向——比如视频广告可以定向投放在某类内容(体育、新闻、娱乐)旁边,常见于 Xandr 视频广告和 Deal 场景。我处理过几个问题:一,Genre 的 Bulk Delta 问题——批量编辑时 genre 的增量计算有 bug;二,Genre Performance Report 的时间范围翻译——报表里 genre 数据的时间跨度处理(改成 12 个月);三,在 Deal 自动管道里支持 genre 的映射。Genre 属于比较细分的定向维度,坑在于它和其他定向、和报表、和 Deal 的交叉场景。

### 75. 广告的编辑审核(Editorial)流程你了解吗?

了解一些。广告创意上线前要过编辑审核(editorial review)——检查内容是否合规(不违规、不误导、符合政策)。每个广告/资产有 editorial status(比如待审、通过、拒绝)。我在 Disclaimer 里处理过 editorial status 校验,也在 Legacy Ad 清理里做过大量 editorial status 回刷(retouch)、绕过审核流触发的工作。技术上,编辑状态的变更会触发下游流程(比如重新审核、更新创意),所以改它要很小心副作用。像"更新 headline 后要不要重新触发审核"、"迁移时怎么绕过 change history 记录"都是这块的典型问题。

### 76. 广告系统里为什么"数据一致性"特别难?

几个原因叠加:一,多入口——同一个实体能通过 SOAP、Bulk、OData、内部服务多个入口修改,任何一个入口漏了逻辑就不一致。二,多层缓存和副本——数据从 DB 到各级缓存到投放侧,更新有传播延迟。三,分库分表——跨片操作难保证事务。四,异步管道——同步、评分、监测都是最终一致,中间有窗口。五,第三方数据——Xandr 等外部源的数据要同步,天然滞后。六,海量并发——高并发下的竞态。所以做广告中间层,"想清楚这个改动在所有入口、所有副本、所有异步链路上是否一致"是核心功力。我用 BitMask 统一数据源、用幂等、用 change history、用对账,都是在对抗这种一致性复杂度。

## 板块十四 · 工程效率 / 工具 / 协作流程

### 77. 你们的代码规模巨大(几万个 .cs 文件),怎么保证构建和 CI 效率?

超大单体的构建是真实痛点。我们用了几种手段:一,CloudBuild / 分布式缓存构建——微软内部的分布式构建系统,能缓存和并行化,不用每次全量编译。二,增量构建——只重建受影响的部分。三,门禁分层——gated(合入前必过的核心测试)和更全的 CI(合入后/定时跑的完整测试)分开,不让所有测试都卡门禁。四,CI-only 隔离 flaky 测试,不拖慢门禁。五,PR 覆盖率工具——只关注 PR 改动部分的覆盖。作为开发,我能做的是控制改动的影响面、写快速的单测、合理分模块,避免动到全局依赖导致大范围重建。

### 78. 你们用什么源码管理和 PR 流程?

我们用 Azure DevOps(内部叫 VSTS / msasg 的 git)。流程是标准的 feature branch + Pull Request:从 master 切分支(命名如 users/qirenliu/xxx)、开发、提 PR、过门禁(gated build + 必需测试)、经 code review 批准、再 Merge(我的提交里大量 "Merged PR xxx" 就是这个)。热修复走 hotfix 分支和专门的部署列表(.lst)。我很熟悉这套流程:处理 review comments、跑 gated、解决冲突(经常 merge master)、处理 PR 里的 CI 失败。这套和 GitHub PR flow 理念一致,只是工具是 Azure DevOps。

### 79. 近期你们在引入 AI 辅助开发吗?你怎么看?

是的,我们仓库里已经有不少 AI agent 相关的基建——比如 agent 的 dev/pr/review 命令、skill 库、skill-miner 工具、AI 辅助的代码分析和文档生成流程。我的看法:AI 辅助能显著提升效率,尤其在大代码库里做代码理解、模板化的样板代码、写测试、生成文档、PR review 辅助这些场景。但要保持工程判断——AI 生成的代码必须经过 review、测试和对业务逻辑的把关,尤其我们这种一致性要求极高、影响面大的系统,不能盲信。我个人拥抱这个趋势,也愿意把 AI 工程化能力用在提升团队效率上,同时守住质量底线。

### 80. 面对一个你不熟悉的大代码库,你怎么快速上手?

我的方法:一,先建立地图——搞清整体架构分层(API/中间层/数据层)、主要模块边界、关键实体模型,而不是一头扎进细节。二,顺着一个真实特性走一遍——挑一个功能,从入口 API 一路追到数据层,理解完整调用链,这比孤立读代码有效得多。三,看测试——测试是最好的用法文档,告诉你模块怎么被调用、边界是什么。四,从小改动开始——先做 bug fix、加日志这种低风险任务,在实战中熟悉。五,善用文档和问人——我们仓库有 AGENTS.md、code patterns 文档,不懂就问同事。我自己从广告小白到能独立负责特性线,就是这么过来的——先框架后细节,以特性为线索,边做边学。

### 81. 你怎么保证自己的代码可维护、不给后人挖坑?

几个习惯:一,复用而非复制——把公共逻辑下沉共享层(比如多 API 入口复用同一套校验映射),避免多处不一致。二,配套测试——改逻辑必配测试,尤其边界和组合场景,给后人重构的安全网。三,关键路径埋日志和监控——让问题可观测。四,危险改动带开关——用动态配置隔离,可灰度可回滚。五,及时清理技术债——GA 后清理临时开关、下线旧代码(我做过 V1 Deal 下线)。六,清晰的命名和必要的注释——尤其像 BitMask 这种隐晦的设计要文档化。核心是假设后面会有人(包括我自己)来改这段代码,让他能安全地改。

## 板块十六 · 技术深挖补充(冲刺 100+)

### 87. Cosmos DB 和 SQL Server 你们都用,分别用在什么场景?为什么?

SQL Server(分库分表)用在核心 OLTP——账户、Campaign、AdGroup、Ad、Criterion 这些强关系、强一致、要事务的投放实体,关系模型和存储过程适合复杂业务逻辑。Cosmos DB用在需要弹性伸缩、schema 灵活、或事件驱动的场景——比如某些任务触发数据、需要 change feed 触发离线任务的地方(我在视频推荐用 Cosmos Trigger)。取舍逻辑:强关系强一致 → SQL Server;高伸缩、灵活 schema、全球分布、事件驱动 → Cosmos。两者互补,不是替代关系。用哪个取决于这块数据的一致性要求、访问模式和伸缩需求。

### 88. 你提到用 request 的 CustomerId 而不是共享变量,这背后是什么坑?

这是我在 PPS V2 里踩的一个真实坑。任务处理器在并发处理多个任务时,如果把某个上下文值(比如 CustomerId)存在处理器的共享字段/静态变量里,不同任务的并发执行就会互相覆盖——A 任务刚设了自己的 CustomerId,B 任务又改成它的,A 接着用就串了。修正是每个任务从自己的 request 里取 CustomerId,数据随请求走,处理器保持无状态。这就是前面说的"并发安全靠无状态设计而非加锁"的具体体现。这类共享可变状态导致的并发串数据 bug 很隐蔽,低并发测不出来,只在生产高并发暴露。

### 89. 你怎么理解"至少一次(at-least-once)"和"恰好一次(exactly-once)"投递?

分布式消息系统里,恰好一次极难实现(要端到端的分布式事务,代价高)。工程上主流是 at-least-once(至少一次)+ 消费端幂等 = 业务上的恰好一次效果。意思是:消息系统保证消息不丢(至少投一次),但可能重复投;消费端通过幂等设计(幂等键去重、状态机、upsert)保证重复消费不产生副作用,最终效果等价于恰好处理一次。我们的 Task Engine 就是这个模式——任务可能重试/重复,所以我做的处理器都强调幂等。反过来,如果追求真正的 exactly-once 投递,系统复杂度和性能代价通常不划算。

### 90. 动态配置(dynamic config)本身是怎么实现的?刷新有什么代价?

动态配置本质是一份可以在运行时热更新、不需重启就生效的配置,通常存在中心配置服务/存储里,应用定期拉取或推送刷新到本地缓存。代价在于刷新的频率和开销:刷太频繁会给配置服务和网络造成压力,刷太慢则配置变更生效有延迟。我实际处理过这个权衡——在 Impression Tracking 里用计数器控制刷新节奏(不是每次都刷,累计 N 次才刷一次),就是为了降低刷新开销又不牺牲太多时效。另外要注意配置读取要线程安全(热更新时有并发读),以及配置错误的爆炸半径——一个错配置可能瞬间影响全量,所以配置变更本身也要谨慎、可回滚。

### 91. 灰度用"百分比"和"白名单账户"两种方式,分别什么时候用?

白名单账户:精确控制哪些具体账户先体验,适合早期验证——用我们自己的测试账户或愿意尝鲜的特定客户,能精准观察、出问题影响面完全可控。百分比放量:按流量比例(1%→5%→…→100%)随机放开,适合验证规模化效果和统计指标——需要足够样本量看聚合指标(成功率、性能、业务指标)时用。典型顺序是:先白名单(定性验证功能对不对)→ 再百分比(定量验证规模化安全)→ GA。我做 Privacy Check 就是先白名单测试账户,再一档档百分比往上放。选择取决于你这一步是想验证"功能正确性"还是"规模化指标"。

### 92. 你做过 nuget package 的版本管理(pump up version),这里有什么坑?

我们不少共享逻辑(比如 Xandr client、deal 相关的包)是通过 NuGet 包在服务间共享的。版本管理的坑:一,版本升级要兼容——升级包版本时,依赖它的所有服务都可能受影响,要保证向后兼容或协调所有消费方。二,版本地狱(diamond dependency)——不同包依赖同一个包的不同版本,会冲突。三,发布时机——包发布和消费方升级要协调,不然消费方拿不到新版本或拿到不稳定版本。我做 Deal、视频广告时都处理过 pump up version 和 modify nuget package,原则是小步升级、保持兼容、协调好上下游。这本质是模块化系统的依赖管理问题。

### 93. 你怎么权衡"加日志"带来的性能和成本?

日志不是越多越好,要权衡。成本:大量日志有 CPU/IO 开销、存储成本、以及淹没关键信息的噪音。我的做法:一,分级——关键路径和异常用较高级别(Error/Warn),细节用 Debug/Verbose 且可开关。二,关键节点埋,不是每行都埋——外部调用边界、状态转换、异常分支这些高价值点。三,降噪——预期内的"正常异常"降级或不记(我做过把 Deal 每天正常过期的日志降级)。四,结构化日志——便于用 Kusto 查询和聚合,而不是纯文本。五,采样——高频路径可以采样记录而非全记。目标是用最小的开销获得最大的排障能力,而不是无脑刷屏。

### 94. 如果让你优化你们某个慢的存储过程,你的排查思路?

一,先测量定位——用执行计划(execution plan)和统计,找出真正慢的环节(全表扫描?缺索引?锁等待?)。二,看索引——是否走了合适的索引,WHERE/JOIN 的列有没有索引,是否有隐式类型转换导致索引失效。三,看数据量和访问模式——是不是逐行处理(cursor)应该改成集合操作,是不是可以分批。四,看锁和阻塞——是不是锁竞争导致的慢,能否降低隔离级别或缩小事务范围。五,看参数嗅探(parameter sniffing)——SQL Server 常见坑,缓存的执行计划不适合当前参数。六,分片层面——是不是跨片查询,能否局限到单片。优化后用 UT 和真实数据量验证。核心是先用数据定位瓶颈,再对症下药,避免凭感觉改。

### 95. 你们系统里"批量(batch)"处理无处不在,批量大小怎么定?

批量大小是个典型的权衡:太小——任务/调用次数多,调度和网络开销大,吞吐低;太大——单次内存占用高、单次失败影响面大、超时风险高、对下游冲击大。定批量的考量:一,下游承受能力——第三方 API/DB 一次能吃多少不出问题。二,超时窗口——单批要能在超时内完成。三,失败重试成本——批太大,失败重试浪费大,所以要配合部分成功处理。四,可调——我做视频推荐时就支持动态降级批量大小,压力大就调小。实践上先取一个保守值,再根据监控(延迟、成功率、下游压力)调优,并且做成配置可随时改,而不是硬编码。

### 96. Kusto 在你排障中怎么用?举个例子。

Kusto 是我们的遥测/日志查询主力工具(类似大数据的 SQL)。排障时我用它:一,按账户/时间/错误码切片——比如"查最近 1 小时某账户视频推荐任务的所有失败日志",快速定位问题范围。二,聚合看趋势——统计成功率、延迟分布、错误类型占比,判断是普遍问题还是个例。三,关联调用链——顺着一个请求 ID 追整条链路。比如视频推荐那个 P0,我就是用 Kusto 发现失败集中在特定的外部调用和凭据错误上,才定位到限流和 cred 两层根因。Kusto 是大规模分布式系统里把海量日志变成可查询证据的关键,排障"用证据不靠猜"就靠它。

### 97. 你做过 KPI / 指标相关的东西吗?怎么理解监测广告系统健康度?

是的,我们仓库有 KPI 服务和大量监控看板(ClickHouse dashboard、FDP 告警)。理解广告系统健康度我会分层看:一,系统层——服务可用性、延迟、错误率、任务队列积压、DB 压力。二,业务层——广告投放成功率、Deal 同步及时性、评分/推荐的产出量和质量、监测触发率。三,数据质量层——一致性、滞后度(比如 Deal sync time)。设计指标要抓能真实反映用户受影响程度的信号,而不只是技术指标。告警要分级、可行动、低噪音。我做过给 Deal、Impression、PPS/Ad Strength 配监控告警,核心是让系统在用户感知到之前,我们先知道。

### 98. 你怎么看后端工程师的"业务理解"重要性?

我认为对广告这种业务逻辑极其复杂的领域,业务理解和技术能力同等重要。原因:一,很多 bug 的根源是业务规则理解偏差,不是代码写错——比如 Deal 的定向约束、免责声明的合规规则、编辑审核的触发条件,不懂业务根本写不对。二,好的技术决策要基于业务——什么能最终一致、什么必须强一致,取决于业务容忍度。三,能和产品有效对话,提前发现需求里的坑。我这三年半很大的成长就是从只懂代码到懂广告业务——理解账户层级、各广告类型差异、程序化交易、第三方测量的商业含义。我觉得资深后端的分水岭之一,就是能不能把技术方案和业务价值对齐。

### 99. 给应届生/初级工程师一条你最想给的建议?

如果只给一条:建立"生产意识"——写代码时就想着它在真实大流量下会怎么挂。具体就是:高风险改动带开关、先加日志和监控、破坏性操作先做成可逆的、新特性灰度放量而不是一把梭、改逻辑必配测试。初级工程师容易只关注"功能实现了没有",而资深工程师关注"上线安全吗、出问题能多快止血、后人能安全地改吗"。这套意识不是天生的,是被生产事故教出来的——我自己就是在广告系统里踩了 P0、修了无数线上 bug 才养成的。早一点建立这个意识,能少踩很多坑,成长得更快。

### 100. 你在数据层和中间层都能干,这种"全链路后端"能力是怎么练出来的?对你有什么帮助?

是在做完整特性线中自然长出来的。一个特性(比如 PPS、Deal、Orphan Image)要落地,天然横跨中间层(API、业务逻辑、任务处理器)和数据层(存储过程、schema、部署清单),我为了把一件事真正做完,就得两头都碰,久而久之两层都熟了。好处很实在:一,定位问题快——一个 bug 到底在中间层逻辑还是存储过程,我能一路追下去不用来回甩锅。二,设计更合理——知道数据层的约束(分片、锁、性能),中间层设计就不会拍脑袋。三,独立交付——不用等别人配合就能推动一整条线。这种全链路视角是我很看重的竞争力。

### 101. 你们代码里有 xsd/wsdl/cscfg/props 这么多配置和契约文件,怎么管理不出错?

大型 .NET 系统确实有一堆契约和配置文件:XSD/WSDL(API 契约)、cscfg/csdef(Azure 服务配置)、props/csproj(构建)、Dynamic.config(动态配置)、.lst(部署清单)。管理不出错靠几点:一,改契约走加法、保持向后兼容(前面 XSD 那题讲过)。二,配置改动也要 review 和灰度——配置错误的爆炸半径不比代码小。三,部署清单(.lst)是强制步骤——数据层对象必须注册进清单才会部署,漏了代码合了也不生效,这是我做数据层改动的必查项。四,靠流水线统一发布而不是手工。核心是把这些"看着不起眼但一错就出大事"的文件,纳入和代码同等的 review + 测试 + 灰度纪律。

### 102. 回顾这三年半,如果重来一次,你会做得不一样的地方是什么?

诚实说几点:一,更早重视测试的稳定性——我早期写了一些 flaky 测试,后来花了不少力气治理,如果一开始就把测试的确定性(不依赖时序、不依赖共享数据)做好,能省很多返工。二,更早清理技术债——GA 后的临时开关、旧代码,当时容易拖着,后来发现债越滚越大,现在我习惯 GA 后就安排下线(像 V1 Deal)。三,设计前多和上下游对齐接口——有几个组合场景的 bug,根源是特性开发时没充分考虑和其他特性的交互。四,更系统地沉淀文档。这些反思其实都指向同一个方向:从"把功能做出来"进阶到"把系统长期健康地维护好"——这正是我这几年成长的主线。

### 104. 你只用过 C#/.NET,我们是 Java/Spring 技术栈,你能胜任吗?

能,我很有信心,理由有三:一,C# 和 Java 是"表亲"——两者都是静态类型、面向对象、带 GC、跑在虚拟机(CLR/JVM)上的语言,语法、OOP 思想、泛型、异常处理、并发模型高度相似。会 C# 的人学 Java 通常一两周就能上手写生产代码,不存在范式鸿沟(不像从 C# 转 Haskell 那种)。二,框架思想一致——.NET Core 的依赖注入、中间件、配置系统,和 Spring 的 IoC、AOP、Bean 管理几乎一一对应;我天天用 DI,换成 Spring 的 @Autowired 只是语法差异。三,难的从来不是语言——真正难的是分布式系统设计、数据一致性、大流量治理、业务复杂度,这些我已经在广告系统里趟过了。语言是最容易补的一环。我可以坦诚说:入职前我会主动把 Spring Boot 全家桶(Spring MVC、MyBatis、Spring Cloud)过一遍,不会让语言成为障碍。

### 105. 你用的 WCF / OData 我们不用,我们是 gRPC / Spring REST,差别大吗?

概念上几乎没差别,只是具体框架不同。WCF 本质就是 RPC 框架——服务间用强类型契约(接口 + 数据模型)互相调用,这和 gRPC / Dubbo 解决的是同一件事:定义 service 接口、序列化传输、客户端像调本地方法一样调远程。WCF 用 WSDL/XSD 定义契约,gRPC 用 Protobuf,都是"契约优先(contract-first)"的思路,连"改契约要向后兼容"这些坑都一模一样(我前面讲的 XSD 只能加字段不能删,gRPC 的 Protobuf 字段号规则完全同理)。OData 就是带标准查询语义的 REST——和 Spring MVC 写的 RESTful API 是一回事,OData 的 $filter/$select 相当于把查询参数标准化了。所以我对 RPC 契约设计、多协议对外暴露、序列化兼容性的理解是直接可迁移的,换到 gRPC + Spring REST 只是学新工具的 API。

### 106. 你说的"Task Engine"是什么?我们没有这个东西。

"Task Engine"是我们内部自研的分布式异步任务框架的名字,不是通用术语,所以你没听过很正常。它解决的问题,在国内的标准做法是 消息队列 + 分布式任务调度 的组合:要"异步解耦、削峰、重试"——对应 Kafka / RocketMQ 的消费者模型;要"定时触发、任务分片、失败重试、调度管理"——对应 XXL-Job / Elastic-Job 这类分布式任务调度平台;如果要复杂的有状态工作流、checkpoint,对应的是 Temporal / Cadence。我在 Task Engine 上做的事——新增任务类型、写处理器、配置限流(dequeue limit)、优先级队列、幂等、回填(backfill)、checkpoint——换成"写一个 RocketMQ 消费者 + 用 XXL-Job 调度"是完全一样的工作。我理解的是任务调度的本质问题(可靠投递、幂等、限流、优先级、死信),这些在任何 MQ/调度框架上都通用。

### 107. Azure Queue 和 Kafka / RocketMQ 有什么区别?你会用 Kafka 吗?

先说会不会用:会,而且很快能上手,因为消息队列的核心概念是相通的。区别层面:Azure Queue 是一个比较"简单"的队列——提供基本的入队/出队、可见性超时(visibility timeout,类似消费确认)、at-least-once 投递,适合我做的削峰限流场景。Kafka / RocketMQ 更重、更强——Kafka 是高吞吐的分区日志(partitioned log),支持消费者组、分区顺序、消息回溯(offset)、超高吞吐,更适合大数据流和事件溯源;RocketMQ 在此基础上强化了事务消息、顺序消息、延迟消息,国内电商用得多。我用 Azure Queue 时理解的核心概念——生产消费解耦、at-least-once + 幂等消费、削峰、死信——在 Kafka/RocketMQ 上完全适用,我只需要额外学分区、消费者组、offset 管理这些 Kafka 特有的东西,几天就能补上。我甚至可以聊聊为什么当时选简单队列而不是 Kafka——因为削峰场景不需要 Kafka 的重型能力,选型要匹配问题规模。

### 108. Cosmos DB 是什么?和 MongoDB / MySQL 比呢?你说的 change feed / trigger 呢?

Cosmos DB 是微软的分布式多模型 NoSQL 数据库,最接近的国内/开源对应是 MongoDB(文档型、schema 灵活、水平伸缩)。它的特点是全球分布、弹性伸缩、多种一致性级别可选。我用它主要是两点:一,存灵活 schema、需要弹性伸缩的数据;二,用 change feed(变更流)做事件驱动——数据一有变更就产生一个事件流,我可以订阅它触发下游任务。这个 change feed 机制,国内最经典的对应就是 Canal 订阅 MySQL Binlog:MySQL 数据变更 → Canal 捕获 Binlog → 投到 Kafka → 消费者处理。MongoDB 自己也有 Change Streams,概念一模一样。所以我理解的"事件驱动、数据变更触发下游、CDC(变更数据捕获)"这套模式是通用的。至于选型——强关系强事务用 MySQL/SQL Server,灵活 schema 高伸缩用 MongoDB/Cosmos,这个判断我在前面 OLTP 那题也讲过,是通用的数据库选型能力。

### 109. 你们用 SQL Server 分库分表,和国内 MySQL + ShardingSphere 有区别吗?

分库分表的原理和难点是完全一样的,只是数据库产品和中间件不同。核心问题都是:数据量太大单库扛不住,要按分片键水平拆分,让同一逻辑单元落同一片、避免跨片查询和跨片事务。我在 SQL Server 上处理的所有难题——选分片键、避免跨片操作、分片环境下的 schema 变更要每片执行、跨片一致性、单元测试要覆盖分片场景——在 MySQL + ShardingSphere / MyCat 上是同样的挑战、同样的解法。国内还有一个趋势是用 TiDB 这种"分布式 NewSQL"来免去手动分片,但底层的分片思想你还是得懂,否则用不好。所以我对水平拆分、分片键设计、跨片一致性的理解直接可迁移。唯一要补的是 MySQL 的具体特性(存储引擎 InnoDB、索引细节、和 SQL Server 的语法差异),这是纯熟练度问题。

### 110. 你说的 "Dynamic Config 灰度",国内是怎么做的?你熟悉 Apollo / Nacos 吗?

这正好是我最强的能力之一,而且国内有非常成熟的对应——配置中心 Apollo / Nacos。我用的 Dynamic Config,本质就是一个配置中心 + 特性开关(Feature Flag):配置存在中心、运行时热更新不重启、控制功能开关和灰度比例。这和 Apollo / Nacos 做的是同一件事:配置热更新、灰度发布、按比例/按白名单放量、秒级回滚。我在微软做的"代码带开关上线(dark launch)→ SI 验证 → 1%/5%/15% 百分比放量 → GA → 清理开关"这套灰度方法论,是业界通用的渐进式交付(progressive delivery),换成 Apollo 管理开关、用它的灰度能力,方法论一模一样。虽然我没直接用过 Apollo 的界面,但我对"配置中心 + 灰度发布"的理解是深度的、方法论级的,工具只是承载。这块我不但能无缝迁移,还能把欧美严格的灰度纪律带过去。

### 111. 你担心你的技术栈在国内"不通用"吗?怎么说服我你能快速融入?

我不担心,原因是我很清楚"工具"和"能力"的区别。工具(WCF、Cosmos、Task Engine)是会变的,但我沉淀下来的是可迁移的工程能力:一,分布式异步系统设计——MQ、任务调度、幂等、限流,换个 MQ 就行;二,数据一致性治理——多入口一致、最终一致、CDC、对账,和用什么库无关;三,大流量安全上线——灰度、开关、监控、快速止血,是方法论;四,复杂业务建模和第三方集成——这是最难也最值钱的,和技术栈无关。说服你的最好方式是:面试里我把每个微软概念都能主动翻译成你们的栈来讲(就像这一整节做的),这本身就证明我理解的是本质而非表象。另外我会用行动表态——入职前主动补齐 Java/Spring + Kafka + MySQL 分库这套主流栈,把语言和工具的差距在最短时间内抹平。真正难的分布式和业务能力我已经具备,补工具是最快的部分。

### 112. 如果面试官对某个微软名词一脸茫然,你现场怎么处理?(话术技巧)

这是很实际的沟通问题,我的处理套路是"三步翻译法":第一步,不纠缠产品名,立刻抽象成通用问题——比如别人问懵了,我会说"Task Engine 您可以理解成我们内部的分布式任务调度框架,解决的就是异步任务的可靠执行"。第二步,主动给出国内对应物——"它相当于你们用 RocketMQ 消费者加 XXL-Job 做的那套"。第三步,回到我做的事和能力——"我在上面做了限流、幂等、优先级队列这些,这些经验换到你们的栈是直接可用的"。核心原则:永远不要让面试官卡在一个陌生名词上,而是主动把话题从"我用过什么产品"引导到"我具备什么能力"。我会把每个陌生名词都当成一个展示"我理解本质、我能迁移"的机会,而不是障碍。这种主动翻译的沟通能力,本身也是加分项。
