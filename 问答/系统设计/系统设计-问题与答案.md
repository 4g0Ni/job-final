# 系统设计 / 工程化问题与答案

> 面试结构：先澄清规模与 SLO → API/数据模型 → 主链路 → 扩展性/一致性 → 失败与安全 → 指标与成本。

### 1. 设计一个广告素材 AIGC 生成与审核系统。
入口接收账户、素材和生成参数，先做配额/权限/幂等校验，再写任务表与队列；Worker 调模型，候选结果逐个写对象存储并通过 SSE 推送；审核服务做安全、版权、格式和业务规则过滤；用户选择后持久化资产并记录 lineage。必须支持取消、重试、部分成功、模型/Prompt 版本、成本预算和审计。用户的图片重塑 partial render、Azure Queue 限流和遥测经验可直接映射。

### 2. SSE、WebSocket、长轮询如何选？
服务端单向持续输出优先 SSE：HTTP 友好、自动重连、实现简单；需要客户端和服务端高频双向通信选 WebSocket；兼容性或基础设施受限才考虑长轮询。AI token/候选图片流通常 SSE 足够，但仍需事件 id、断线续传、心跳和背压。

### 3. 如何设计高并发第三方 API 集成？
以适配器层隔离各厂商契约；令牌按 tenant 缓存并提前刷新；客户端设置连接池、timeout、有限重试、熔断和 rate limiter；写请求带幂等键；大任务经队列削峰；响应落审计与 dead-letter。分页、GZip、100 并发压测和 Xandr 集成是可讲实例。

### 4. 固定窗口、滑动窗口、令牌桶、漏桶怎么选？
固定窗口简单但边界可突发；滑动窗口更精确但状态成本高；令牌桶允许受控突发，适合 API；漏桶平滑输出，适合保护固定吞吐下游。分布式实现需原子更新，常用 Redis Lua 或存储过程，并按用户/租户/模型分别设额度。

### 5. 如何设计幂等的异步任务？
定义业务幂等键；创建任务时唯一约束或 compare-and-set；状态机只允许合法转换；副作用写入 outbox 并带幂等 key；重试不重复扣费/生成；结果可查询。数据管道可用 staging+merge，API 可用 Idempotency-Key，队列消费需 at-least-once 下的去重。

### 6. 如何处理“消息已消费但结果未写入”或反过来的双写问题？
使用事务 outbox/inbox：业务状态与待发布事件同事务提交，后台可靠投递；消费者用消息 id 去重。若基础设施支持可用事务消息，但不要轻易宣称端到端 exactly-once；实际通常是 at-least-once + 幂等副作用。

### 7. 设计一个 TB 级广告指标平台。
数据分层为 raw/staging/curated/serving；按事件时间与业务键分区；ADF/Airflow 编排批作业；SCOPE/Spark 做早过滤、列裁剪、预聚合和去倾斜；指标定义版本化；staging+merge 支持审计和回填；数据质量 gate 检查时效、行数、唯一性和分布漂移；下游提供实验、BI 和模型特征。

### 8. 数据回填如何不影响在线正常任务？
明确日期/租户范围，先 dry-run 估算数据量；回填使用独立队列/计算池或低优先级；输出写临时分区，经校验后原子替换；任务幂等且可暂停；监控资源、延迟和下游读一致性。完成后核对分区、总量和关键指标。

### 9. 如何设计 A/B 实验指标服务？
实验分流与曝光口径先固定；按正确 analysis unit 去重；同时产出分子、分母、effect size、置信区间和 p-value；处理多重比较、样本量与提前停止；指标定义和代码版本化；检查 SRM、缺失和污染；结论同时看统计显著与业务显著。

### 10. 设计一个代码库 RAG 服务。
Repo webhook 触发增量解析；tree-sitter 按符号分块并保存路径、commit、语言和调用关系；关键词+向量+图检索融合；权限在召回阶段过滤；答案强制引用文件与版本；索引使用版本快照原子切换。评测分函数题/架构题，计算 Recall@K、MRR、faithfulness 与 P95。

### 11. 向量库如何选？
先看数据规模、维度、更新频率、过滤选择性、多租户、备份、延迟和运维。小型离线工具可用 SQLite FTS5 + sqlite-vec，把原始 JSON 当 source of truth、索引当可重建派生物；窄 metadata 条件要先过滤再算相似度。需要数十万以上高维向量、ANN、分片和高可用时，再评 HNSW/IVF 引擎或托管向量服务。迁移阈值以真实数据的 Recall@K、P95、内存和构建时间 benchmark 为准，而不是框架热度。

### 12. 如何设计多租户 AI 服务的数据隔离？
身份映射到 tenant；存储主键、索引、缓存 key、日志都带 tenant；检索在存储层做 ACL filter；密钥按 tenant 隔离；配额和成本按 tenant 计量；管理接口与运行接口分权；删除请求能级联清理索引、缓存、对象与 trace。

### 13. 如何做缓存？最难的是什么？
先明确缓存对象和一致性要求。参考数据可长 TTL；用户编辑数据需 write-through/失效；LLM 输出缓存 key 要含模型、prompt、参数和知识版本；in-flight promise cache 可去重并发请求。难点不是“加 Redis”，而是 key 稳定、失效、雪崩/击穿、权限污染和可观测性。

### 14. 如何治理前端首屏/向导性能？
先定义用户时刻和 P75/P95；用 RUM、Performance API、React Profiler 分解网络、后端、脚本、渲染；把不可见面板懒渲染，稳定 props、拆 state，预取高概率数据，拆分可缓存请求，移除非关键调用；用 feature flag 灰度并对比生产指标。用户已有 10s→2.8s 等真实案例。

### 15. 如何设计可观测性？
日志回答“发生了什么”，指标回答“是否异常”，trace 回答“慢/错在哪一跳”。统一 correlation id；RED（rate/errors/duration）与 USE 指标；关键业务成功率、队列积压、模型 token/费用、检索命中、缓存命中；设置 SLO 和 burn-rate 告警，避免仅按单个错误数报警。

### 16. 如何安全灰度到 100%？
开关支持租户/地区/百分比和 kill switch；先内部/SI，再 1%→5%→15% 等逐级；每档定义观察窗口与成功/回滚阈值；影子流量只比对不生效；数据库变更遵循 expand-migrate-contract；回滚路径在上线前演练。

### 17. 分库分表后如何查询和扩容？
选择稳定且分布均匀的 shard key；路由层根据 key 定位；跨 shard 查询尽量异步聚合并限制范围；全局唯一 id 避免冲突；扩容使用虚拟分片/一致性哈希或双写迁移。重点说明热点、事务和二级索引代价。

### 18. 如何设计权限、安全与审计完备的 Coding Agent？
工作区沙箱、最小文件路径和命令 allowlist；读写/执行/联网分能力授权；危险命令和外发需人工审批；密钥隔离；所有 patch、命令、返回码与审批有审计；执行后跑测试/静态检查；失败可回滚。网页与仓库文本一律当不可信输入，防 prompt injection。

### 19. 什么时候使用最终一致性？
当跨服务强事务成本过高且业务允许短暂不同步时，如搜索索引、推荐特征、邮件通知。必须定义可接受延迟、补偿、去重、读己之写和对账；资金、权限等强约束路径通常不能只靠最终一致。

### 20. 容量规划怎么做？
从峰值 QPS、对象/事件大小、保留期、读写比和增长率估算存储、带宽、CPU/内存；再乘复制、索引和安全余量。对 AI 服务还要估 token/s、并发、模型限额和单任务 fan-out。用压测验证 P95/P99，并找饱和点，不只看平均值。

### 21. 如何设计 CI/CD 质量门？
快速单测/静态检查先跑，集成与 E2E 分层；契约测试保护跨团队 API；数据/Agent 项目增加 golden eval 回归；构建产物不可变并签名；逐环境 promote；发布后自动验证 SLO，失败回滚。避免把不稳定 E2E 当唯一 gate。

### 22. 如何做灾难恢复？
先定 RPO/RTO；数据库备份+时间点恢复，对象版本，索引可由 source of truth 重建；跨区副本和配置/密钥恢复流程；定期做 restore drill。没有演练过的备份不算恢复能力。

### 23. 如果 Commit RAG 扩展到大公司、多 Repo、海量数据，如何结合 Azure 技术栈演进？
先澄清规模、写入速率、查询 QPS、数据驻留、权限边界和 freshness SLO。正常链路由 GitHub Enterprise/Azure DevOps 事件进入 Event Hubs，Azure Functions 或 AKS Worker 异步完成 Diff 解析、摘要和 Azure OpenAI embedding，失败任务进入 Service Bus dead-letter；原始 Commit/Diff 存 ADLS Gen2，处理状态与版本元数据存 Cosmos DB 或 Azure SQL。检索层用 Azure AI Search 在同一请求中执行 BM25 与 HNSW 向量召回并用原生 RRF 融合，候选集再交给 Semantic Ranker/独立 reranker；Microsoft Entra ID 映射出的 tenant/ACL、repo、时间和分支必须在召回阶段 pre-filter，服务间使用 Managed Identity。

扩展时不为每个 Repo 建独立索引，而按 tenant、业务域、区域和访问模式路由，避免索引爆炸；用 partition 扩展存储/索引吞吐、replica 扩展查询吞吐与可用性。超长历史建立 Repo—Release—PR—Commit 分层摘要，宽泛问题先检索上层再下钻，精确标识符问题直接进入 Commit 层。索引通过事件增量 upsert；模型或 schema 升级采用 v1/v2 双索引、历史批量回填、新数据双写、评测后灰度切换。

Agent 控制面可以保留 Incident Commander → Retrieval / Diff Investigator / Evidence Critic 的职责分离，但 request-local 状态要迁移到可持久化 store。Harness 在服务端强制执行 tenant-aware Candidate Ledger、工具白名单、Agent/Tool/Diff/时间预算、超时、幂等、取消传播和审计；Supervisor 不能直接绕过 Specialist 访问底层索引或 Diff。workflow 与 multi-agent 通过 feature flag 做 paired/shadow rollout，按任务成功率、路由正确率、P95、每成功任务成本和错误回答率决定是否放量。监控还包括索引 freshness、队列积压、embedding token/day 和单查询 fan-out。这里要明确：本地 Demo 已验证真实 multi-agent RCA vertical slice，以上 Azure 多租户与高可用设计仍是演进方案，不能表述成已经上线的事实。
