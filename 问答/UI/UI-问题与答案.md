## B. React 与前端基础

### 13. ⭐ React 里为什么会出现"重渲染风暴（re-render storm）"？你怎么定位？
**参考回答**：本质是**不稳定的 props/state 引用**导致大量子组件跟着父组件反复渲染。常见诱因：父组件每次渲染都新建对象/数组/内联函数当 props、context value 每次变、state 更新级联。定位手段：React DevTools Profiler 看哪些组件渲染次数异常、"why did this render"；或者加渲染计数日志。我在 Native 广告创建步就遇到过：表单状态一变，文案、图片、校验、预览、推荐组件全跟着重渲染，初始化时延被拉高。

### 14. 那你具体怎么治理重渲染？
**参考回答**：几个层次：① 用 `React.memo` 包裹纯展示子组件，配合稳定的 props；② 用 `useMemo`/`useCallback` 稳定对象和回调引用；③ 拆分 state，避免一个大 state 变化牵动全局；④ 稳定共享组件的数据更新逻辑，避免每次生成新引用；⑤ 把"表单局部状态"隔离，不让它级联到不相关组件。关键是先用 Profiler 找到真正热点，而不是到处乱加 memo（memo 本身也有成本）。

### 15. `useMemo` 和 `useCallback` 的区别？什么时候不该用？
**参考回答**：`useMemo` 缓存一个计算结果值，`useCallback` 缓存一个函数引用（其实是 `useMemo(() => fn, deps)` 的语法糖）。不该滥用：如果计算很便宜、或者下游没有 memo 化去消费这个稳定引用，那加 memo 反而增加内存和比较成本。原则是——**它要么保护一个昂贵计算，要么为 memo 化的子组件提供稳定引用**，否则不加。

### 16. React 的 reconciliation（协调）机制你怎么理解？
**参考回答**：React 用虚拟 DOM diff 来决定最小 DOM 更新。它按组件类型和 key 做同层比较：类型变了就整棵重建，key 帮助列表项复用。理解这个的实际意义是：① 列表要用稳定 key，别用 index；② 避免组件类型在渲染间"跳变"（比如条件渲染成不同组件导致卸载重挂）；③ 大组件树的初始渲染成本本身就高，所以懒渲染很关键。

### 17. ⭐ 什么是懒渲染（lazy render）？和 `React.lazy` / 代码分割是一回事吗？
**参考回答**：不完全是。`React.lazy` + `Suspense` 是**代码分割**——按需加载 JS 包。我说的懒渲染更偏**渲染时机控制**：即使代码已加载，也不在初始就把不可见的面板挂载进 React 树，等用户真正需要（展开/切到该步）再渲染。两者可以配合。我在向导页做的是后者——很多隐藏的高级设置面板、遗留 Backbone 受众列表，用户当下看不到，就不该进初始渲染成本。

### 18. 受控组件 vs 非受控组件？表单里怎么选？
**参考回答**：受控组件的值由 React state 驱动，非受控由 DOM 自身维护（ref 读取）。复杂广告表单大多用受控，因为要做实时校验、联动、预览。但受控的代价是每次输入都触发渲染，所以对大表单我会把频繁变化的字段做局部状态隔离、必要时 debounce，避免每个按键都级联重渲染。

### 19. React 里怎么管理复杂的跨组件状态？你们用 Redux 吗？
**参考回答**：用。大型广告向导有大量跨步骤共享的状态（campaign/adgroup/ad 模型、定向、素材），用 Redux/store 管理；局部 UI 状态用 Hooks。原则是**能局部就局部**，只有真正跨组件/跨步骤共享的才进全局 store，避免全局 state 变化引发大范围渲染。数据层（OData/REST）我们有独立的 repository/hook 封装。

### 20. useEffect 的依赖数组你踩过什么坑？
**参考回答**：最常见是**依赖不稳定导致 effect 反复触发**（对象/函数每次新建）、或**漏依赖导致闭包读到旧值**。性能场景里，我遇到过 effect 里发数据请求、但依赖是每次新建的对象，结果重复发请求拉高时延——解法是稳定依赖引用或改用 ref。还有清理函数要写好，避免订阅泄漏。

### 21. 你怎么在 Class 组件和 Hooks 之间共存/迁移？
**参考回答**：我们库里两者共存。旧的 Class 组件用 HOC（比如 `withI18nConsumer`、`withValidation`）注入能力；新代码用 Hooks + Context。迁移时我会保持导出符号不变（比如把类改名、再导出同名的 HOC 包裹版本），避免影响所有引用方。不为迁移而迁移，优先在改动该文件时顺手现代化。

### 22. TypeScript 给你带来的实际价值？
**参考回答**：在广告这种强契约系统里，TS 最大价值是**把后端模型和 API 契约类型化**，编译期就能挡住字段拼错、可选字段没判空、枚举用错。重构大型模块时类型是安全网。我也用它约束组件 props，减少集成 bug。

### 23. `any` 和 `unknown` 的区别？你怎么控制 any 蔓延？
**参考回答**：`any` 关闭类型检查、会传染；`unknown` 是类型安全的顶层类型，用前必须收窄。遗留代码里常有 any，我的做法是改到哪清到哪，边界（API 响应）优先加类型，用 `unknown` + 类型守卫替代 any。

### 24. 前端怎么做数据校验？你们的校验框架？
**参考回答**：我们有基于 schema 的校验框架（`ValidationGroup`/`withValidation`/`FormItem`）。广告表单校验很重：字段级、跨字段、还有服务端错误回填。我做第三方监测时写过不少校验——比如品牌 ID 长度超限的前端报错、追踪参数格式的正则校验。原则是**能前端拦的尽量前端拦**，给用户即时反馈，减少提交失败。

### 25. 浏览器渲染关键路径（Critical Rendering Path）你了解吗？
**参考回答**：了解。HTML→DOM、CSS→CSSOM、合成 Render Tree、Layout、Paint、Composite。JS 执行会阻塞。对我们向导页，瓶颈主要在**大量 JS 执行（组件初始化、reconciliation）+ 数据请求等待**，而不是纯 CSS layout，所以我的优化重点是减少初始渲染的组件量和把请求移出关键路径。

### 26. 首屏性能你会看哪些指标？
**参考回答**：业务上我们主要盯**页面/步骤级的 P75/P95 时延**（自定义 perf marker，从进入步骤到可交互）。通用指标层面熟悉 LCP、TTI、TBT。因为是登录后的重交互应用，不是营销落地页，所以我们更看"步骤 ready" 这类自定义标记，而不是纯 LCP。

### 27. 什么是防抖（debounce）和节流（throttle）？各自场景？
**参考回答**：防抖是"停止触发后再执行"，适合搜索输入、校验；节流是"固定频率执行"，适合滚动、resize。表单实时校验、受众搜索我会用 debounce 减少请求和渲染。

### 28. 事件委托（event delegation）？
**参考回答**：把子元素事件绑到父元素，利用冒泡统一处理，减少监听器数量。大列表/表格用得多。React 本身在根节点做了合成事件委托。

### 29. 你怎么处理前端的异步竞态（race condition）？
**参考回答**：典型场景是快速切换/连续请求，后发的先回导致状态错乱。手段：请求带序号/时间戳，只接受最新的；用 AbortController 取消过期请求；或用带缓存的 promise（我们数据层做过 promise caching，相同请求复用同一个 in-flight promise，既防重复请求也防竞态）。

### 30. Promise caching 是什么？你为什么用它？
**参考回答**：把"正在进行中的请求 promise"缓存起来，相同 key 的并发请求复用同一个 promise，不重复打后端；完成后可继续缓存结果供后续复用。我在性能优化里靠它避免向导初始化时重复拉同样的受众/行业数据，既减请求又天然防竞态。

## C. Fluent UI 与组件设计

### 31. 你们为什么用 Fluent UI？v9 和 v2 有什么区别？
**参考回答**：Fluent 是微软的设计系统，用它能和整个微软产品视觉/交互一致，还内建了不少 A11y。v9（`@fluentui/react-components`）是新一代，基于 design tokens、Griffel 原子化 CSS-in-JS、slots 组合模式，性能和主题化更好；v2（v8，`@fluentui/react`）是老一代。我们新代码优先 v9，老页面还在用 v2，所以经常要处理两代共存。

### 32. Griffel（makeStyles）和传统 CSS-in-JS 有什么不同？
**参考回答**：Griffel 是原子化的、构建期可提取的 CSS-in-JS，生成原子类名、去重、支持 RTL 自动翻转，运行时开销比很多传统 runtime CSS-in-JS 低。对大型应用性能友好。

### 33. 你怎么决定"造一个新组件"还是"复用/扩展现有的"？
**参考回答**：先查团队的共享组件库（AdsUI Kit / fluent-component 包）和 Fluent 原生组件，有就复用；只有当交互确实特殊、且会被多处使用时才抽新组件。一次性的东西不过度抽象。我做 Deal、监测这些功能时大量复用已有的表单、抽屉、popover 组件，只在业务差异处定制。

### 34. Popover / Dialog / Drawer 这类浮层组件，前端要注意什么？
**参考回答**：焦点管理是重点——打开要 trap focus（键盘不能跑到浮层外）、关闭要把焦点还给触发元素（MAS 2.4.3）。我专门修过这类 A11y bug。另外要注意浮层的定位、滚动、以及在浮层里做异步/分页时的状态管理（我遇到过 popup 分页 disclaimer 的问题）。

### 35. 组件的可复用性和可定制性怎么平衡？
**参考回答**：用组合（composition）而不是配置爆炸。Fluent v9 的 slots 模式就是好例子——把子部件作为 slot 暴露，让调用方替换，而不是给一堆布尔 props。props 太多说明该拆或该用 children/slots。

### 36. 你怎么保证组件在设计上符合 Figma 稿？
**参考回答**：我们有 Figma→代码的流程，提取 design token（颜色/间距/字号）对齐 Fluent token，下载切图资源。我会用运行中的 demo 逐像素对照，特别是响应式和暗色主题。

### 37. 大表格/网格（grid）性能你怎么优化？
**参考回答**：广告的 ads grid、asset group grid 数据量大。手段：虚拟滚动只渲染可视行、列按需渲染、单元格 renderer 记忆化、避免每行新建函数、分页/懒加载。我们有专门的 grid 组件体系（grid-core/addons）。

### 38. shimmer / skeleton 骨架屏为什么重要？你在哪用过？
**参考回答**：异步加载时用骨架屏占位，能显著降低"白屏/闪烁"的负面感知，让等待更可接受。我在素材质量预测的推荐加载、图片重塑生成过程中用 shimmer，配合流式渲染，用户感觉"系统在动"，而不是卡住。

## D. UI 性能优化 ⭐

### 39. ⭐ 讲讲你最有代表性的性能优化项目，量化结果是什么？
**参考回答**：DNV 广告创建/编辑向导性能优化。多个向导步 P95 高达 8–10 秒。我作为核心贡献者从 UI 和数据两侧优化，最终：广告组编辑页 P95 从 10s→2.8s（-72%），创建页 8s→2.7s（-66%），Native 广告创建 6s→3.6s（-40%）。P75 也有 49%–70% 的改善。这些都是**生产环境**多周对比数据。

### 40. ⭐ 你是怎么定位性能瓶颈的？方法论是什么？
**参考回答**：我把总时延拆成几段：**浏览器渲染（JS 执行 + reconciliation）+ UI 侧 API 等待 + MT 处理 + MDS/OData 依赖 + MT↔MDS 网络传输**。用 Chrome Performance 面板看 JS 执行热点和渲染，用自定义 perf marker 和日志埋点区分各段耗时。关键是**先分清是 UI 慢还是后端慢**，否则会在错误的地方使劲。结果发现既有 UI 渲染问题，也有后端依赖问题，所以两侧都要治。

### 41. UI 侧你做了哪些优化？
**参考回答**：① **隐藏面板懒渲染**——不可见的高级设置、遗留 Backbone 受众列表不进初始渲染；② **React 记忆化治理重渲染风暴**——稳定引用、拆 state、memo 化；③ **延迟加载重组件**——比如 Image Experience 图片组件不阻塞首屏 ready。Native 广告步早期实验单是懒渲染就有约 40% 的渲染时间收益。

### 42. ⭐ 数据侧你做了哪些优化？
**参考回答**：① **缓存预热（cache warm-up）**——把受众关联、行业、职能、人口属性这些昂贵请求提前到用户到达该步之前触发，等真正进步骤时缓存已就绪；② **请求拆分**——把一个合并的大受众请求拆成几个参数更稳定的小请求，提高缓存命中率；③ **绕过非必要的初始调用**——区分"首屏必需"和"可延迟"的数据，删掉初始路径上不必要的 audience association 调用；④ **客户端缓存 + promise caching**。这几招配合下来，广告组编辑 P75 从 2.6s→1.8s，创建从 2.0s→1.2s。

### 43. ⭐ "缓存预热"具体怎么实现？为什么有效？
**参考回答**：核心思想是**把昂贵的数据获取移出交互关键路径**。多步向导有天然机会：用户还在当前步操作时，我就提前发起下一步需要的数据请求。等用户点进下一步，数据要么已在缓存、要么请求已在飞行中，就不用在渲染时同步等待。之所以有效，是因为用户的"思考/操作时间"本来是空闲的，用它来预取等于把延迟藏起来了。

### 44. 请求拆分为什么能提高缓存命中率？合并请求不是更省往返吗？
**参考回答**：这是个权衡。合并请求往返次数少，但**参数组合多、更易变**，缓存 key 不稳定、命中率低，而且一个大请求里只要有一个不可缓存的部分，整体就没法有效缓存。拆成小请求后，每个请求参数稳定、可独立复用缓存，命中率显著提高，还能让可缓存的部分不被不可缓存的部分拖住。在我们这个"同样的受众/行业数据被反复需要"的场景，缓存命中的收益远大于多几次往返的成本。

### 45. 你怎么确认懒渲染没有破坏功能（比如保存语义）？
**参考回答**：隐藏面板懒渲染最大的风险是——某些组件在初始挂载时有副作用（发请求、初始化数据），不渲染就丢了。所以我会：① 排查这些隐藏组件是否有初始副作用；② 对比 Beta SI 上的行为和 bulk upsert 的保存 payload，确认懒渲染前后**保存的数据完全一致**；③ 补 E2E 覆盖关键保存路径。确认"不可见 ≠ 不需要其副作用"之后才敢延迟渲染。

### 46. 你怎么区分 UI 渲染瓶颈和后端瓶颈？
**参考回答**：加分段埋点。我在 MT 受众瓶颈区、OData 服务、MT↔MDS 网络传输都加了日志/marker。这样一条请求能看到：前端等了多久、MT 处理多久、MDS 依赖多久、网络传输多久。发现有些残余延迟其实来自 MDS/OData 的服务端 P95 很高和 MT-MDS 之间的网络传输——这部分 UI 优化不了，得推动后端。这避免了"后端慢却拼命优化前端"的浪费。

### 47. 优化后你怎么验证效果？为什么不只看本地？
**参考回答**：本地和 Beta SI 只能验证正确性和相对行为，**真实收益必须看生产**。我会对比发布前 3 周和发布后 2 周的 P75/P95 平均值，按步骤（创建/编辑/Native 广告）分别追踪，并在每次优化落地后持续监控确保收益稳定、不回退。比如 01/06 发布后我持续盯了 Prod 数据。

### 48. 如果懒渲染的组件用户后来展开了，会不会有"延迟一下才出现"的新体验问题？
**参考回答**：会有一点，所以要权衡。做法：① 对高频展开的部分可以用 idle 时间预渲染（`requestIdleCallback` 思路）或预取数据，让展开瞬间就绪；② 展开时给即时的骨架屏反馈，避免"点了没反应"。目标是把成本从"所有用户的首屏"转移到"少数真正用该功能的用户的一次小等待"，整体是划算的。

### 49. React 18 的 concurrent 特性（如 `useTransition`）能帮上忙吗？
**参考回答**：能，用于把非紧急更新标记为可中断，优先响应用户输入。比如大列表过滤、重计算可以放进 transition 避免卡输入。不过我们主要收益来自减少不必要的渲染和请求（治本），concurrent 更多是让剩余的重更新不阻塞交互（治标层面的调度优化）。要结合用，先减量再调度。

### 50. 你提到 Native 广告的 P95 从 6s 降到 3.6s，还没到 3s 目标，接下来你会怎么做？
**参考回答**：继续拆剩余的渲染时延和图片/组件初始化成本。具体：进一步细化哪些子组件还在初始就重渲染、把 Image Experience 这类重组件的初始化再往后推、看还有没有可预取或可缓存的调用、以及推动后端把高 P95 的受众/人口属性接口再压。同时加回归护栏（关键 marker 的监控告警），防止后续功能悄悄把延迟顶回去。

### 51. 你会怎么防止性能优化被后续开发者"改回去"？
**参考回答**：加**回归护栏**——对关键向导步的 perf marker 建监控和告警，延迟超阈值就报警；把懒渲染、缓存预热沉淀成团队**可复用的模式/文档**，让新功能默认按这个套路写；code review 时关注新增的初始渲染和初始请求。

### 52. 打包体积（bundle size）优化你做过吗？
**参考回答**：了解手段——代码分割、tree-shaking、按需引入（别整包 import lodash/图标）、分析 bundle analyzer 找大依赖、公共依赖抽 chunk。大型 monorepo 里还要注意包边界和重复依赖。我们团队也做过 SSR bundle 拆分（Ad Preview SSR）。

### 53. 首屏之外，运行时性能（比如输入卡顿）你怎么调？
**参考回答**：定位到具体交互的渲染热点（Profiler），减少该交互触发的渲染范围（局部 state、memo）、把重计算 memo 化或移出渲染、必要时 debounce/transition。表单大量联动时，隔离频繁变化字段是关键。

### 54. 你怎么看"过早优化"？
**参考回答**：优化要**数据驱动**。我不会凭感觉到处加 memo——那反而增加复杂度和比较成本。我的顺序是：先测（Profiler/生产 P95 找真瓶颈）→ 改真正的热点 → 再测验证。没有数据支撑的优化我不做。

### 55. 缓存会带来数据陈旧问题，你怎么控制缓存失效？
**参考回答**：按数据特性定策略。像行业、职能这种**基本不变的参考数据**可以缓存较久甚至整个会话；像受众关联这种**会被用户编辑的数据**，编辑后要主动失效/更新缓存，或用 key 带上版本。原则是"读多写少、变化慢"的数据才激进缓存，可变数据要有明确的失效路径。

### 56. 除了向导页，你的优化方法能推广到别处吗？
**参考回答**：能，而且已经沉淀成团队模式。三条核心原则通用：**① 把昂贵工作移出关键路径（预取/预热）；② 只渲染用户当下需要的（懒渲染）；③ 分离 UI 与后端瓶颈再各自治理**。任何有大量可选区块、遗留内嵌视图、或初始重数据的复杂页面都适用。

### 57. 如果一个页面慢，但你没有埋点数据，你会怎么下手？
**参考回答**：先用 Chrome Performance 录一段，看主线程 JS 执行、长任务、渲染次数、网络瀑布，快速判断是 JS 执行重、渲染多、还是网络等待。再用 React Profiler 定位渲染热点。同时补关键 marker/日志，让后续能持续观测。第一步永远是"让不可见的变可见"。

### 58. 性能和功能开发有冲突时你怎么取舍？
**参考回答**：看用户影响和数据。如果某步 P95 已经很差、影响转化，性能优先；如果只是边际改善但会显著增加复杂度/风险，就排后面。我倾向把优化做成**不改变功能语义**的（懒渲染、缓存、预取都是），这样和功能开发不对立，可以并行推进。

## E. AIGC 素材质量预测 ⭐

### 59. ⭐ 介绍一下素材质量预测（Asset Performance Prediction / PPS）这个功能。
**参考回答**：广告主创建/编辑广告时，系统用 AI 实时预测每个素材（图片、文案）的表现分，并给出可执行的优化建议——比如"这张图和你的落地页相关性低，点一下换成 AI 重塑的更相关版本"。它横跨搜索、Pmax、MMA 等场景，目标是帮广告主在投放前就提升素材质量。我负责其中图片相关性和 AIGC 图片重塑两个核心场景，以及配套遥测。

### 60. ⭐ AIGC 图片重塑（recontextualization）具体是什么？技术流程？
**参考回答**：广告主原图如果和场景/落地页不够贴合，我们调用后端生成式 AI，把图片"重新语境化"生成更相关的候选版本给用户选。前端流程：用户在面板触发 → 前端发起重塑任务 → **轮询任务状态** → 拿到生成的候选图 → 渲染供多选替换。因为生成是异步且耗时的，任务状态轮询和结果的增量呈现是关键。

### 61. ⭐ 你提到的"流式/增量渲染（partial render）"是怎么做的？解决什么问题？
**参考回答**：问题是——AI 一次要生成多张候选图，如果等所有图都生成完再一次性展示，用户要干等好几秒，体验很差。我改成**生成一张就渲染一张**：轮询到部分结果就先把已完成的图片渲染出来，剩下的继续来、继续补。用户很快看到第一张，感知等待大幅下降。配合 shimmer 占位，整个过程感觉是"图在陆续出现"，而不是"卡住了"。

### 62. 轮询（polling）间隔怎么定？太快太慢各有什么问题？
**参考回答**：太慢——用户等待感强、结果出现不及时；太快——请求量大、给后端压力、也浪费。团队把重塑轮询间隔调到过 1 秒这种量级，并在轮询里带任务状态日志便于观测。原则是**在体验和后端负载之间找平衡**，并且只在**用户真正打开面板时才发起**重塑调用（不打开不发），避免无谓开销。

### 63. 为什么"只在打开面板时才触发重塑调用"很重要？
**参考回答**：因为重塑是昂贵的 AI 调用。如果页面一加载就预发起，大量用户根本不会用这个功能，白白消耗后端算力、也拖慢页面。所以要**按需触发**——用户表达意图（打开面板）才调用。这也是性能和成本意识：AI 调用不是免费的。

### 64. 调用里设置 `SkipClassification=true` 是做什么的？
**参考回答**：这是和后端约定的一个优化参数。在这个 UI 场景下，某一步分类计算不是必需的，跳过它能减少端到端处理时间。它体现的是——**前端要理解后端的处理链路，在满足功能的前提下，通过参数裁掉不必要的计算来降时延**，而不是把后端当黑盒。

### 65. ⭐ 这种 AI 功能你怎么设计遥测？为什么遥测这么关键？
**参考回答**：AI 功能的好坏没法只靠直觉，必须靠数据闭环。我埋了多维度信号：Fix-it 按钮点击、Tooltip 展示/点击、预测分数、目标素材列表（targetAssetIdList）、AdType、创建/编辑 Flow、原图 URL、面板打开时渲染出的候选数等。这些一路打通到后端 SCOPE/Kusto 报表，用来回答：用户接受率多少？哪种素材更容易被建议替换？重塑图的采纳率如何？这些数据直接驱动产品迭代和模型评估。

### 66. 前端遥测怎么保证不影响性能和不丢数据？
**参考回答**：埋点要**轻量、异步、批量**，不阻塞主交互；关键转化信号（点击、采纳）要可靠上报，可用 sendBeacon/重试。同时避免过度埋点造成噪音。我埋点时会想清楚"这个信号要回答什么产品问题"，而不是把所有东西都记下来。

### 67. AIGC 生成失败/超时前端怎么处理？
**参考回答**：要有明确的错误态和重试。我做过"出错时展示 Try Again 视图"、处理新的错误 schema。因为 AI 调用不稳定性天然高（超时、内容安全拦截、生成失败），前端必须优雅降级：给清晰提示、允许重试、不让用户卡在无反馈的中间态。

### 68. 图片重塑的多选交互你怎么设计？
**参考回答**：用户可能想从多张 AI 候选里选多张替换，所以我支持了面板上的多选。要处理选中态管理、和原素材的关联替换逻辑、以及选择后的保存语义。难点在于把"AI 候选 → 用户选择 → 替换到广告素材"这条链路的数据映射做对（比如 targetAssetId 的对应）。

### 69. 你怎么处理 AI 返回图片的 assetId 是字符串还是数字这类契约不一致？
**参考回答**：这正是我们踩过的坑（image asset id 是 string 时预测失败）。前端要对后端契约保持防御：类型收窄、兼容 string/number、别假设。根因是前后端对 id 类型理解不一致，解决要么统一契约、要么前端做兼容转换并加类型守卫。这类"契约边界"bug 在 AI + 多团队协作里很常见。

### 70. 这个功能怎么灰度上线的？
**参考回答**：用 pilot/feature flag 分市场、分场景灰度。比如先排除某些市场（中国市场单独处理）、先在部分广告类型开。配合动态权限/配置控制谁能看到。灰度期间盯遥测和 P95，稳了再扩量。GA 前要补足 signup 测试、pmax 测试、image-diff 视觉回归等。

### 71. 素材质量预测和"广告强度（Ad Strength）"是什么关系？
**参考回答**：Ad Strength 是给广告整体素材质量打分的体系，PPS/素材表现预测是更细粒度、AI 驱动的预测与改进建议，二者在产品上融合——比如在 Universal Campaign 的素材汇总面板里集成 Ad Strength + 表现预测。后端数据侧我也为 Ad Strength 写了 UI 遥测的 SCOPE 分析。

### 72. 如果让你评估这个 AI 功能"是否成功"，你看什么指标？
**参考回答**：核心是**采纳率和效果**：建议的展示→点击→采纳漏斗、AI 重塑图的采纳率、采纳后素材质量分/预测分的提升、以及最终对广告表现（点击率/转化）的影响。还要看负面信号——错误率、超时率、用户是否频繁忽略建议。我搭的遥测就是为回答这些问题服务的。

## F. 第三方广告监测 IAS / DoubleVerify / ISPOT / MOAT

### 73. ⭐ 什么是广告第三方监测？为什么广告主需要它？
**参考回答**：广告主花钱投广告，需要一个**独立于平台**的第三方来验证广告真的被展示了、展示在品牌安全的环境里、没有被机器人刷量。IAS（Integral Ad Science）、DoubleVerify、ISPOT、MOAT 就是这类第三方公司。前端要做的是让广告主在 UI 里配置这些监测：填厂商、追踪参数、品牌 ID 等，平台再把这些信息传给投放系统，曝光时触发第三方的监测像素。

### 74. ⭐ 这个功能的技术难点在哪？
**参考回答**：**组合复杂度**。监测要覆盖展示、视频、原生等多种广告形态，每种形态的数据模型和 UI 不同；又要支持广告级和广告系列级；还有多家厂商各自的规则。形态 × 厂商 × 层级，排列组合很多，每一条都要保证数据正确、和后端 MT 模型对齐、错误码映射正确。此外还有竞价策略约束（某些监测只在特定竞价策略下允许）、追踪参数的格式校验。

### 75. 你提到"追踪参数的正则提取（regex extract）"，具体是什么？
**参考回答**：第三方追踪 URL 里包含结构化的参数（比如厂商标识、监测属性）。前端需要用正则从用户输入或既有配置里提取/校验这些参数，映射到后端需要的字段（我做过 CH 属性映射名的 mapping）。难点是各厂商格式不同、要兼容多种输入、正则要够健壮又不误伤。我为此专门调过多次正则和提取 pattern。

### 76. 品牌 ID 校验你在前端怎么做？
**参考回答**：ISPOT 的品牌 ID 有长度/格式约束，我在 UI 加了前端校验——超长/非法即时报错，而不是等提交被后端拒。还处理了"厂商已选时把无效项加回可选列表"这类边界。核心思路还是**尽早拦截错误**，减少无效提交。

### 77. 竞价策略约束是怎么回事？
**参考回答**：某些第三方监测（比如 IAS 的 verified tracking）只在特定竞价策略/广告目标下才有意义或被允许，所以前端要根据当前竞价策略动态启用/禁用监测选项，并给出解释。这需要理解业务规则并在 UI 状态里正确联动。

### 78. 批量编辑（bulk edit）监测设置有什么坑？
**参考回答**：批量编辑要对多个实体应用同一改动，坑在于**各实体当前状态不同**（有的已链接厂商、有的没有）、以及"应用到全部"和"解除链接时的重置"逻辑。我做过 MOAT 的批量编辑、以及 DoubleVerify 解除链接时对未链接项的忽略处理。要仔细定义批量语义，避免误改。

### 79. 你怎么和后端对齐错误码映射？
**参考回答**：后端 MT 返回的错误码需要在前端映射成用户能看懂的提示。我会和后端一起把错误码→用户消息的映射表定清楚（Deal 的 GEO 错误、监测的各种校验错误都做过），并处理新错误 schema。目标是让广告主看到"哪里错了、怎么改"，而不是一个裸错误码。

### 80. 原生广告（Native Ads）的监测和展示广告有什么不同？
**参考回答**：原生广告的素材结构和展示位不同，IAS 设置的落地点、提取 pattern 都不一样。我为原生广告单独做过 IAS 落地（还修过 native ad display plus 编辑页 IAS 不正确显示的 bug）。核心是**同一套监测能力要适配不同广告形态的数据模型**。

### 81. 这么复杂的组合，你怎么保证不出回归？
**参考回答**：靠测试。每个形态×层级都有 E2E/单测覆盖，GA 前跑全套。灰度用 ccflag/pilot 控制，先小范围。改动时我会特别关注共享逻辑的影响面。作为 DRI 我也经常处理这块的测试稳定性。

### 82. ISPOT 在广告系列级支持，和广告级有什么区别？
**参考回答**：系列级设置会作为默认下发到该系列下的广告，广告级可覆盖。要处理**继承和覆盖**的优先级、以及层级间的数据一致性。我做过把 ISPOT 支持提升到 campaign level 的工作。

### 83. 你从这个 0→GA 项目里学到最多的是什么？
**参考回答**：**如何在高复杂度业务里保持正确性**。方法是：把组合空间显式列清楚、共享逻辑收敛、边界用校验和测试兜住、和后端把契约/错误码对齐。还有就是**同理心**——每一个前端校验、每一个清晰报错，都是在帮广告主少犯错、少浪费预算。

### 84. 如果第三方厂商 API 变更，你的设计能多快适应？
**参考回答**：因为我把厂商差异收敛在提取/映射层，加新厂商或改参数格式主要动那一层，UI 骨架和保存链路基本不变。契约变更靠类型和校验兜底、靠 E2E 回归验证。设计目标就是让"厂商维度的变化"局部化。

## G. Deal / Netflix / Xandr 版权广告

### 85. 什么是 Media Deal / Deal 广告？
**参考回答**：微软和优质媒体（比如 Netflix、以及通过 Xandr 的视频库存）有版权/直采合作，广告主可以投到这些优质库存上，这类叫 Deal 广告。前端要支持 Deal 广告系列/广告组的创建和编辑：选 Deal、配定向（年龄/性别/地域/频次）、竞价、以及各种 Deal 特有的约束。

### 86. ⭐ 你做的"被拒地域前置拦截"是什么？为什么有价值？
**参考回答**：某些 Deal 对可投放地域有限制，如果广告主选了被拒的地域，提交后会被后端 MT 拒绝。我做的是**在 UI 就前置拦截这些 denied location**，提交前就拦下并提示，而不是提交—失败—再改。价值是省掉一次无效的前后端往返、给用户即时反馈、降低挫败感。这是"fail fast in UI"思想的体现。

### 87. Deal 的竞价校验有什么特别？
**参考回答**：Deal 有自己的最低竞价/视频质量等约束，前端要在提交前校验（我做过 deal bid 校验、视频质量校验）。坑在于这些规则和普通广告不同、还会变，要和后端规则保持一致，避免前端放过了后端却拒、或前端过严挡了合法配置。

### 88. ⭐ Netflix/Media Deal 创建入口的 kill-switch 清理，你是怎么做的？风险在哪？
**参考回答**：这个功能 GA 后决定永久下线创建入口（用一个恒为 true 的 kill-switch 控制）。我负责把整条**创建路径**安全删除，同时**保留编辑流**（已有的 Deal 广告还要能编辑）。风险在于：① 创建和编辑共享了很多组件，要精确区分哪些只属于创建、哪些编辑也用，不能误删；② 跨两个代码库（CampaignUI + AdsAppUI），有严格的**合并顺序**——必须先合前端创建代码的删除，再删后端的 pilot 定义，否则 `!flag` 会翻转让入口"复活"；③ 还要清理 E2E 套件注册、pilot、配置。稍有不慎就破坏线上，所以我做了完整的依赖分析和分阶段验证。

### 89. 跨仓库、有依赖顺序的清理，你怎么保证不出事？
**参考回答**：① 先做**依赖分析**，画清楚"谁依赖谁、删了会不会让某个开关翻转"；② 定明确的**PR 合并顺序**并写进文档；③ **分阶段**做，每阶段可独立验证（先删创建 UI、再删下游 wiring、再删 package、最后清测试/配置）；④ 用 lint（含 package 级 orphan 依赖检查）和 build 验证每步没留悬空引用。这类"减法"工作比加功能更考验对系统的理解。

### 90. 删代码时你怎么确定某段逻辑"没人用了"？
**参考回答**：用工具找引用（全局搜索、find usages、package 依赖分析），确认没有 runtime 引用；对共享符号，确认剩下的引用都是无害的（比如测试里的 mock）。删完跑 lint + build + 相关测试。绝不靠"看起来没用"就删——广告系统里一个悬空引用可能就是线上崩溃。

### 91. Xandr 视频广告系列你做过什么？
**参考回答**：Xandr 是微软收购的广告技术栈，涉及视频库存。我在 Xandr 视频广告系列上做过 IAS 监测的启用和测试、以及相关的 Deal/视频质量逻辑。这块和 Deal、视频广告都有交叉。

### 92. Deal 删除场景前端要处理什么？
**参考回答**：如果一个 Deal 被删除，但广告还引用它，前端要优雅处理——不能崩，要给出合理状态/提示。我专门加过 deal deleted 场景的处理。这属于"外部依赖消失"的健壮性问题，前端要防御。

## H. 推荐系统

### 93. 你做的广告推荐都有哪些类型？
**参考回答**：受众广告推荐（Audience Ads Recommendation）、视频推荐（VID/DIS/IBRMT/CTV 多种子类型）、原生推荐（DAO/NAQ）、以及视频素材推荐直接应用到 UI。本质都是把后端 AI/算法产出的推荐，在合适的位置（页面、卡片、summary bar）呈现给广告主并支持一键应用。

### 94. 推荐功能前端的难点？
**参考回答**：① **动态权限/配置**——不同用户/市场看到的推荐不同，要动态加载权限和配置（我修过 dynamic permission 不加载、动态 config 的问题）；② **应用推荐的数据回写**——用户接受推荐后要正确改写广告模型；③ **多类型统一呈现**——不同推荐类型共享一套卡片/交互，又要处理各自差异（我修过 campaign type 未处理的 i18n 映射问题）。

### 95. 推荐的"接受/忽略"你会怎么埋点？
**参考回答**：展示、点击、接受、忽略都要埋，形成漏斗。这样能算接受率、看哪类推荐更有效。和素材质量预测的埋点思路一致——推荐类功能必须有数据闭环才能证明价值和迭代。

### 96. 动态权限加载失败会怎样？你怎么处理？
**参考回答**：权限没加载好，推荐可能不显示或显示错。要有**加载态和兜底**：权限未就绪时不渲染/显示占位，就绪后再渲染；失败要降级而不是崩。我修过 dynamic permission not load 的 bug，根因常是异步时序——权限还没回来组件就渲染了。

### 97. 推荐卡片的文案经常要改（text scrub），你怎么应对？
**参考回答**：所有文案走 i18n 的 `_TL_`，text scrub 时改的是 resource，不动逻辑。我做过多次视频、受众推荐的 text scrub。把文案和逻辑解耦，改文案就很轻。

### 98. 推荐和素材质量预测在产品逻辑上有重叠吗？
**参考回答**：有关联。推荐是"给你更好的素材/配置"，素材质量预测是"评估并改进你现有素材"，都是**帮广告主提升质量**的 AI 能力，产品上会协同呈现。技术上都涉及异步拉取、动态呈现、一键应用、遥测闭环这套模式。

## I. 可访问性 A11y

### 99. ⭐ 你们为什么如此重视可访问性？MAS 是什么？
**参考回答**：微软有强制的可访问性标准 MAS（Microsoft Accessibility Standard），对标 WCAG。作为面向全球广告主的产品，键盘可操作、屏幕阅读器可读是硬性合规要求，不是可选项。我修过大量 A11y bug，也把它当作日常质量的一部分。

### 100. ⭐ 你修过的焦点管理（focus management）问题举个例子？
**参考回答**：典型是**面板/浮层关闭后焦点丢失**。比如素材质量预测的"替换图片"面板，关闭后焦点没回到触发它的"Fix it"按钮，键盘用户就"迷路"了。我修的是——关闭时把焦点显式还给触发元素（trigger），满足 MAS 2.4.3。还修过下拉框关闭后的焦点重聚（ref refocus）。

### 101. `aria-activedescendant` 是干什么的？你怎么用？
**参考回答**：它用于**组合框/列表这种"焦点在容器、但高亮项在变"的场景**：容器保持焦点，通过 `aria-activedescendant` 指向当前活动项的 id，屏幕阅读器就能播报当前项，而不用真的移动 DOM 焦点。我修过它取值异常导致屏幕阅读器播报错误的问题。

### 102. Popover 里的键盘焦点会"跑出去"，怎么办？
**参考回答**：给交互式 Popover 加 **focus trap**（Fluent v9 的 `trapFocus`），让 Tab 在浮层内循环，不跑到背后的页面；关闭再把焦点还回触发元素。这满足 MAS 2.1.2 / 2.4.3。

### 103. 一个"看起来像标题但不是标题"的文本，为什么是 A11y 问题？
**参考回答**：屏幕阅读器用户靠标题（h1–h6）导航。如果视觉上是标题、但用 styled span/div 实现，屏幕阅读器的"按标题跳转"就会跳过它，信息结构对盲人用户就丢了。解法是用真正的语义标题（Fluent 的 `as="hN"` 或 `role="heading"` + `aria-level`），满足 1.3.1。

### 104. 你怎么测可访问性？
**参考回答**：键盘走查（只用 Tab/方向键/Enter 能不能完成流程）、屏幕阅读器（NVDA/Narrator）实测、自动化 a11y 检查（axe 类）、以及我们有 accessibility E2E。但工具只能查一部分，焦点顺序、播报是否合理还得人工走查。

### 105. 图表（chart）的可访问性怎么做？
**参考回答**：图表纯视觉，要给键盘和屏幕阅读器等价信息：图例可键盘操作、数据点可读、必要时提供数据表替代。团队在 Highcharts/Smart Page 仪表盘上做过 a11y 化（饼图图例键盘处理等）。

## J. 国际化 i18n

### 106. 你们的 i18n 机制是怎样的？
**参考回答**：所有用户可见文案用 `_TL_('...')` 标记（构建期抽取，无需 import），再用 `i18n.getString(_TL_('...'))` 取译文。`_TL_` 的参数必须是**静态字符串字面量**（不能传变量），这样构建期才能扫描抽取。变量插值走 `i18n.getString(_TL_('Welcome {{name}}'), { name })`。

### 107. 为什么 `_TL_` 的参数必须是静态字符串？
**参考回答**：因为它是**构建期静态抽取**——构建工具扫描源码里 `_TL_('字面量')` 收集待翻译串。如果传变量，构建期无法确定值，就抽不到、翻译不了。所以规则是第一个参数必须是 raw string。

### 108. 函数组件和类组件怎么拿到 i18n？（一个常见坑）
**参考回答**：函数组件用 `useContext(I18nContext)`；类组件用 `withI18nConsumer` HOC 注入 `this.props.i18n`。**特别注意：没有 `useI18n` 这个 hook**——这是个常见错误，用了会崩。已经从 props/context 拿到 i18n 的组件直接用即可，不用再包一层。

### 109. 复数、日期、货币这种本地化怎么处理？
**参考回答**：走 i18n 框架的格式化能力（占位符 + 参数），不手工拼字符串。货币/数字/日期用本地化格式化。广告是全球产品，市场差异（比如中国市场单独处理逻辑）也常见，我在功能里会按 market/locale 做分支。

### 110. text scrub 是什么流程？
**参考回答**：文案评审——产品/文案团队审校所有用户可见串。因为文案都走 `_TL_`，scrub 时改的是资源串，代码逻辑不动。我做过多次视频、受众推荐、监测的 text scrub，属于低风险改动。

## K. 测试与质量工程

### 111. ⭐ 你们的测试体系有哪些层次？
**参考回答**：① Jest **单元测试**（逻辑、组件）；② **组件测试 CT**（在近真实环境渲染组件、跑 demo）；③ **E2E**（Selenium/Playwright，跑真实浏览器流程）；④ **image-diff 视觉回归**（截图对比防 UI 回归）。不同层次覆盖不同风险，E2E 保关键用户流程，单测保逻辑，image-diff 保视觉。

### 112. ⭐ 讲讲 Enzyme 到现代框架的迁移（DTRT），为什么迁、怎么迁？
**参考回答**：Enzyme 对新版 React 支持差、且鼓励测实现细节（shallow render、测 state/props）。迁移方向是更贴近用户行为的测法（RTL 思路——测渲染结果和交互，而不是内部实现）。迁移工作量大：要逐个把 shallow/instance 断言改成基于 DOM/角色的查询，处理 mock 差异。我主导做了多批（Enzyme Mig 1/2、Video tests 等），也踩过不少 API 差异的坑。

### 113. E2E 测试最容易 flaky（不稳定）的原因？你怎么治？
**参考回答**：主要是**时序/异步**——元素还没出现就去操作、动画未结束、网络时机不定、测试间状态污染。治法：用**显式等待条件**（等元素可见/可点、等状态）而不是硬 sleep；测试前重置状态/过滤器；隔离测试数据；对已知抖动加稳定化（等 state、优化随机数）。作为 DRI 我处理过大量 flaky test。

### 114. 一个测试一直 flaky，短期你会怎么办？长期呢？
**参考回答**：短期——如果确认是环境/抖动且阻塞发布，把它加进 `IgnoredTestNames` 临时忽略，避免堵住整个流水线（但要记录、跟踪）。长期——定位真实根因（时序、选择器、数据），修好再 unignore。忽略只是止血，不能当解决。我两边都做过（filter/ignore 和后续 re-enable）。

### 115. 你怎么写一个好的 E2E 测试？
**参考回答**：① 面向用户流程，不测实现细节；② 用稳定的选择器（data-testid/role，别用易变的样式类）；③ 显式等待，不硬 sleep；④ 每个测试自带数据/状态、可独立跑；⑤ 失败信息可读。我们有 TAPI 页面对象封装选择器，测试复用它们，选择器变了只改一处。

### 116. image-diff 视觉回归怎么工作？有什么坑？
**参考回答**：跑测试截图和基准 hash 比对，不一致就报回归。坑：① **合理的 UI 改动**也会让 diff 失败，需要更新基准 hash；② 渲染的不确定性（字体、动画、异步内容）导致假阳性，要稳定渲染或遮罩动态区域。我做过 image-diff 基准的 bootstrap 和更新。

### 117. 你怎么保证改动不破坏别人？
**参考回答**：改共享逻辑前先 find usages 看影响面；跑相关单测/CT/E2E；关注 code review 里的契约变更；灰度发布小范围先验证。作为 DRI，我对"改一处崩一片"的连锁反应比较敏感。

### 118. 代码覆盖率你怎么看？追求 100% 吗？
**参考回答**：覆盖率是**信号不是目标**。我们有覆盖率门槛（.istanbul.yml 阈值），CI 会卡。我追求的是**关键逻辑和分支被有意义地覆盖**，而不是为凑数写无断言的测试。推 PR 前我会跑单测+demo 测合并覆盖率，确保不掉线、必要时提阈值防回退。

### 119. CTUT 是什么？
**参考回答**：是我们的组件测试（CT）+ 单元测试（UT）体系及其在 CI 的过滤/调度机制。团队还做过 UT/CT 自动生成（AI 生成测试）。作为质量基建的一部分，保证组件在近真实环境被测到。

### 120. 你怎么 mock 数据层（OData/REST）？
**参考回答**：数据层有独立封装（repository/hook），测试时 mock 这层的返回，让组件在确定数据下渲染。既能测正常态，也能构造错误态、空态、加载态。mock 要贴近真实契约，否则测过了线上还挂。

### 121. 单元测试和 E2E 的比例你怎么权衡（测试金字塔）？
**参考回答**：经典金字塔——单测多、集成中、E2E 少而精。E2E 贵且慢，只保最关键的用户流程；大量逻辑/边界用单测覆盖。但广告 UI 很多 bug 是集成/时序问题，所以 CT 和关键 E2E 也不能省。按风险和成本分配。

### 122. 你会为一个 bug 修复写测试吗？
**参考回答**：会，尤其是回归 bug。修复的同时补一个能复现该 bug 的测试，防止它再回来。比如我修某个 IAS 显示 bug、契约 bug 后都会考虑加覆盖。

### 123. 测试跑得慢影响开发效率，你怎么优化？
**参考回答**：拆套件避免超时（我们把大套件拆分过）、并行跑、CT 时间优化、只跑受影响的包。团队有 repeater/调度机制。本地我只跑改动相关的包而不是全量。

### 124. RME、SI、BVT 这些是什么？
**参考回答**：都是 CI 里的测试环境/阶段——SI（服务集成环境）、BVT（构建验证测试）、RME（滚动模型评估，验证上游依赖变更不破坏我们）。作为 DRI 我经常处理这些环境里的失败：定位是真回归还是环境/上游问题，真问题修、环境问题协调或临时过滤。

## L. 数据与遥测 SCOPE / KQL / ADF

### 125. ⭐ 作为前端，你为什么还写 SCOPE 大数据脚本？
**参考回答**：因为 AI/推荐这类功能的价值必须靠数据证明。前端埋的遥测流到大数据平台（Cosmos），我用 SCOPE 脚本去聚合分析——比如 Ad Strength UI 遥测按 Flow（创建/编辑）、Segment、ClickType 拆分，算采纳率、覆盖率。我不想只交付 UI 就完事，我想端到端知道"这个功能到底有没有用"。这也让我和数据/产品沟通更顺。

### 126. SCOPE 是什么？和 SQL 有什么关系？
**参考回答**：SCOPE 是微软内部的大数据处理语言/平台（跑在 Cosmos 上），语法类 SQL（SELECT、JOIN、GROUP BY）但面向海量分布式数据，支持自定义 extractor/processor/reducer。我用它写批处理脚本聚合遥测。

### 127. 你提到读 ">250MB 的 substrate1 ADLS Gen2 文件"，难点在哪？
**参考回答**：超大文件不能简单整体读。我用了 **AtomicFileProcessing extractor / AriaExtractorBlueshift** 这类机制从 ADLS Gen2 读取大文件。难点是大文件的分片/流式读取、格式解析、以及性能。这属于把 UI 遥测原始数据落地成可分析形式的管线环节。

### 128. KQL / Kusto 你用来做什么？
**参考回答**：Kusto 是微软的实时日志/遥测查询引擎，KQL 是它的查询语言。我用它写遥测报表和线上问题排查查询——比如 Fix-it 预测分数报表、采纳率、以及 DRI 时查客户端错误日志定位根因。我还修过报表口径（把 `dcount` 近似去重改成 `count_distinct` 精确去重）。

### 129. `dcount` 和 `count_distinct` 的区别，为什么要改？
**参考回答**：`dcount` 是**近似**去重计数（用 HLL 算法，快但有误差），`count_distinct` 是**精确**去重。数据量大时 dcount 省资源，但做需要精确口径的报表（比如按客户统计）时误差不可接受，所以我切成 count_distinct 保证准确。这是"性能 vs 精度"的典型权衡。

### 130. Azure Data Factory (ADF) 你做过什么？
**参考回答**：在 DemandMetrics 里维护 ADF 的**触发器（trigger）和数据回填（backfill）**、以及 ARM 模板部署，支撑 Creative Quality 的数据管线——比如把某段时间的素材数据回填进表、加新的 sourceType、把 Ad Strength 加进表。ADF 是编排数据流的工具，我用它做定时/回填的数据搬运和处理编排。

### 131. 数据回填（backfill）要注意什么？
**参考回答**：① **幂等**——重跑不能产生重复数据；② **范围明确**——回填哪段时间、哪些实体要清楚（我做过 2/17→3/1 的回填）；③ **不影响线上正常管线**；④ 回填量大时注意资源和时长。回填本质是"补历史数据"，最怕重复和污染。

### 132. ARM 模板是什么？你怎么用？
**参考回答**：Azure Resource Manager 模板，用声明式 JSON 定义 Azure 资源/配置，实现基础设施即代码（IaC）。我用它部署 ADF 相关的配置（部署时基于协作分支的 commit）。好处是可版本化、可复现、可审计。

### 133. 前端 + 数据这套全链路能力，对你做功能有什么帮助？
**参考回答**：闭环。我能自己定义"这个功能要回答什么问题"→在前端埋对的信号→在后端 SCOPE/Kusto 把它变成报表→用数据验证并迭代。不用来回等别人，沟通成本低，也更容易证明工作的业务价值。这是我区别于纯 UI 工程师的地方。

## M. 系统设计 / 架构 / 权衡

### 134. ⭐ 如果让你从零设计一个"广告创建向导"，你会怎么架构？
**参考回答**：分层：① **数据层**——OData/REST repository 封装 + 客户端缓存/预取，屏蔽后端细节；② **状态层**——全局 store 存跨步骤的 campaign/adgroup/ad 模型，局部 state 存步骤内 UI；③ **步骤编排**——FlowGate/向导框架控制步骤顺序、校验门禁、可选步骤；④ **组件层**——Fluent 组件 + 共享业务组件，隐藏面板懒渲染；⑤ **校验层**——schema 校验 + 服务端错误回填；⑥ **遥测层**——每步 perf marker + 行为埋点。设计原则贯穿"昂贵工作移出关键路径、只渲染当下需要、契约类型化、可灰度"。

### 135. 多步向导的状态管理，跨步骤数据怎么设计？
**参考回答**：跨步骤共享的领域模型（广告数据）放全局 store，单一数据源；步骤内的临时 UI 态放局部。要处理"步骤间预填/联动"（前一步的选择影响后一步的选项）和"保存语义"（草稿 vs 提交）。同时利用步骤间的空闲预取下一步数据。

### 136. 大型 monorepo 相比多仓库，优劣是什么？
**参考回答**：优点——统一依赖版本、跨包重构方便、共享组件易复用、一致的工具链。缺点——构建/测试慢、包边界容易失控、一个改动影响面大。应对：清晰的包边界和依赖规则（lint-package 查 orphan/循环依赖）、增量构建、只测受影响包。我在 Netflix 清理时就靠 package 级依赖检查发现悬空依赖。

### 137. 前端和后端的契约怎么管理，避免集成 bug？
**参考回答**：把契约**类型化**（TS 类型/接口），边界处（API 响应）做防御性收窄；错误码有明确映射；契约变更走版本/兼容；用 E2E 在真实链路验证。我踩过 assetId string/number 不一致的坑，教训就是"边界不能假设，要么统一契约、要么前端兼容+守卫"。

### 138. 你怎么设计 feature flag / 灰度？
**参考回答**：用 pilot flag 控制功能可见性，可按市场/客户/百分比灰度。新功能默认关，逐步放量，盯遥测和 P95，稳了 GA。GA 后清理 flag（我做过 GA'd flag 的 kill-switch 清理）。设计时代码要能干净地"两条路都走"，flag 删除时不留死代码。

### 139. 遗留系统（Backbone）和现代 React 怎么共存/演进？
**参考回答**：桥接——在 React 里挂载 Backbone view，或反之，共享数据层。演进策略是**绞杀者模式（strangler）**：新功能用 React，旧的在触碰时逐步替换，而不是大爆炸重写。性能上要注意别在初始就渲染重的遗留 view（我做的懒渲染就针对遗留 Backbone 受众列表）。

### 140. 如果一个功能同时要"快上线"和"高质量"，你怎么权衡？
**参考回答**：先 MVP + 灰度小范围，用 flag 控制风险，快速验证价值；同时把关键路径（数据正确、不崩、可回滚）做扎实，非关键的打磨可迭代。质量的底线（不破坏线上、可访问性、可本地化、有测试）不能省，锦上添花的可以排期。

### 141. 你怎么做技术方案的决策？
**参考回答**：先明确约束和目标（用户价值、性能、复杂度、风险）；调研现有代码和模式（能复用不重造）；必要时写设计文档、和团队/资深工程师对齐；用数据或原型验证关键假设。我倾向选**改动面小、可灰度、可回退**的方案。

### 142. 一个页面数据依赖很多个 API，你怎么编排？
**参考回答**：区分**首屏必需**和**可延迟**：必需的并行发起（Promise.all）、可延迟的懒发或预取；有依赖关系的串行但尽量减少链长；可缓存的走缓存/promise caching 防重复；给每个关键调用埋 marker 便于定位瓶颈。核心还是"关键路径最短"。

### 143. 你怎么保证前端的健壮性（一个 API 挂了不整页崩）？
**参考回答**：局部错误边界（error boundary）隔离崩溃、每个异步有 loading/error/empty 三态、外部依赖消失要防御（Deal 删除场景）、可选数据缺失不能让主流程挂。目标是**降级而非崩溃**。

### 144. 如果要支持一个新广告形态，你的代码扩展性如何？
**参考回答**：因为我把形态差异收敛在数据模型映射和少数分支里，加新形态主要是补映射、配置和该形态特有的 UI，共享的向导骨架、监测、校验框架基本复用。设计时就按"形态是一个维度"来抽象，避免把形态逻辑散落各处。

### 145. 回顾这些项目，如果重做一次，你会改进什么？
**参考回答**：① 更早建**回归护栏**（性能 marker 的告警），别等出问题；② 契约边界更早类型化，少踩 string/number 这类坑；③ 遥测在功能设计阶段就一起设计，而不是后补；④ 复杂组合（监测的形态×厂商）更早抽出显式的映射层，减少后期修补。

## N. DRI / 线上 / CI-CD

### 146. ⭐ DRI 是什么？你作为 DRI 都做什么？
**参考回答**：DRI（Designated Responsible Individual）是轮值的线上响应负责人。职责：盯生产告警和客户端错误、定位并修复线上问题、稳定 CI/CD 流水线（处理 flaky/失败测试）、协调上游依赖变更的影响。我干过很多：查 Kusto 错误日志定位根因、临时过滤堵塞流水线的 flaky test、修真回归、协调 RME/MT 变更。

### 147. 线上报了一个客户端 JS 错误，你的排查流程？
**参考回答**：① 用 Kusto 查错误详情、堆栈、影响范围（多少 CID/用户/会话）；② 从堆栈定位到源码；③ 查 git 历史找可疑改动（哪个 commit/PR 引入）；④ 本地复现；⑤ 修复 + 加回归测试；⑥ 建 bug、开 PR 关联、必要时热修/回滚。核心是"从遥测→源码→提交历史"三段式定位。

### 148. 上游依赖（比如 MT 后端）的变更把你的测试搞挂了，怎么办？
**参考回答**：先判断是**真回归**还是**上游契约变更导致的预期失败**。如果是上游变更，协调时间线、更新前端以适配（或临时过滤等上游就绪）；如果是真 bug，修。RME 就是专门检测上游变更影响的，我处理过很多这类。关键是分清责任边界，不盲目改自己的代码。

### 149. 你怎么在"堵塞发布"和"不掩盖问题"之间平衡（忽略测试）？
**参考回答**：忽略是**止血不是治疗**。只有确认是环境/抖动、且在堵塞整条流水线时才临时忽略，并且必须记录、建 bug、跟踪、后续修复 re-enable。绝不用忽略来掩盖真回归。我两端都做过——filter/ignore 和后续 re-enable。

### 150. CI/CD 流水线你了解到什么程度？
**参考回答**：了解我们从构建、单测/CT、E2E、image-diff、到部署（SI/Beta SI/Prod）的流程，以及 lint（文件级 ESLint + package 级 spindle lint）的门禁。推 PR 前我会本地跑 lint 和相关测试避免堵流水线。也处理过流水线失败的诊断（构建、测试、依赖问题）。

### 151. 你怎么减少自己 PR 被流水线打回的概率？
**参考回答**：推前本地跑 file-level ESLint + package-level lint（查 orphan/缺失依赖）+ 相关单测/CT，改了性能敏感区就本地看渲染。把问题挡在本地，别浪费流水线时间。这也是团队沉淀的 pre-push 检查习惯。

### 152. 处理线上紧急问题时你怎么决定"热修 vs 回滚"？
**参考回答**：看影响面和修复确定性。影响大、根因清楚、修复小而稳→热修；根因不明或修复有风险→先回滚止血再从容修。永远优先**尽快恢复用户体验**，再追根因。回滚这种高风险操作我会确认清楚再做。

## O. 软技能与职业发展

### 153. 你怎么和产品经理/设计师协作？
**参考回答**：早参与，把技术约束和成本前置沟通（比如某个交互会拖慢首屏、某个 AI 调用很贵要按需触发）。用数据和产品对话（遥测、P95）。设计上用运行 demo 对照 Figma 逐像素对齐。目标是既满足体验又不牺牲性能/可维护性。

### 154. 你怎么做 code review？
**参考回答**：关注正确性（契约、边界、异步/await）、性能（新增的初始渲染和请求）、可访问性、i18n、测试覆盖、以及可维护性（是否过度设计）。对复杂改动我会看影响面。给反馈对事不对人、给出可操作建议。我们有专门的 review 规范（前端质量、性能重点）。

### 155. 遇到不熟悉的大代码库，你怎么快速上手？
**参考回答**：先搜索定位（语义搜索找概念、grep 找精确串、find usages 看引用）、读关键路径而不是逐行；跑起来 demo/本地 debug 看真实行为；必要时加日志/断点。理解"数据从哪来、状态怎么流、组件怎么组合"三条主线。我在这个 490+ 提交的库里就是这么工作的。

### 156. 你怎么持续学习新技术？
**参考回答**：跟进 React/Fluent 的演进（v9、concurrent）、在真实项目里试用；读团队资深工程师的设计和 PR；做完项目复盘沉淀模式（我把性能优化沉淀成团队可复用模式）。我也主动往数据、AI 功能这些相邻领域扩展。

### 157. 你和别人技术意见不合时怎么处理？
**参考回答**：用数据和场景说话，而不是凭偏好。列清各方案的成本/风险/收益，必要时写小原型或查生产数据验证。对齐目标（用户价值、可维护性），通常分歧就化解了。实在不定就升级到资深工程师一起拍。

### 158. 举一个你主动推动改进的例子。
**参考回答**：性能优化。它不是分派给我的单一 bug，而是我看到向导页 P95 太差，主动做了系统的瓶颈分析、UI+数据两侧优化、并把方法沉淀成团队可复用模式，还建议加回归护栏防止倒退。从发现问题、量化、解决到防复发，我推动了整条。

### 159. 你的技术优势和短板分别是什么？
**参考回答**：优势——大型复杂系统里端到端交付、性能优化、前端+数据全链路、对线上质量负责。短板（诚实版）——纯后端服务/分布式系统的深度不如前端；不过我在数据管线上补了不少，也愿意继续往系统广度上扩展。我会主动找机会补齐。

### 160. 你未来 3–5 年的技术规划？
**参考回答**：在前端深度上继续精进（架构、性能、复杂交互），同时把系统广度（数据、AI 功能落地、跨端协作）做扎实，往能独立负责一个较大产品域的方向走。我享受"从用户价值出发、用工程把它做扎实、用数据证明它"的完整闭环，希望在更大的舞台上继续做这件事。

## P. 简历“广告 UI 项目”逐项深挖

### 161. 图片广告素材质量预测与图片优化中，你具体负责什么？
**参考回答**：这个功能在广告创建/编辑流程中展示图片与文案质量分数，并提供可执行的优化建议；底层图片生成和重塑能力由 AIGC 团队通过 API 提供，我主要负责前端产品集成，包括请求参数、异步任务轮询、返回结果与素材映射、异常处理，以及图片相关性、候选图片选择和图片重塑场景。为了降低等待感，我把候选结果改成增量 partial render，轮询获得一张就展示一张，并补齐多选、Shimmer 和错误重试状态。我还建立 Fix-it、Tooltip、质量分数、目标素材、AdType、创建/编辑 Flow 等遥测，并修复面板关闭后的焦点恢复与键盘导航，满足 MAS 可访问性要求。

### 162. 第三方广告监测项目的复杂度体现在哪里？
**参考回答**：复杂度来自广告形态、厂商和配置层级的组合。项目覆盖 IAS、DoubleVerify、ISPOT、MOAT，横跨展示、视频和原生广告，并同时支持广告级与广告系列级设置。我负责追踪参数提取、属性映射、竞价策略约束、品牌 ID 校验、厂商去重、Bulk Edit 和 Impression Tracking，还要与 MT 团队统一 API 契约及错误码映射，保证多入口提交行为一致。

### 163. Media Deal / Netflix 项目中你做了哪些创建、校验和下线工作？
**参考回答**：创建和编辑阶段，我参与 Deal 竞价校验、GEO 错误映射、Deal 删除场景，并把被拒地域提前在 UI 拦截，避免提交后再被后端拒绝。GA 后我负责 Netflix / Media Deal 创建入口的 kill-switch 清理，跨 CampaignUI 与 AdsAppUI 两个仓库安全下线创建路径，同时保留已有广告的编辑流，并同步清理 E2E 套件注册、pilot 定义和配置依赖。

### 164. 广告推荐项目覆盖了哪些类型，前端如何落地？
**参考回答**：一类是受众广告推荐，我负责动态权限与配置加载、推荐卡片渲染、文案本地化和单元测试；另一类是视频广告推荐（VID / DIS / IBRMT / CTV）与原生广告推荐（DAO / NAQ），把系统生成或推荐的图片/视频素材直接应用到广告创建和编辑流程。关键是处理推荐资格、配置、素材映射、用户确认和失败状态，而不只是展示一张推荐卡片。

### 165. UI 性能优化用了哪些手段，结果如何证明？
**参考回答**：我先通过生产埋点和 React Profiler 区分 UI 渲染、网络、MT/MDS 后端耗时，再针对关键路径做隐藏面板懒渲染、React 重渲染治理、请求缓存预热与拆分、绕过非必要初始 API，并用分段 marker 持续验证。生产 P95 结果是：广告组编辑页 10s→2.8s（-72%）、广告组创建页 8s→2.7s（-66%）、Native 广告创建页 6s→3.6s（-40%）。

### 166. 你如何负责可访问性、国际化、测试和线上质量？
**参考回答**：可访问性方面，我修复过焦点恢复、`aria-activedescendant`、复选框和键盘导航等问题；国际化方面遵循 `_TL_` 构建期抽取与 `i18n.getString` 规范，保证用户文案可翻译。质量工程方面长期承担 DRI/on-call，处理线上问题以及 RME/SI/CI 测试失败，维护 CI/CD 稳定性，并推动 Enzyme 向现代测试框架迁移。

## 附：高频"深挖"话术准备（面试官常追问）

- **"这个数字是怎么测出来的？"** → 生产环境 perf marker，发布前 3 周 vs 发布后 2 周 P75/P95 平均，按步骤分别对比。
- **"如果让你再优化 20%，你从哪下手？"** → 先看当前 Profiler/生产数据的最大残余段，通常是剩余重组件初始化 + 后端高 P95 接口，UI 侧继续懒化、数据侧推后端。
- **"你怎么确认是你的优化带来的，而不是别的因素？"** → 单点发布 + 前后对比 + 持续多周监控 + 分步骤隔离，尽量控制变量。
- **"这个功能失败了怎么办 / 出了线上事故你怎么处理？"** → 遥测定位→回滚止血→根因→回归测试→复盘。
- **"你写的代码别人接手容易吗？"** → 复用现有模式、不过度抽象、契约类型化、关键处有测试和遥测、遵循团队规范（i18n/a11y）。

> 建议：把 ⭐ 题和 D/E 两节（性能 + AIGC）练到能脱口而出，这两块是你最有区分度的技术资产。
