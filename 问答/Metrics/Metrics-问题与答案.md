## 一、广告度量与 A/B 实验平台

### 1. 你们的广告主指标平台整体架构是怎样的？数据从哪来、到哪去？
**为什么问**：考察你对端到端数据链路的整体理解。
**参考回答**：整体是一个"多源采集 → 加工 → 度量 → 消费"的批处理平台。上游数据源有三类：Kusto（遥测/日志）、Cosmos（结构化事件）、HDFS（大数据）。中间用 Azure Data Factory 编排调度，具体计算跑在 PySpark（MTSpark）和 SCOPE 作业上，先落暂存区（staging）做去重，再合并进主数据文件（TSV/SSTREAM）。下游是 BI 报表、Streamlit 看板和实验分析。整条链路按天/小时触发，凌晨定时跑，同时支持按日期区间手动回填。核心设计目标是**幂等、可审计、多环境一致**。

### 2. 为什么要自己沉淀一个近 40 个模块的 Python 分析库，而不是每个作业各写各的？
**为什么问**：考察抽象能力与工程治理意识。
**参考回答**：因为指标计算有大量重复逻辑：读取按日期分目录的 CSV、跨产品归一化、按分析单元（MSA/CID/AID）算比率、算 p-value 等。如果每个作业各写一套，会出现口径不一致、改一个 bug 要改几十处、新人上手成本高等问题。抽成库之后，指标定义单点收敛，测试可以集中覆盖，作业只需要组合调用。这也让"新增一类 A/B 指标"从改代码变成加一个模块，迭代更快、更可靠。

### 3. 指标计算里"analysis unit（分析单元）"是什么概念？为什么重要？
**为什么问**：这是广告/实验度量的核心概念，考察业务理解。
**参考回答**：分析单元是"按什么粒度去重和计率"的对象，常见有 MSA（账户集）、CID（客户）、AID（账户）。同一个用户可能有多条事件，如果直接对行计数，会因为活跃用户事件多而产生偏差。所以比如"注册转化率"要先按 CID 去重，再算"有转化的 CID 数 / 总 CID 数"。选错分析单元会让指标失真，也会让 A/B 对比不公平，所以我在库里把 `calculate_rate(df, column, analysis_unit)` 做成显式参数，强制每个指标声明自己的粒度。

### 4. "幂等"在你的管道里具体是怎么实现的？
**为什么问**：幂等是数据工程的关键难点。
**参考回答**：核心是"先暂存、再去重合并"。每次作业把当天结果写到带日期的 staging 文件，而不是直接改主表；然后有一步去重合并逻辑，用主键（如账户+日期+指标）把 staging 合并进主表，遇到相同键就覆盖为最新值。这样同一天作业重跑多次，结果都一样，不会重复累加。回填也一样：指定日期区间重跑，只影响那几天的分区。staging 文件本身还充当审计轨迹，出问题能追溯到某天的原始产出。

### 5. 如果某天上游数据延迟或缺失，你的管道怎么处理？
**为什么问**：考察数据质量与容错设计。
**参考回答**：分两层。第一层是**依赖与就绪检查**：作业启动前校验上游数据是否到齐（分区是否存在、行数是否在合理范围），不满足就等待或告警，而不是拿半份数据算出错误指标。第二层是**可回填**：因为管道幂等，等数据补齐后按日期重跑那一天即可自动纠正。我们还有验证作业（Validations）专门做数据质量校验，比如空值率、主键唯一性、指标是否突变，异常就拦截并通知。

### 6. Copilot / AI 助手相关的指标和传统广告指标有什么不同？你怎么度量？
**为什么问**：结合近期 AI 热点，考察你对新场景度量的理解。
**参考回答**：传统广告指标偏"转化漏斗"（曝光→点击→注册→付费），而 AI 助手指标更关注**交互质量与采纳**：比如用户和 Live Agent 的对话轮次、SSR（自助解决率）升级/转人工比例、建议采纳事件、QnA 标注质量等。度量上我要从对话/事件日志里抽取会话级信号，按用户或会话去重，再算采纳率、升级率这类比率，同样套用 A/B 框架看某个模型/提示词改动是否显著提升采纳。难点在于事件语义更复杂、噪声更大，需要更多清洗和标注。

### 7. 你怎么保证 Dev / PME / Prod 三套环境的一致性？
**为什么问**：多环境一致是企业级工程的常见痛点。
**参考回答**：核心是**同一套代码 + 环境参数化**。业务逻辑只有一份，环境差异（数据路径、连接串、视图路径、试点白名单）通过参数或配置注入，SCOPE 里用 `#IF/#DECLARE` 做条件编译，ADF 里用参数化的 pipeline。发布走 CI/CD，从 Dev 逐级 promote 到 PME 再到 Prod，保证跑在 Prod 的就是验证过的那份。这样避免了"测试环境好好的、上线就出问题"的环境漂移。

### 8. 平台每天要处理 TB 级数据，性能瓶颈通常出在哪？你怎么优化？
**为什么问**：考察大数据性能调优经验。
**参考回答**：瓶颈主要在**shuffle（数据重分布）和数据倾斜**。优化手段：一是尽早过滤和裁剪列，减少参与 join/聚合的数据量；二是对大表 join 用合适的分区键、必要时做广播小表；三是处理倾斜键（比如某个大账户占比过高）用加盐或单独处理；四是输出用列式/流式格式并设置合理的分区。SCOPE 侧我会关注每个 stage 的顶点数和数据量，Spark 侧看 stage 的 shuffle read/write 和是否有长尾 task。

### 9. 数据倾斜你具体遇到过吗？怎么定位和解决？
**为什么问**：倾斜是大数据高频难点。
**参考回答**：遇到过。典型现象是一个 stage 里绝大多数 task 秒级完成，个别 task 跑很久甚至 OOM。定位靠看 task 级别的输入数据量分布，找出热点 key——广告场景常见是超大账户或空值 key。解决上：空值/默认值单独分流处理；热点 key 做加盐（key 后拼随机后缀打散，再二次聚合）；或者对倾斜的 join 改成 map-side broadcast。核心思路是"把一个巨大的 key 拆成多个小 key 并行处理"。

### 10. 你们的 A/B 指标有 20 多类，怎么管理和保证口径统一？
**为什么问**：考察指标治理。
**参考回答**：每一类指标在库里是一个独立模块，遵循统一接口：输入实验数据，输出（控制组比率、实验组比率、p-value）。口径统一靠三点：一是共享的底层计率函数，所有指标都调同一个 `calculate_rate`；二是每个指标显式声明分析单元和分子分母定义，代码即文档；三是有单元测试用固定输入验证输出。这样即使不同人维护不同指标，核心计算方式也是一致的。

### 11. `calculate_rate_based_on_multiple_columns` 这种多列计率是什么场景？
**为什么问**：考察你对复杂指标定义的处理。
**参考回答**：有些指标的"成功"条件不是单列，而是多列组合。比如"完成关键设置"要求同时创建了活动、加了预算、加了支付方式。这时分子是"满足多个条件的分析单元数"，我需要先在多列上做 AND 判定生成一个复合标志，再按分析单元去重计率。抽成 `calculate_rate_based_on_multiple_columns` 就是为了复用这种"多条件 → 复合标志 → 计率"的模式，避免每个复合指标重写一遍。

### 12. 滚动窗口指标（如按 N 天滚动算人均日收入）你是怎么实现的？
**为什么问**：时间窗口聚合是分析常见难点。
**参考回答**：我在库里有类似 `calculate_revenue_per_user_per_day_rolling(df, rolling_days, current_datetime)` 的函数。思路是以当前时间为锚点，取过去 N 天的数据，按用户聚合收入，再除以用户在窗口内的活跃天数得到人均日收入。难点在于窗口边界和缺失天的处理：要明确窗口是左闭右开还是闭区间，活跃天要按实际有数据的天算而不是固定 N 天，否则新用户会被低估。

### 13. 新用户 / 专家用户（new expert）这类人群分析你是怎么做的？
**为什么问**：考察分群/cohort 分析能力。
**参考回答**：我有专门的 `new_expert` 和 cohort 预处理模块。核心是先根据首次活跃时间、账户成熟度等把用户打上 cohort 标签，再在每个 cohort 内算指标。这样能回答"新用户的采纳率是不是比老用户低""某功能对专家用户是否更有效"。工程上要注意 cohort 定义的时间点要固定（用注册/首次活跃时间而不是当前时间），否则用户会随时间在 cohort 间漂移，导致对比不可比。

### 14. 你们的指标最终怎么被消费？谁在看、怎么驱动决策？
**为什么问**：考察业务闭环意识。
**参考回答**：三类消费方：一是实验平台，PM/DS 看 A/B 结果的 p-value 决定功能是否全量；二是 BI 报表和 Streamlit 看板，业务看趋势和 Top 客户；三是下游模型/推荐，用采纳指标做特征或效果评估。指标不是终点，而是驱动"要不要推这个建议、要不要上这个功能"的依据，所以口径准确和可信度比花哨更重要。

### 15. 如果一个指标突然异常波动，你怎么排查是真实变化还是数据问题？
**为什么问**：考察问题定位方法论。
**参考回答**：先分层排查。第一步看**是不是数据问题**：上游分区是否完整、行数是否正常、有没有重复或缺失、是否某次 schema 变更导致解析错位。第二步看**是不是口径变化**：最近代码/配置有没有改动，用版本追踪对比。第三步才看**是不是真实业务变化**：拆维度（渠道、地域、账户段）看波动是否集中在某一块，是否和某次发布/活动时间吻合。这套"数据→口径→业务"的顺序能快速缩小范围。

### 16. 你在这个平台里遇到过最难的一个工程问题是什么？
**为什么问**：行为面高频，考察深度。
**参考回答**：最难的是保证大规模管道的**幂等与回填正确性**。早期直接往主表追加，一旦作业失败重跑或上游补数，就会数据翻倍或错乱，排查很痛苦。我重构成"staging + 去重合并"的模式，用主键覆盖而非追加，并把回填做成按日期分区的独立操作。难点在于要梳理清楚每个指标的主键、处理迟到数据、还要兼容历史已有数据的迁移。改完之后作业可以放心重跑，运维成本大幅下降。

### 17. 这个平台的代码质量和可维护性你是怎么保证的？
**为什么问**：考察工程规范。
**参考回答**：几方面：分析逻辑抽成库并加单元测试；用 black/mypy 做格式和类型检查；作业和库通过 CI 发布，版本化（bump patch/minor/major）；关键指标有验证作业兜底。文档上，指标的分子分母和分析单元在代码里显式声明，减少"只有作者知道口径"的情况。

### 18. 如果让你从零重做这个指标平台，你会改进什么？
**为什么问**：考察反思与架构视野。
**参考回答**：几点：一是引入**统一的指标定义层（metric store/语义层）**，让口径以声明式配置存在，而不是散在代码里；二是加强**数据契约和 schema 演进管理**，上游改 schema 能自动检测；三是把批处理里时效要求高的部分往**近实时（流式）**迁移；四是把数据质量校验做成**可观测的 SLA**，异常自动阻断下游并告警。整体方向是从"能跑的管道"升级到"可治理、可观测的数据产品"。

## 二、统计与假设检验

### 19. 你说 A/B 指标内置了假设检验，具体用的什么检验？为什么？
**为什么问**：核心统计能力，必问。
**参考回答**：对"比率型"指标（如转化率、采纳率）用**双样本比例检验（two-proportion z-test）**，比较控制组和实验组两个比例是否有显著差异，输出 p-value。因为这类指标本质是伯努利成功率，两组样本量都很大，正态近似成立，用两比例 z 检验最直接。对连续型指标（如人均收入）则更适合用 t 检验或非参数方法。选择检验方法的关键是看指标的数据类型和分布假设。

### 20. 双样本比例检验的原假设和统计量怎么写？
**为什么问**：考察是否真懂而非背名词。
**参考回答**：原假设 $H_0: p_1 = p_2$，即两组转化率相等；备择是不等（双侧）。统计量用合并比例 $\hat{p}=\frac{x_1+x_2}{n_1+n_2}$，然后
$$ z = \frac{\hat{p}_1 - \hat{p}_2}{\sqrt{\hat{p}(1-\hat{p})(\frac{1}{n_1}+\frac{1}{n_2})}} $$
z 服从近似标准正态，双侧 p-value = $2(1-\Phi(|z|))$。p 小于显著性水平（如 0.05）就拒绝原假设，认为实验有显著影响。

### 21. p-value 到底是什么意思？很多人会误解。
**为什么问**：考察统计素养。
**参考回答**：p-value 是"在原假设成立（两组无差异）的前提下，观测到当前或更极端结果的概率"。它**不是**"实验有效的概率"，也不是"原假设为真的概率"。p 小只说明当前数据在无差异假设下很罕见，所以我们倾向拒绝原假设。我会特别提醒业务：p 显著不等于效应量大，还要看提升的绝对幅度和置信区间，才知道有没有业务价值。

### 22. 多重比较问题你怎么处理？一次实验看几十个指标会怎样？
**为什么问**：这是 A/B 实践的关键陷阱。
**参考回答**：同时看很多指标，即使实际都没差异，也会因为随机性出现假阳性——看 20 个指标，按 0.05 水平期望就有 1 个"显著"。处理办法：一是区分**主指标（primary）和护栏/次要指标**，决策主要看事先定义的主指标；二是对次要指标做多重比较校正，比如 Bonferroni（把阈值除以指标数）或更温和的 Benjamini-Hochberg 控制 FDR。核心是不能"哪个显著就挑哪个讲故事"。

### 23. 样本量不够 / 实验刚开始就看结果，有什么风险？
**为什么问**：考察实验严谨性。
**参考回答**：两个风险。一是**功效不足**：样本太少，真实存在的效应也检验不出来（假阴性）。二是**偷看（peeking）**：实验没到预定时间反复看、一显著就停，会大幅抬高假阳性率，因为你在多个时间点重复检验。正确做法是提前做**功效分析/样本量估算**（给定期望的最小可检测效应 MDE、显著性水平和 power 反推样本量），跑够时间再下结论；如果要中途看，用序贯检验方法而不是普通 z 检验。

### 24. 怎么估算一个实验需要多少样本量？
**为什么问**：考察实验设计能力。
**参考回答**：需要四个输入：基线转化率 $p$、想检测的最小提升幅度（MDE）、显著性水平 $\alpha$（如 0.05）、统计功效 $1-\beta$（如 0.8）。比例检验下每组样本量近似
$$ n \approx \frac{(z_{1-\alpha/2}+z_{1-\beta})^2 \cdot 2\bar{p}(1-\bar{p})}{(\text{MDE})^2} $$
基线率越低、想检测的提升越小，需要的样本越多。实践中我会用这个先估出实验要跑多久，避免样本不足白跑。

### 25. 置信区间和 p-value 的关系？你更看重哪个？
**为什么问**：考察统计表达的成熟度。
**参考回答**：两者一致但视角不同：95% 置信区间不包含 0（对差值）就等价于双侧 p<0.05。我更倾向同时给出**效应量的置信区间**，因为它同时告诉你"方向、幅度、不确定性"，比单个 p-value 更有决策价值。比如"提升 2%±0.3%"比"p=0.01"更能让业务判断值不值得上。

### 26. 实验分流不均匀或有偏，你怎么发现？
**为什么问**：考察 A/B 数据质量意识（SRM）。
**参考回答**：用**样本比率不匹配检测（SRM, Sample Ratio Mismatch）**。如果设计是 50/50，但实际两组样本量偏离过大，用卡方检验一测就会显著，说明分流有问题——可能是埋点丢失、某组加载失败、bot 流量不均。SRM 一旦触发，实验结果基本不可信，要先修分流再看指标，而不是硬解读。

### 27. 什么是辛普森悖论？在广告实验里会怎么坑人？
**为什么问**：考察对聚合陷阱的理解。
**参考回答**：辛普森悖论是"分组里每一组实验都占优，但合并后反而劣势（或反过来）"，通常是因为各组的样本构成/基线不同。广告里比如实验在高价值账户和低价值账户上都提升了转化，但两组账户在实验/对照里的占比不均，合并后就可能看反。应对是分维度看、控制混杂变量，或者用 CUPED、分层分析来消除构成差异的影响。

### 28. CUPED 或方差缩减你了解吗？为什么有用？
**为什么问**：考察进阶 A/B 方法。
**参考回答**：CUPED（用实验前协变量做方差缩减）的思路是：用户的实验前指标（比如上周的花费）能解释一部分实验期指标的方差，把这部分"可预测的波动"扣掉后，指标方差变小，同样样本量下就能更快达到显著。它不改变期望（无偏），但提高了检验功效。对于本身波动大的收入类指标特别有用，能缩短实验时间。

### 29. 比率指标的方差怎么算？为什么不能直接当独立样本？
**为什么问**：考察 delta method / 聚类效应理解。
**参考回答**：当分子分母的单元不一致时（比如指标是"点击/曝光"，但随机化单元是用户），一个用户内的多次曝光是相关的，不能当独立样本，否则会低估方差、假阳性。这时要用 **delta method** 估计比率的方差，或者按随机化单元做**聚类（cluster）标准误**。核心原则是：方差估计的单元要和随机化单元一致。

### 30. 如果 p 值显著但业务方觉得"看起来没变化"，你怎么沟通？
**为什么问**：考察数据沟通能力。
**参考回答**：我会把**统计显著**和**实际显著**分开讲。大样本下极小的差异也会显著，所以要给出效应量和置信区间："提升幅度是 0.2%，虽然统计上显著，但绝对量很小，可能不值得为它付出工程成本。"反过来如果不显著，也要说明是"没检测到差异"而不是"证明没差异"，可能是样本或功效不够。让决策建立在效应量+不确定性+业务成本三者之上。

## 三、大数据引擎：SCOPE / Cosmos

### 31. 先介绍一下 SCOPE 是什么？和 SQL / Spark 有什么区别？
**为什么问**：考察你对所用平台的本质理解。
**参考回答**：SCOPE 是微软内部的大规模数据处理语言和平台，跑在 Cosmos 集群上，语法类似 SQL 加 C#，是一种声明式+可嵌入命令式的混合体。和标准 SQL 比，它支持自定义的 Extractor/Processor/Reducer/Combiner 和 C# UDF，能处理非结构化数据；和 Spark 比，理念相似（都是分布式 DAG 执行），但 SCOPE 是微软自研、与内部存储（结构化流 SSTREAM）深度整合的批处理系统，优化器会把脚本编译成分布式执行计划。

### 32. SCOPE 里 Extractor / Processor / Reducer / Combiner 分别是什么？
**为什么问**：考察对 SCOPE 编程模型的掌握。
**参考回答**：这是 SCOPE 的自定义算子模型。**Extractor** 负责把原始文件（CSV/TSV/自定义格式）解析成行；**Processor** 是逐行处理/转换（类似 map）；**Reducer** 是按 key 分组后对每组做聚合（类似 reduce）；**Combiner** 是自定义的两路 join 逻辑。它们都用 C# 写，能表达标准 SQL 表达不了的复杂逻辑，比如我在视频管道里就写过自定义 Extractor 来解析特殊格式并异步补元数据。

### 33. 你用 ROW_NUMBER() 做去重，具体怎么写、为什么这样去重？
**为什么问**：考察窗口函数与去重模式。
**参考回答**：模式是 `ROW_NUMBER() OVER (PARTITION BY 主键 ORDER BY 时间 DESC)` 给每个主键的多条记录编号，然后 `WHERE rn == 1` 只保留最新一条。用在"同一个账户/活动有多条快照，只要最新状态"的场景。相比 `GROUP BY` 只能取聚合值，窗口函数能保留整行且精确控制"最新"的定义（按更新时间、版本号等排序），这对状态型数据去重很关键。

### 34. ANTISEMIJOIN / LEFT ANTISEMIJOIN 是什么？你用在哪？
**为什么问**：考察集合运算与 SCOPE 特性。
**参考回答**：ANTISEMIJOIN 是"反半连接"，返回左表中在右表**找不到匹配**的行，语义上等价于 `WHERE NOT EXISTS`，但执行更高效，因为不产生笛卡尔膨胀、只判断存在性。我用它做集合差：比如"找出所有没有有效视频素材的广告"——用全部广告 ANTISEMIJOIN 有效视频集合，剩下的就是缺视频的。相比 `LEFT JOIN ... WHERE right IS NULL`，antisemijoin 语义更清晰、优化器也更好处理。

### 35. 什么是特征掩码（feature mask）？位运算怎么用？为什么不用多个布尔列？
**为什么问**：这是你项目里的亮点技术点。
**参考回答**：特征掩码是把很多布尔属性压进一个整型的不同比特位，比如第 23 位表示"有视频素材"、第 24 位表示"有展示素材"。判断某属性就用位运算：`(FeatureMask & (1 << 23)) != 0`。好处是**存储紧凑、扩展方便**（加一种属性只占一个比特，不用改表结构加列），在海量数据下能省大量空间和 IO。代价是可读性差，所以我会用命名常量把比特位含义封装起来，避免魔法数字。

### 36. 位运算判定广告类型时，怎么保证不出错？
**为什么问**：考察细节严谨性。
**参考回答**：几点：一是把比特位定义集中成命名常量（如 `VideoAssetBit = 1<<23`），杜绝散落的魔法数字；二是明确"与（&）判存在、或（|）做合并、异或做翻转"的语义，判存在时一定和 0 比较而不是和掩码本身比（避免多位混淆）；三是对关键组合写测试用例覆盖。位运算最容易错的是运算符优先级，所以我会显式加括号。

### 37. SSTREAM 是什么？为什么用它而不是普通文件？还有你提到的 stream expiry。
**为什么问**：考察 SCOPE 存储格式理解。
**参考回答**：SSTREAM 是 SCOPE 的结构化流存储格式，自带 schema、支持按列裁剪、可指定分区和排序（clustering），读写都比纯文本高效，适合作为作业间传递的中间/结果数据。stream expiry 是给流设置过期时间（比如 10 天），到期自动清理，用来管理临时数据的生命周期，避免中间结果无限堆积占用集群存储。对每天产生的临时数据设过期是很实用的成本控制手段。

### 38. 多阶段级联 JOIN 的富化管道，你怎么保证正确又高效？
**为什么问**：考察复杂 SCOPE 脚本设计。
**参考回答**：我的富化管道通常是"基础表 → 逐步 LEFT JOIN 补充维度（转化数、账户段、试点状态、目标信息…）"。正确性上，每一步都用 LEFT JOIN 保证主表行不因为缺维度而丢失，并用 `?? 0` 之类做空值兜底。效率上，尽早过滤、只 join 需要的列、把最能缩小数据量的过滤放前面、大表 join 选好分区键。我还会把中间结果落成命名清晰的流，方便调试和复用，而不是写成一个巨大的嵌套查询。

### 39. 试点（pilot）功能的账户/客户双层追踪是怎么回事？
**为什么问**：考察业务建模能力。
**参考回答**：一个功能可能在**账户级**开白名单，也可能在**客户级**开（客户下所有账户都生效）。所以判断"某账户是否在试点"要同时查账户级和客户级两张表，用 UNION 合并资格。难点是层级继承：客户级开了，其下账户即使没单独开也算命中。我在脚本里会先分别算出两级命中集合，再合并去重，最后再和实际使用情况关联，区分"有资格"和"真正用了"。

### 40. C2C Master View、UnifiedLayer 这些视图在你们体系里是什么角色？
**为什么问**：考察对内部数据资产的理解。
**参考回答**：它们是团队维护的**中心化数据视图/数仓层**。C2C Master View 提供账户、活动、广告、素材等实体的元数据快照（有 snapshot 和 delta 两类视图）；UnifiedLayerDemand/UnifiedLayerPerf 提供投放需求和效果数据。作用是把底层复杂的原始表封装成稳定、统一的接口，业务脚本直接查视图而不用关心底层存储细节。这也是为什么我的脚本大多以查这些视图开头。

### 41. snapshot 视图和 delta 视图有什么区别？分别什么时候用？
**为什么问**：考察增量处理理解。
**参考回答**：snapshot 是某时刻的全量状态快照，适合"我要当前所有账户的最新属性"；delta 是变更增量，适合"我只关心这段时间发生了变化的记录"。全量重算用 snapshot 简单可靠但成本高；增量/近实时更新用 delta 省资源但要处理好乱序和补偿。我会根据作业是"重算型"还是"增量型"来选，比如每日全量指标用 snapshot，变更检测类用 delta。

### 42. 你怎么调试一个跑得很慢的 SCOPE 作业？
**为什么问**：考察实操调优能力。
**参考回答**：先看作业的执行图，SCOPE 会把脚本拆成多个 stage（顶点集合）。我关注：哪个 stage 数据量/耗时最大、有没有数据倾斜（某些顶点远慢于其他）、有没有不必要的全量 shuffle。常见优化是把过滤和列裁剪提前、减少 join 的数据量、对倾斜 key 特殊处理、调整分区数。也会检查是不是自定义 Extractor/Processor 里有低效的逐行操作。改完对比 stage 耗时验证效果。

### 43. 自定义 C# Extractor 里做异步 IO（比如去 Blob 拉元数据）有什么坑？
**为什么问**：这是你视频管道的真实难点。
**参考回答**：坑在于 SCOPE 顶点是大规模并发跑的，如果每行都同步阻塞去拉远程数据，吞吐会很差；但在分布式算子里滥用异步/并发又容易踩线程和资源限制。我的做法是**批量+连接复用+缓存**：按 Host Account 缓存 Blob 连接串避免重复建连，控制并发度，能批处理就批处理，并对失败做重试和降级（失败行落错误流不阻断整体）。还要注意超时设置，避免个别慢请求拖垮整个顶点。

### 44. 数据里有大量空值和类型转换，你怎么稳健处理？
**为什么问**：考察数据清洗严谨性。
**参考回答**：原则是"边界处显式处理，不让脏数据往下传"。可空类型用 `?? 默认值` 兜底；类型转换（string→int、时间解析）用安全转换并对失败记录单独处理，而不是让整个作业挂掉；关键字段做校验（范围、格式）。我倾向在 Extractor/预处理阶段就把类型和空值规整好，下游逻辑就能假设数据是干净的，减少到处写防御代码。

### 45. 你写过的最复杂的一个 SCOPE 脚本大概是什么样？难在哪？
**为什么问**：考察深度。
**参考回答**：比较复杂的是广告优化机会的度量脚本，比如 IBR/DAO 这类。它要：从多个视图取活动/广告组/广告/素材，按生命周期状态和特征掩码过滤，做多级 join 关联素材与广告组，判定"是否需要优化"，再按时间窗口算采纳和收入，最后用 Bond 序列化输出并生成 manifest。难点在于业务规则多、状态码和特征位含义复杂、还要多环境（SI/PROD）和多 tactic 参数化复用，所以我用模块化 + 条件编译把公共逻辑抽出来，避免每个 tactic 复制一份。

### 46. SCOPE 这种内部技术栈，你觉得能力怎么迁移到通用大数据岗位？
**为什么问**：换工作时面试官真实关心。
**参考回答**：SCOPE 的底层理念和 Spark/Hive/Flink 是相通的：分布式 DAG、shuffle、分区、倾斜、UDF、窗口函数、join 优化，这些是共通的大数据思维。我用 SCOPE 解决的去重、幂等、倾斜、级联富化问题，换到 Spark 就是 DataFrame/SQL + 相同的优化思路。而且我本身也在 AdvertiserMetrics 里用 PySpark，所以能力是可迁移的，只是 API 和语法换一套。

## 四、PySpark / ADF / Databricks / CI-CD

### 47. PySpark 里 DataFrame 和 RDD 你更常用哪个？为什么？
**为什么问**：考察 Spark 基础与性能意识。
**参考回答**：绝大多数用 DataFrame。因为 DataFrame 有 Catalyst 优化器和 Tungsten 内存管理，能做谓词下推、列裁剪、代码生成，性能通常远好于手写 RDD；而且 API 更接近 SQL，可读性好。只有极少数需要极细粒度控制、无法用内置算子表达的逻辑，我才会退回 RDD 或用 UDF。原则是"能用内置表达式就不写 UDF，能用 DataFrame 就不用 RDD"。

### 48. Spark 里 UDF 有什么性能问题？怎么优化？
**为什么问**：常见性能陷阱。
**参考回答**：Python UDF 有序列化开销和跨进程（JVM↔Python）通信开销，还会阻断 Catalyst 优化，成为瓶颈。优化办法：优先用 Spark 内置函数（`F.when`、`F.regexp_extract` 等）替代 UDF；实在要写就用 **Pandas UDF（向量化 UDF）**，它基于 Arrow 批量传输，比逐行 UDF 快很多；或者把逻辑下推到 SQL 表达式。我会先问自己"这个 UDF 能不能用内置函数拼出来"。

### 49. 宽依赖和窄依赖、shuffle 的代价你怎么理解？
**为什么问**：Spark 执行模型核心。
**参考回答**：窄依赖是每个父分区最多被一个子分区用（map、filter），能在同一节点流水线执行，没有网络传输；宽依赖（groupBy、join、repartition）需要跨节点重分布数据，也就是 shuffle，涉及磁盘写和网络传输，是最贵的操作，也是 stage 的分界。优化的核心思路就是**减少 shuffle 的次数和数据量**：提前过滤、广播小表、复用已分区的数据、避免不必要的 repartition。

### 50. 什么时候用 broadcast join？有什么风险？
**为什么问**：join 优化高频题。
**参考回答**：当 join 的一侧足够小（能放进 executor 内存）时，把小表广播到每个节点，大表不用 shuffle，直接本地 join，能极大提速。风险是如果"小表"其实不小，广播会撑爆 driver 或 executor 内存导致 OOM。所以要控制广播阈值，只对确实小的维表用；不确定大小时让 Spark 的自适应执行（AQE）自动决定更稳妥。

### 51. 你怎么处理 PySpark 作业的 OOM？
**为什么问**：实战运维能力。
**参考回答**：先定位是 driver 还是 executor OOM。driver OOM 常因为 `collect()` 把大数据拉回本地或广播了大表——避免 collect、控制广播大小。executor OOM 常因为数据倾斜、分区过大或 shuffle 数据过多——增加分区数、处理倾斜 key、调 executor 内存和内存分数、减少一次性 cache 的数据。也会检查是不是 cache 了不该 cache 的中间结果占内存。

### 52. ADF 里你是怎么编排这些作业的？触发和依赖怎么管理？
**为什么问**：考察调度编排经验。
**参考回答**：用 ADF 的 pipeline 把抽取、去重、合并等步骤串成有依赖的活动，按 schedule trigger 定时（比如凌晨 2 点）跑，同时支持带参数的手动触发做回填（传日期区间）。步骤间有依赖和成功/失败分支，失败会告警。pipeline 本身参数化，同一套定义通过参数适配不同环境和日期，避免为每天/每环境复制 pipeline。

### 53. 回填（backfill）在 ADF 里怎么实现？要注意什么？
**为什么问**：延续幂等主题。
**参考回答**：回填就是用日期区间参数触发同一条 pipeline，逐日或批量重跑历史分区。前提是作业幂等（前面讲的 staging+去重），否则回填会污染数据。要注意：控制并发避免一次回填太多天把集群压垮；回填顺序（有些指标依赖前一天状态要按序）；以及回填完做数据校验确认结果正确。

### 54. Databricks 在你们流程里承担什么？和 ADF 怎么配合？
**为什么问**：考察工具分工理解。
**参考回答**：Databricks 提供托管的 Spark 计算和 notebook 环境，实际的 PySpark 计算跑在上面；ADF 负责编排和调度，触发 Databricks 上的 job/notebook。CI/CD 会把 notebook/包部署到 Databricks。这样职责清晰：ADF 管"什么时候、按什么依赖跑"，Databricks 管"计算怎么跑"。

### 55. 你们的 CI/CD 具体做了哪些事？
**为什么问**：考察工程化成熟度。
**参考回答**：用 Azure DevOps pipeline：代码提交后做版本号自增（patch/minor/major），构建 Python 包发布到 Azure Artifacts feed，构建 Docker 镜像推到 ACR，部署 Databricks notebook，并支持从 Dev→PME→Prod 的多环境 promote。好处是发布可重复、可回滚，Prod 跑的一定是验证过的构建产物，避免手工部署的漂移和遗漏。

### 56. 为什么数据作业还要打 Docker 镜像？
**为什么问**：考察容器化理解。
**参考回答**：为了**环境一致性和可复现**。Python 依赖版本、系统库如果各环境不一致，会出现"本地能跑线上报错"。把运行环境固化进镜像，Dev/PME/Prod 用同一个镜像，就消除了依赖漂移。镜像也方便版本管理和回滚——出问题直接回退到上一个可用镜像 tag。

### 57. 数据管道的监控和告警你们怎么做？
**为什么问**：考察可观测性。
**参考回答**：几层：作业级有成功/失败状态和运行时长监控，失败即告警；数据级有验证作业检查行数、空值率、主键唯一性、指标是否突变，异常拦截并通知；还有 manifest/审计文件记录每次产出。关键是不能等业务发现指标不对才知道，而是让管道自己"体检"，异常时主动阻断下游并报警。

### 58. 你怎么保证 PySpark 计算结果和 SCOPE 计算结果一致？
**为什么问**：多引擎并存时的真实问题。
**参考回答**：核心是**口径对齐 + 交叉校验**。同一个指标不管用哪个引擎，分子分母定义、分析单元、过滤条件必须完全一致，这靠把口径写清楚并 code review。上线新实现时会做**对拍**：用同一份历史数据两边各跑一遍，比对结果差异，定位不一致的根因（常见是空值处理、去重顺序、时间边界不同）。对齐后再切换。

### 59. 处理时间和时区在你们的日级作业里怎么统一？
**为什么问**：时间处理是隐形坑。
**参考回答**：全链路统一到一个基准时区（我们按 PT 定义"业务日"），所有日期切分、窗口都基于这个基准，避免有的用 UTC 有的用本地时间导致跨天错位。解析时间戳要明确来源时区并显式转换，边界统一约定（左闭右开）。迟到数据用事件时间归到正确的业务日，而不是按处理时间。

### 60. 如果一个每日作业越跑越慢（数据量增长），你怎么应对？
**为什么问**：考察容量规划。
**参考回答**：先分析慢在哪：是全量重算导致数据量线性增长，还是某步倾斜/资源不足。应对：把"全量重算"改成"增量处理"只算变化部分；对历史数据做归档/冷热分层，只在热数据上算；调整并行度和资源；必要时对输出做分区裁剪。长期看要做容量规划，预测增长提前扩资源或重构算法复杂度。

## 五、广告机会度量与推荐、UCM 打分、Bond

### 61. 广告优化机会（tactic）的"采纳度量"到底在度量什么？难点在哪？
**为什么问**：考察归因与度量设计。
**参考回答**：度量的是"我们给广告主推了某个优化建议后，他到底采纳了没有、采纳后带来多少增量效果/收入"。难点有三：一是**归因**——广告主的改动是因为我们的推荐还是自发的，要有对照或时间窗口逻辑判定；二是**时序**——推荐和采纳有时间差，要定义合理的观察窗口；三是**状态快照**——要留采纳历史快照才能回溯"某天的采纳状态是什么"。我用采纳历史流 + 收入归因来回答这些。

### 62. UCM 的多因子打分（RawScore/NormalizedScore/MPI/STR）是怎么设计的？
**为什么问**：考察打分/排序系统设计。
**参考回答**：RawScore 是基于原始信号（预估花费、点击、曝光等）算出的原始分；NormalizedScore 是把 RawScore 归一化到可比区间，消除不同 tactic/账户量级差异，让不同机会能横向排序；MPI、STR 是从不同业务维度（市场表现、强度）刻画机会质量的因子。最终排序综合这些因子，还支持可配置的屏蔽规则过滤掉不该推的机会。设计核心是"可比、可解释、可配置"。

### 63. 为什么要归一化？不归一化直接用原始分排序会怎样？
**为什么问**：考察排序公平性理解。
**参考回答**：不同 tactic 或账户的原始信号量级差别巨大，比如大账户的预估花费天然比小账户高几个数量级，直接用 RawScore 排序会让大账户永远排前面，中小账户的好机会被埋没。归一化把分数拉到可比尺度（比如按分布做标准化或分位数映射），让排序反映的是"机会的相对价值"而不是"账户的绝对体量"，这样推荐才公平有效。

### 64. Bond 序列化是什么？为什么用它而不是 JSON？
**为什么问**：考察序列化选型。
**参考回答**：Bond 是微软开源的跨语言结构化数据序列化框架，类似 Protobuf/Thrift。相比 JSON，Bond 是**二进制、带 schema、更紧凑、序列化/反序列化更快**，在海量数据跨系统交换时能显著省空间和 CPU。广告度量数据量大、还要在 SCOPE 和下游系统间传，用 Bond 比文本格式高效得多。代价是不可读、需要 schema 定义，但这些在生产管道里是可接受的。

### 65. Bond 的 schema 演进怎么做？加字段会不会破坏兼容？
**为什么问**：考察序列化实战细节。
**参考回答**：Bond 和 Protobuf 类似，字段有编号，遵循前后兼容规则：**新增可选字段**、不复用/不改已有字段编号，老代码遇到不认识的新字段会忽略，新代码遇到老数据缺的字段用默认值，这样能平滑演进。要避免的是改字段类型、复用旧编号、把可选改成必需，这些会破坏兼容。上线新 schema 前我会确认读写两端的兼容策略。

### 66. 视频加素材推荐里 P0/P1/P2 优先级是怎么定的？
**为什么问**：考察业务规则设计。
**参考回答**：按"业务影响 + 采纳可能性"分层。P0 是最高价值/最明确的，比如从 Google 导入但视频素材导入失败的广告，或视频挂载失败的——这些是明确缺口且影响大；P1 是"广告组里只有原生广告、没有视频素材"；P2 是"广告组只有展示广告"。越靠前越优先推。分层的意义是让有限的推荐位/运营资源先覆盖收益最高的机会。

### 67. 怎么从海量广告里高效筛出"缺视频"的广告？
**为什么问**：考察集合运算落地。
**参考回答**：核心是集合差。先用特征掩码位运算和素材关联，构造出"已有有效视频素材的广告集合"，再用全部候选广告 **ANTISEMIJOIN** 这个集合，剩下的就是缺视频的。相比对每条广告逐个查有没有视频（会有大量重复扫描），用反半连接在分布式下一次性算出差集，效率高很多。再叠加生命周期状态、试点资格等过滤，得到最终推荐候选。

### 68. 多种 tactic（DIS/VID/DAO/NAQ/CTV/IBR）逻辑相似，你怎么避免重复代码？
**为什么问**：考察抽象与复用。
**参考回答**：用**模块化 + 参数化 + 条件编译**。把公共的度量骨架（取数、过滤、窗口聚合、序列化输出）抽成共享 module，各 tactic 通过参数（TacticCode、OpportunityTypeId、特征位、时间窗口）注入差异，用 `#IF/#DECLARE` 处理环境和 tactic 分支。这样加一个新 tactic 主要是配参数而不是复制整份脚本，维护一处逻辑就能覆盖多个 tactic。

### 69. 采纳历史快照为什么要存全量快照？增量不行吗？
**为什么问**：考察数据建模权衡。
**参考回答**：因为很多分析要回答"某个历史时点的采纳状态是什么"，如果只存增量变更，回溯任意时点要重放全部历史，代价高且易错。存每日全量快照（如 `AdoptionHistory_New_{date}.ss`）能直接按日期取到那天的完整状态，查询简单可靠。代价是存储更大，所以配合 stream expiry 控制保留窗口，在可回溯性和成本间平衡。

### 70. 收入归因你是怎么算的？怎么避免高估推荐的价值？
**为什么问**：考察归因严谨性。
**参考回答**：归因要小心把"本来就会发生的收入"算到推荐头上。做法上要有对照基准或时间窗口逻辑：比较采纳前后、或采纳组与相似未采纳组的收入差，而不是把采纳账户的全部收入都归给推荐。还要控制混杂（季节、账户体量）。我倾向保守口径，宁可低估也不夸大，因为这些数字会影响业务对功能价值的判断。

### 71. 打分系统怎么做版本管理和 A/B？
**为什么问**：考察模型/规则迭代。
**参考回答**：打分逻辑和数据都带版本号（model version / data version），输出里记录用了哪个版本，方便回溯和对比。迭代新打分策略时，用 A/B：一部分流量用新打分、一部分用旧的，比较下游采纳率、收入等指标是否显著提升，再决定全量。可配置的屏蔽规则也让我们能快速关掉表现差的机会类型而不用发版。

### 72. 如果推荐打分上线后采纳率反而下降，你怎么排查？
**为什么问**：考察问题定位。
**参考回答**：先确认是不是**度量口径变了**（采纳事件定义、归因窗口），排除假象。再看**打分变化**：新版本是不是把低质机会排前了，拆维度看哪些 tactic/账户段掉得多。也看**外部因素**：是不是同期有别的发布或季节影响。用 A/B 对照是最干净的判断方式——如果对照组正常、实验组掉，就基本能归因到新打分，然后回滚或修正因子权重。

### 73. 这套度量/推荐系统的数据质量怎么保证？
**为什么问**：考察端到端质量意识。
**参考回答**：多环节校验：输入侧校验视图数据完整性；计算侧对关键中间结果做行数和分布检查；输出侧生成 manifest 记录产出清单用于验证。还有专门的测试脚本（比如 TestDAOTactic）用构造的测试数据验证复杂业务逻辑（尺寸匹配、多格式检测等）是否正确。核心是"复杂业务规则一定要有可重复的测试兜底"。

### 74. 你会怎么把这套基于规则的推荐升级成机器学习推荐？
**为什么问**：考察成长性和 ML 视野。
**参考回答**：现在的打分很多是专家规则和线性因子。升级路径：先把规则产出的机会和真实采纳/收入作为标注数据积累起来（其实 AssetPerfPrediction 已经在做这类数据准备和 train/test 切分），然后训练一个排序/CTR 类模型（如 GBDT 或深度排序）预测"采纳概率×预期收益"，用它替代或融合现有因子。上线仍用 A/B 验证。关键是先有高质量标注和特征，再谈模型。

## 六、C# 高性能数据工具与 Azure Blob 视频管道

### 75. 视频元数据补全工具解决什么问题？为什么要单独做工具？
**为什么问**：考察问题背景理解。
**参考回答**：视频资产表里有些元数据（码率、时长、分辨率、格式）在数据库里是缺失的，必须去 Azure Blob 读真实视频文件、解析媒体头才能拿到。数据量是百万级，还要反复跑。用 SCOPE 直接做不够灵活（涉及媒体解析和大量 Blob IO），所以我用 C# 写了专门的高性能工具，专注把"读 TSV → 拉 Blob 元数据 → 写回"这条链路做到快且稳。

### 76. 你说用"表达式树动态生成反序列化器"，能具体讲讲吗？
**为什么问**：这是硬核技术点，考察是否真懂。
**参考回答**：TSV 每行要按 DSV schema 映射成强类型对象。如果用反射逐字段 set，每行都反射会很慢。我用 `System.Linq.Expressions` 在**运行时按 schema 构建一棵表达式树**，编译成一个 `Func<CsvStructuredDataReader, T>` 委托，把"读第几列→转类型→赋给哪个属性"的逻辑编译成等价于手写的强类型代码，只在启动时编译一次，之后每行调用都是原生委托调用，没有反射开销。这样既保留了 schema 驱动的灵活性，又拿到了接近硬编码的吞吐。

### 77. 为什么不用反射或者现成的 CSV 库？
**为什么问**：考察选型权衡。
**参考回答**：反射每行开销大，百万级下累积很可观；通用 CSV 库很多也是基于反射或没有针对我们的 DSV schema 和性能场景优化。自己用表达式树生成反序列化器，能针对固定 schema 生成最优代码，还能集成我们的类型转换和错误处理逻辑。这是典型的"用一次性编译成本换每行运行时性能"的权衡，在高吞吐批处理里很值。

### 78. 按 Host Account 缓存连接串是解决什么问题？
**为什么问**：考察连接管理。
**参考回答**：不同 Host Account 的视频在不同的存储账户里，需要不同连接串。如果每个视频都重新构造连接/客户端，会有大量重复初始化开销。我用一个按 Host Account ID 索引的字典缓存连接串/客户端，同一账户的视频复用同一个客户端。这样把"每视频建连"降到"每账户建连一次"，在批量处理时显著减少开销。

### 79. 异步批量拉元数据时，你怎么控制并发、避免打爆 Blob 或本地资源？
**为什么问**：考察异步与限流。
**参考回答**：不能无限制地并发发请求，否则会触发存储限流或本地线程/内存耗尽。我会控制并发度（比如设定并行线程数为 2 这种保守值），配合 BlobRequestOptions 调超时（如 3600s）、并行度和分块阈值（64MB）。用异步 IO 让等待网络时不阻塞线程，但用信号量或分批来限制同时在飞的请求数。核心是"在吞吐和稳定性之间找平衡点"，并对限流错误做退避重试。

### 80. 处理失败的行你怎么办？会不会因为个别坏数据整个作业失败？
**为什么问**：考察容错设计。
**参考回答**：不会。我把主流程和错误处理分开：能正常处理的写主输出流，解析失败或拉不到元数据的行封装成 VideoError 写到**独立的错误流**，记录原因。这样整个作业不会因为个别坏数据中断，还能事后对错误流单独分析和补救。这是批处理容错的基本原则——"坏样本隔离，不阻断主流程"。

### 81. 视频媒体解析（码率、时长、格式）具体怎么做的？
**为什么问**：考察媒体处理细节。
**参考回答**：用内部的 VideoParser 库读视频流的头信息/元数据，从中解析出码率、时长、分辨率、格式等。关键是只读必要的头部而不是下载整份大文件——媒体容器的元数据通常在文件头/特定 box 里，读少量字节就能拿到，避免为了拿元数据把几百 MB 视频全下下来。对拿不到或格式异常的做兜底。

### 82. 你还用过 MIME 类型检测，为什么不能只看文件扩展名？
**为什么问**：考察健壮性意识（对应 TestHeyRedMimeType）。
**参考回答**：扩展名可以被伪造或缺失，不可靠。真正判断文件类型要看**文件内容的魔数（magic bytes）/二进制特征**。我用 HeyRed.Mime 这类库从文件流的字节特征识别真实 MIME 类型，能正确区分 .ts、.webm、.mp4 等，即使扩展名错了也能识别。这在处理用户上传的、来源不可控的视频时尤其重要。

### 83. SAS URL（共享访问签名）你是怎么用的？"无限期 SAS"有什么风险？
**为什么问**：考察 Azure 存储安全（对应 TestInfiniteSASUrl）。
**参考回答**：SAS 是给 Blob 授予有时限、有权限范围（读/列举等）的临时访问令牌，不用暴露账户密钥。我测试过 SAS URL 的有效期和权限约束。"无限期/超长期 SAS"的风险是**一旦泄露就长期可被滥用且难以撤销**，所以安全实践是尽量短时效、最小权限，或用 stored access policy 便于统一吊销，而不是签发永久 URL。

### 84. 这个工具的吞吐大概是什么量级？瓶颈在哪？
**为什么问**：考察对性能的量化认知。
**参考回答**：处理规模是百万级视频。瓶颈主要在**网络 IO（拉 Blob）**而不是 CPU，因为解析本身很快、反序列化又已经用表达式树优化过。所以优化重点全在 IO：连接复用、异步并发、只读必要字节、批处理、合理超时和重试。写出侧我用带大缓冲（如 2MB）的 CsvWriter 减少 IO 次数。整体是"IO 密集型作业"，优化思路和 CPU 密集型不同。

### 85. 为什么用 CommandLineParser 做成命令行工具？
**为什么问**：考察工程易用性。
**参考回答**：做成 CLI 工具方便参数化和自动化调度：连接串、输入输出路径、环境（test/prod）都通过命令行参数传，不用改代码重编译。CommandLineParser 帮我把参数解析、校验、帮助文档标准化。这样工具既能人工手跑，也能被管道/脚本调用，复用性好。

### 86. 老旧视频识别（OldVideoScope 那类）业务上是要干嘛？
**为什么问**：考察业务价值理解。
**参考回答**：是做**存量视频资产的治理**：找出创建时间早、且源元数据缺失（码率/时长/格式为空）、或生命周期已删除的视频，统计数量、补全元数据或清理。价值在于数据质量和存储成本——大量陈旧、无效或元数据不全的视频既占存储又影响下游分析准确性。我会做计数统计、补元数据、以及 C2C 更新后的校验，确认治理效果。

### 87. C# 里 `async/await` 和 `Task` 你怎么正确用？有没有踩过坑？
**为什么问**：考察异步编程功底。
**参考回答**：坑主要有：一是 `.Result`/`.Wait()` 在同步上下文里可能死锁，库代码里我会尽量全程 async 或明确在无同步上下文的环境用；二是不要 `async void`（除事件处理），异常无法被捕获；三是大量并发 Task 要用信号量或 `Parallel`/分批限流，不能无脑 `Task.WhenAll` 上百万个。批处理场景我倾向"分批 + 限并发 + 每批 await"，兼顾吞吐和资源可控。

### 88. 这类高性能工具你怎么测试？
**为什么问**：考察测试意识。
**参考回答**：分几层：反序列化器用构造的 TSV 样本验证各类型/空值/异常行的解析是否正确；Blob 交互用小规模真实数据或 mock 验证连接复用和错误落流；整体做小批量端到端跑，比对输出行数和错误行数。性能上用有代表性的数据量做压测，观察吞吐和资源占用，确认没有内存泄漏或句柄泄漏。

### 89. 如果让这个工具支持水平扩展（多机并行），你会怎么设计？
**为什么问**：考察分布式设计延展。
**参考回答**：把输入按 Host Account 或视频 ID 哈希**分片**，每个 worker 处理一个分片，天然并行且无共享状态（连接缓存本来就是按账户的）。用一个协调层（队列或分片清单）分配任务，每个 worker 独立输出结果和错误流，最后合并。要处理好幂等（分片可重跑）和失败重试。其实这正是 SCOPE 分布式做的事——我在单机工具里也是按账户分片的思路，扩展到多机是自然的。

### 90. 单机 C# 工具 vs 直接用 SCOPE/Spark 做，你怎么选？
**为什么问**：考察技术选型判断。
**参考回答**：看瓶颈和逻辑复杂度。如果是纯粹的分布式聚合/join，SCOPE/Spark 更合适，能自动并行。但如果涉及复杂的媒体解析、精细的异步 Blob IO 控制、或需要用成熟 .NET 库，单机（或可分片的）C# 工具更灵活可控。视频元数据补全就是后者：媒体解析和 IO 控制在 C# 里更好写。选型原则是"让工具匹配问题的本质瓶颈"。

## 七、Deal ETL 与 Xandr / 程序化交易集成

### 91. 先解释一下什么是程序化交易的 Deal？你的 ETL 在中间做什么？
**为什么问**：考察业务背景。
**参考回答**：Deal 是程序化广告里买卖双方约定的交易（比如 PMP 私有市场），规定了库存、底价、定向等条件。像 Netflix 这样的媒体方通过 Xandr（原 AppNexus）平台发布 Deal，微软广告要把这些外部 Deal 接进来变成平台内可用的对象。我的 ETL 就是"读外部 CSV/JSON 的 Deal → 转换/校验/富化 → 输出成微软广告 SDK 的 Deal 对象"，中间要做货币映射、地域映射、定向约束构建等。

### 92. 外部 Deal 转成内部 SDK 对象，最麻烦的转换是什么？
**为什么问**：考察 ETL 细节。
**参考回答**：麻烦的是**定向约束的构建和校验**。比如把"地域名字"映射成内部 location ID（要查映射表，还要拦截违禁地域如某些国家）；把年龄段字符串（如 "50+"）解析成年龄区间数组；性别字符串转枚举；视频质量、时长转成对应约束对象。数据源格式还不统一（CSV 和 JSON 结构不一样），要写健壮的解析和大量边界处理。我用自定义异常（如 ExtractTargetInfoException）把不同失败类型区分开，便于定位。

### 93. 增量合并（merge）和差异分析（diff）是怎么做的？
**为什么问**：考察增量/对账逻辑。
**参考回答**：merge 是把本次 Deal 和上一版合并，保留仍有效的、更新变化的。diff 分析是对比新旧集合：用集合运算算出**新增的 Deal（new.Except(old)）**和**消失的 Deal（old 里不在 new 的）**，还检测重名冲突。实现上用 HashSet/Dictionary 做 O(1) 查找和集合差，输出 added/removed/duplicate 报告供人工核对。这样每次接入都能清楚知道"这次变了什么"，避免盲目覆盖。

### 94. 重名检测为什么重要？怎么处理冲突？
**为什么问**：考察数据一致性。
**参考回答**：Deal 名字如果重复，会导致下游引用歧义、覆盖错误的 Deal。所以我在转换时收集所有名字，检测重复并报告，而不是静默让后者覆盖前者。处理策略取决于业务：可以拒绝重名、加后缀区分、或人工介入确认。关键是**显式暴露冲突**而不是让它悄悄产生脏数据。

### 95. 对接 Xandr 库存 API 时遇到哪些工程问题？
**为什么问**：考察外部 API 集成经验。
**参考回答**：几个：一是**认证**，要带 Bearer token；二是**分页**，库存 Deal 很多，按 100 一页翻页拉全量；三是**压缩**，库存接口返回 GZip，要解压流；四是**复杂嵌套 JSON**，Deal 里有卖家、可见性画像（年龄/性别/城市/邮编/题材曝光）等多层结构，要写健壮的反序列化模型（还处理了自定义日期格式和可空字段）；五是**筛选**，按卖家/地域过滤出目标 Deal（如 Netflix 专属、CTV 网络、排除某些国家）。

### 96. 你做了 100 并发压测，目的是什么？发现了什么？
**为什么问**：考察性能/稳定性测试意识。
**参考回答**：目的是验证在生产级并发下 Xandr API 的**稳定性和限流边界**，以及我们的客户端在高并发下会不会有连接耗尽、超时、错误率上升等问题。压测能提前暴露"单请求没问题、并发就崩"的隐患，帮我确定合理的并发度、超时和重试策略，避免上线后打爆对方 API 或被限流。

### 97. HttpClient 高并发使用有什么最佳实践？
**为什么问**：C# 网络编程常见坑。
**参考回答**：最重要的是**复用 HttpClient 实例**（或用 IHttpClientFactory），不要每次请求 new 一个——那会耗尽 socket 导致 SocketException。其次配置合理的超时、连接池上限，处理好取消 token；对可重试的错误（限流 429、瞬时 5xx）做指数退避重试；解析响应流时注意 GZip 解压和大响应的流式处理避免一次性读入内存。

### 98. Deal 数据里的违禁地域校验，为什么要硬编码？有没有更好的方式？
**为什么问**：考察可维护性反思。
**参考回答**：当时用硬编码映射表快速实现了违禁地域（如某些国家）的拦截，简单直接。但更好的方式是把这类业务规则**外置成配置/规则表**，改规则不用改代码重新发布，也便于审计和多环境差异化。硬编码适合规则稳定、变更少的场景，规则会频繁变时应该配置化。这是我会主动指出的可改进点。

### 99. 这类 ETL 工具的正确性你怎么保证？
**为什么问**：考察质量保障。
**参考回答**：一是**diff 报告**本身就是一层校验，每次转换都能看到新增/删除/重名，异常数量能立刻发现问题；二是对关键转换（货币、地域、年龄段解析）写单元测试覆盖边界；三是小批量试跑后人工抽检输出的 SDK 对象是否符合预期；四是用异常类型区分失败原因，转换失败的记录不会静默丢弃。核心是"让每次运行都可对账、可解释"。

## 八、服务与集成：Shoplazza / 孤儿图片清理 / 邮件通知 / 安全

### 100. Shoplazza × Merchant Center 集成整体架构是怎样的？
**为什么问**：考察后端/集成系统设计。
**参考回答**：是一个多层 .NET 解决方案：Backend 是 ASP.NET Core REST API（对外接口和页面）；Business 层放业务逻辑、OAuth/token 管理、异常处理、DTO；AutoSyncScheduler 负责定时触发同步任务；AutoSyncProcessor 是后台处理器，做商品数据转换并更新 Merchant Center 库存；Infra.Common 放共享的 HTTP 客户端和配置工具。职责分层清晰，调度和处理分离，支持 Dev/Prod/SI/TIP 多环境配置。

### 101. 商品自动同步的调度器和处理器为什么要拆开？
**为什么问**：考察解耦设计。
**参考回答**：拆开是为了**关注点分离和可伸缩**。Scheduler 只管"什么时候该同步、触发哪些任务"，Processor 只管"具体怎么把商品数据拉取、转换、推送到 Merchant Center"。这样调度逻辑和处理逻辑可以独立演进、独立扩展（处理慢就加 Processor 实例），也便于失败重试——调度产生任务、处理消费任务，天然适合队列化。

### 102. OAuth 鉴权你是怎么处理 token 的生命周期的？
**为什么问**：考察鉴权实现。
**参考回答**：Shoplazza 用 OAuth，我要管理 access token 的获取、缓存和刷新。核心是：token 有有效期，要缓存起来复用而不是每次请求都重新换取；快过期时用 refresh token 提前刷新；token 要安全存储，不能明文散落。请求前检查 token 有效性，失效则刷新后重试。这样既减少鉴权请求，又保证调用不因 token 过期失败。

### 103. 孤儿图片清理服务要解决什么问题？为什么复杂？
**为什么问**：考察复杂业务系统设计（对应最大的 helper 项目）。
**参考回答**：广告系统里会产生"孤儿/已删除但未清理"的图片资产，长期堆积占存储、也有合规问题。这个服务要检测这些图片、通知账户、并安全清理。复杂在于：要区分软删除和硬删除；有 15 个月的保留窗口；要**按 PartitionId 分片**做分布式处理；清理前要**邮件通知且去重**（同一账户不能重复骚扰，要记录已发历史，比如最多发 3 次）；还要支持 SI/CI/PROD 多环境和竞态检测。是"批量数据处理 + 通知 + 生命周期管理"的结合。

### 104. 邮件通知去重具体怎么实现？
**为什么问**：考察幂等/状态管理。
**参考回答**：维护一份**邮件发送历史**（记录哪个账户在什么时候就哪批图片发过通知、发了几次）。每次要发之前先查历史，已经发过且未到再次通知条件的就跳过，最多发预设次数（如 3 次）。这本质是幂等：作业重跑或每日运行都不会导致重复发送。关键是把"已通知"状态持久化，而不是靠运行时内存，这样跨运行也能去重。

### 105. 按 PartitionId 分片处理是怎么做的？为什么要分片？
**为什么问**：考察分布式处理。
**参考回答**：数据量大，单批处理不现实，所以按 PartitionId（用 PartitionId 对分片数取模映射到分片）把数据水平切成多份并行处理，每片独立跑。分片的好处是并行加速、单片失败可单独重跑、也便于灰度（先跑几个分片验证）。用取模映射能让数据比较均匀地落到各分片，避免倾斜。

### 106. 每日邮件通知管道（新增/高效图片）是怎么识别"新增"的？
**为什么问**：考察增量对比逻辑。
**参考回答**：用**今天与昨天的差分**。取今天的图片标注快照和昨天的对比，找出新出现的（今天有昨天没有的），再和广告效果数据（UnifiedLayerPerf）关联，筛出有曝光、有效果的图片对应的账户。数据是小时级分区的，我用 STREAMSET 按时间范围抽取。识别"新增"的核心是有稳定的历史快照做对比基准。

### 107. 处理小时级分区数据、按时间范围抽取，SCOPE 里怎么写？
**为什么问**：考察时序数据处理。
**参考回答**：用 `EXTRACT FROM STREAMSET` 配合路径里的时间占位符模式（如 `%Year/%Month/%Day/%Hour...`）做范围抽取，一次把某个时间区间内的多个小时分区都读进来。好处是不用手写循环拼路径，SCOPE 会按模式匹配到区间内所有分区文件。要注意时区和边界，确保抽的是目标业务日的正确小时范围。

### 108. KQL 自动生成工具（基于 CredScan）是干嘛的？核心逻辑是什么？
**为什么问**：考察安全工具与代码生成。
**参考回答**：它是为**凭据扫描**服务的：从 CredScan 库拿到一大批凭据识别的正则前置过滤器，自动生成一段 KQL，把日志/数据里匹配这些正则的记录打上凭据类别标签并筛出来。核心逻辑是把上百条正则编译成**嵌套的 IIF 语句**（`iff(matches regex1, "cat1", iff(matches regex2, ...))`），最后 `where category != 'NoMatch'` 只留命中的。还要处理正则里特殊字符的转义。价值是把人工写几百条规则的 KQL 自动化了。

### 109. 为什么用代码生成 KQL 而不是手写？
**为什么问**：考察自动化思维。
**参考回答**：因为规则有上百条且会更新，手写又长又容易错，改一条要动一大段。用程序从权威的规则源（CredScan）自动生成，保证 KQL 和规则库一致、更新规则只需重新生成、还消除了手工转义出错的风险。这是典型的"用代码消除重复劳动和人为错误"，也让安全规则的维护单点收敛在规则库。

### 110. 日志解析提取 Asset ID（TestExtractFunction 那类）有什么坑？
**为什么问**：考察字符串/解析健壮性。
**参考回答**：坑在于日志里的数据是**多层转义的**——JSON 字符串里又嵌了转义的 JSON，还有逗号分隔的 ID 列表混在事件参数里。要先正确反转义，再解析出内层结构，才能拿到 image ID / asset ID。健壮性上：对解析不出或非法的 ID 返回哨兵值（如 -1）再过滤掉，而不是让异常冒泡；用正则/JSON 解析结合处理不同格式。核心是"永远假设日志数据是脏的，做防御式解析"。

## 十一、LLM / 向量数据库 / 嵌入 通用

### 139. 嵌入（embedding）到底是什么？相似度怎么算？
**为什么问**：AI 基础必问。
**参考回答**：嵌入是把文本/图像等映射到一个高维向量空间，使**语义相近的内容向量也相近**。相似度常用**余弦相似度**（看夹角，不受向量长度影响）或点积/欧氏距离。RAG 就是把文档和查询都嵌入到同一空间，用相似度找最相关的文档。选距离度量要和嵌入模型训练时用的一致（很多用余弦）。

### 140. 向量维度越高越好吗？768 vs 1024 vs 更高怎么选？
**为什么问**：考察嵌入理解。
**参考回答**：不是越高越好。float32 向量的存储和暴力检索成本近似随维度线性增长，高维只有在目标数据上带来可测的 Recall/NDCG 收益才值得。普通模型不能随意截断；只有支持 Matryoshka 的模型才能在其允许范围内选 256/512/1024 等维度，并且截断后要按模型要求归一化。我的做法是冻结语料和 golden query，对不同模型/维度比较 Recall@K、NDCG、P95、索引大小和本地推理吞吐；`commit-ai-resolver` 也把模型与维度写入索引契约，改变配置必须重建，避免 query/document 向量空间不一致。

### 141. chunk 大小怎么定？太大太小分别有什么问题？
**为什么问**：RAG 核心调参。
**参考回答**：太小，单个 chunk 语义不完整、上下文断裂，检索到也没法回答；太大，一个 chunk 混入多个主题，稀释相关性、还浪费上下文预算。要在“语义完整”和“聚焦”之间平衡，并加适度 overlap 保衔接。代码知识库更适合按函数、类、文件等 AST 语义边界分块；Commit 检索则以结构化 Commit 记录作为检索单元，并通过离线评测确定最终粒度。

### 142. 检索的 top-k 怎么选？k 越大越好吗？
**为什么问**：考察检索调参。
**参考回答**：k 太小可能漏掉相关内容；k 太大会引入噪声、占满上下文、增加成本，还可能让 LLM 分心。要在召回和精度/预算间平衡，通常几个到十几个。我会结合重排：先召回较多候选，重排后只把最相关的少数几个喂给 LLM。所以"召回阶段 k 大一点、生成阶段精选"是常见策略。

### 143. 什么是 reranking？为什么召回后还要重排？
**为什么问**：考察检索进阶。
**参考回答**：召回阶段（向量检索）追求快和高召回，用的是相对粗的相似度，排序不一定最优。重排用更强但更慢的模型（如 cross-encoder，把查询和文档一起编码判相关性）对召回的候选精细打分重新排序，把真正最相关的顶上来。"先粗召回、再精排"是检索系统的经典两阶段架构，兼顾效率和效果。

### 144. LLM 的 temperature、max_tokens 这些参数你怎么设？
**为什么问**：考察实用调参。
**参考回答**：temperature 控制随机性：需要确定、可复现的任务（如基于检索的问答、代码/结构化输出）我设低（0.2 甚至更低）减少幻觉；需要创造性的才调高。max_tokens 控制输出长度上限，按场景设，避免过长浪费或被截断。RAG 场景我普遍用低温度 + 适中 max_tokens + 强约束提示词，目标是稳定、忠于上下文。

### 145. 怎么控制 LLM 应用的成本和延迟？
**为什么问**：考察生产化考量。
**参考回答**：几招：缓存稳定且高频的模型或检索结果；用检索与重排减少喂给模型的 token；对简单任务用小模型、复杂任务才用大模型；通过批处理和异步提升吞吐；控制上下文长度并监控每次调用的 token、延迟与费用。核心是“少喂、复用、按需选模型”。

### 146. Prompt 里怎么防止注入攻击（prompt injection）？
**为什么问**：AI 安全，加分项。
**参考回答**：RAG 里检索到的内容可能含恶意指令（"忽略之前的指令…"）。防护：一是**把用户/检索内容和系统指令分离**，明确告诉模型检索内容只是"资料"不是"指令"；二是对输出做校验/过滤，尤其是会触发工具调用的场景要限制工具权限；三是最小权限原则，不让 LLM 直接执行高危操作。这也是我在评估工具输出时会保持警惕的点——不盲目信任外部内容。

### 147. LangChain 帮你解决了什么？有没有觉得它的局限？
**为什么问**：考察对框架的批判性认识。
**参考回答**：LangChain 提供了现成的抽象：LLM 封装、检索器、chain、agent、工具集成，让我快速把"检索→组装上下文→调用 LLM→格式化"串起来，少写胶水代码。局限是：抽象层多、有时不够透明、调试和定制复杂链路会有黑盒感，版本迭代快、API 变动多。所以核心链路我倾向理解它底层做了什么，必要时绕过抽象自己实现关键部分，而不是完全依赖框架。

### 148. LangChain 接 SQL Server 做自然语言查数，风险在哪？
**为什么问**：考察 Text-to-SQL 安全（对应 LangChain 项目）。
**参考回答**：最大风险是**生成的 SQL 不可控**：可能误删改数据、拖垮库、或被注入。防护：一是**只读连接/最小权限账户**，禁掉写和 DDL；二是加超时和行数限制，防跑垮；三是对生成 SQL 做校验或只允许白名单模式；四是敏感表/列做屏蔽。让 LLM 生成查询很方便，但一定要在"沙箱+最小权限"里跑，绝不用高权限账户直连生产库。

### 149. 你怎么持续跟进快速变化的 LLM 技术？
**为什么问**：考察学习能力（换 AI 岗关心）。

## 十二、系统设计与行为面综合

### 151. 让你设计一个"广告推荐机会度量平台"，你会怎么做？
**为什么问**：系统设计题。
**参考回答**：分层设计。**数据接入层**：从各数据源（遥测、结构化事件）抽取，统一到数仓视图。**计算层**：批处理（SCOPE/Spark）做机会识别、采纳度量、收入归因，设计成幂等可回填。**打分层**：多因子打分+归一化+可配置规则排序，带版本管理。**存储层**：采纳历史快照 + 高效序列化（Bond）。**服务/消费层**：输出给推荐系统和 BI。**质量层**：贯穿的数据校验、监控告警、A/B 验证。关键权衡是时效（批 vs 流）、成本（存储保留窗口）、可解释性（规则 vs ML）。

### 152. 设计一个能扛住千万级 QPS 查询的向量检索服务，你会考虑什么？
**为什么问**：AI 系统设计题。
**参考回答**：几点：用 **ANN 索引**（HNSW）保证单查询毫秒级；**分片（sharding）**把向量分布到多节点水平扩展，**副本**扛读并发和高可用；**缓存**热点查询；**批量化**请求提升吞吐；查询前做**预过滤**（用元数据缩小候选）。还要考虑索引更新（增量 vs 重建）、召回率与延迟的参数权衡、监控（延迟、召回、资源）。存储上向量和元数据分离，各用擅长的系统。

### 153. 你怎么权衡"快速交付"和"工程质量"？
**为什么问**：行为面高频。
**参考回答**：看场景分级。探索性/一次性的东西（比如某个分析、mock 数据）我会快速实现、不过度设计；进生产、要长期维护、影响面大的（指标管道、度量框架）我会投入做幂等、测试、监控。原则是"匹配投入和风险"：验证想法时求快，沉淀为生产系统时求稳。我做视频工具时先跑通再优化性能，做指标平台时一开始就重视幂等，就是这种权衡。

### 154. 讲一次你解决的最有挑战的技术问题。
**为什么问**：行为面经典。
**参考回答**（STAR）：**情境**：早期指标管道直接往主表追加，作业失败重跑或上游补数就导致数据翻倍错乱，运维频繁救火。**任务**：让管道能安全重跑和回填而不污染数据。**行动**：我重构成"staging + 按主键去重合并"的幂等模式，把回填做成按日期分区的独立操作，梳理每个指标的主键、处理迟到数据、迁移历史数据。**结果**：作业变得可放心重跑，回填精确到天，运维成本大幅下降，也成了后续新指标遵循的标准模式。

### 155. 讲一次你主动学习新技术并落地的经历。
**为什么问**：考察主动性和成长。

### 156. 你和同事在技术方案上有分歧时怎么处理？

### 157. 你 code review 时最看重什么？
**为什么问**：工程文化。
**参考回答**：正确性优先（尤其是边界、空值、并发、幂等这些容易错的），其次是可维护性（命名、抽象是否合理、有没有魔法数字/重复代码），再是测试覆盖关键逻辑。对数据代码我特别关注口径（分子分母、分析单元、时间边界）和性能（有没有不必要的 shuffle/全表扫描）。我倾向给出建设性的、能解释"为什么"的意见，而不是只说"这样不好"。
