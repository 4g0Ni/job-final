1. 两个项目的技术主线很互补：`adocag-server` 适合讲**代码知识库、分层图 RAG、索引构建和检索模式**；`commit-ai-resolver` 适合讲**多角色流水线、迭代检索、MCP、RRF、评测与 guardrail**。

# A. AI 项目事实、个人贡献、技术深度与简历 bullet

## A1. `adocag-server`：可确认事实与风险口径

### 可确认项目事实 [材]

- 定位：面向代码仓库的知识库/Wiki 生成服务，采用 HiRAG/分层图 RAG 思路；它当前更准确地说是**固定多阶段 pipeline**，不是自主 ReAct Agent。
- 核心链路：代码解析/AST 分块（tree-sitter）→ 实体关系抽取 → Leiden 图聚类 → 社区摘要 → 分层检索 → Wiki/回答生成。
- 检索模式：材料列出 `hi`、`hi_llm`、`hi_local`、`hi_global`、`hi_bridge` 等模式；适合讲细粒度代码问题与全局架构问题的检索差异。
- 工程形态：FastAPI、异步服务、SSE；材料还提到多 LLM 后端、Azure DevOps、Blob/Table 存储及索引刷新。
- `deep_research` 当前是最多 5 轮的关键词扩展，有界循环；`quality_check ≥ 8` 是 LLM 对关键词/结果的内部质量判断，**不是独立评测体系**。
- 已知问题：LLM 缓存默认关闭；`get_graph` 中同步事件循环调用可能导致空图自愈路径在 FastAPI 运行循环内失效；CORS `*`、JWT 不验签等安全边界需如实说明。

### 可证实技术深度（面试应展示什么）

1. **为什么图/分层检索适合代码仓库**：代码具有函数—文件—模块—业务域层级；普通 chunk 向量检索容易只拿到局部片段，社区图摘要更适合全局架构问题。
2. **索引构建而非只会调 API**：能解释 tree-sitter 为什么优于纯固定长度切分、实体/关系如何进入图、Leiden 的输入输出、社区摘要何时重建。
3. **查询路由**：函数/文件定位偏 local；架构/跨模块依赖偏 global/bridge；路由应由可解释规则或分类器决定，并由离线集验证。
4. **增量与规模瓶颈**：全图聚类重算、内存常驻、仓库隔离、索引热切换、一致性和失败回滚。
5. **诚实区分 pipeline 与 Agent**：当前是固定执行图；只有模型根据观察自主决定下一步工具、并有停止条件时，才更接近 Agent。[官：Anthropic]

### 个人贡献边界

材料只能证明“项目存在这些模块/设计”，不能证明“你独立设计并实现了它们”。面试前逐项填表：模块、你写的文件/PR、你做的设计决策、失败案例、测试证据、线上指标。答法建议：

> 团队项目整体是……；我直接负责的是……；我参与但非 owner 的是……；材料中 eval harness/缓存量化目前属于改进设计，尚未上线，不能当成既成结果。

### 当前可安全写的简历 bullet（仍需确认确为本人工作）

- 参与构建面向大型代码仓库的分层图 RAG 服务，使用 tree-sitter 进行 AST 语义分块，经实体关系抽取、Leiden 社区聚类与社区摘要支持代码 Wiki 生成和多粒度检索。
- 设计/维护 FastAPI + SSE 查询链路，支持 local/global/bridge 等分层检索模式，并针对函数级与架构级问题采用不同检索路径。
- 梳理索引构建与刷新链路，定位事件循环、缓存配置及鉴权/CORS 等工程风险，并给出异步化、可观测性与权限收敛方案。

### 只有真实落地后才能写 [推]

- “构建 N 条 golden set，以 Recall@K/MRR 比较多种检索模式，Recall@K 从 A 提升到 B。”
- “开启并验证 LLM 缓存，将重建耗时从 X 降至 Y、token 成本下降 Z%。”
- “修复 FastAPI 事件循环中的空图自愈路径，并补充请求上下文回归测试。”

不得使用本地材料里的占位数字 X/Y/Z，也不得把示例“P95 2s→600ms”写成自己的数据。

## A2. `commit-ai-resolver`：可确认事实与风险口径

### 可确认项目事实 [材]

- 定位：回答“某 bug/需求由哪次 commit 引入或解决”的 commit 分析系统。
- 核心链路：Intent Extractor → RAG 检索 → Answer Synthesizer → Answer Evaluator；回答不足时反馈重试，最多 3 轮，并用停滞信号提前结束。
- 检索：实际代码使用 `sqlite-vec`，不是旧文档中的 LanceDB；复杂问题最多生成 3 路查询，以 RRF 融合；可带 repo/author/date/risk/changeType 等过滤。
- Guardrail：回答只能基于检索到的 commit；材料提到低结果数、低相似度时做 confidence clamp。
- MCP：作为 MCP Server 通过 Streamable HTTP 暴露 6 个工具，包括语义检索、按 ID 查询、日期/工单摘要、真实 diff 等；Web 与 MCP 入口统一日志。
- 部署：材料纠正为 Azure App Service，而非“真正的 Static Web Apps”。
- 已有评测资产：`SEARCH-QUALITY.md` 记录 18 个 bug 修复前后人工评分；这是有价值的工程证据，但当前不是自动化回归 harness。
- 已知问题：风险/变更类型在 JS 端 post-filter，规模增大时性能退化；测试依赖真实预生成数据；作者 LIKE 子串匹配会误判；会话只保留最近 4 条；缺少集中 token/cost 追踪。

### 可证实技术深度

1. **为什么 sqlite-vec**：当前约 2300 条 commit/短时间窗口，嵌入式单文件、部署简单；若多年全组织数据增长，再讨论 pgvector/Qdrant、ANN 索引与分片。
2. **RRF**：对每路排名按 `1/(k+rank)` 累加，不要求不同检索器分数同尺度；需说明 query 变体的互补性、去重和 k 的选择。
3. **Evaluator 不是万能真值**：LLM 主观评分 + 检索相似度/结果数量/引用存在性等客观规则 + 人工抽检；避免“让另一个 LLM 再评一次”形成伪验证。
4. **为什么不用 LangGraph/CrewAI**：当前是固定 4 角色顺序 + 有界循环，原生 JS 更透明；只有动态路由、持久状态、人机中断显著复杂时再引入状态图框架。
5. **MCP 边界**：MCP 负责 host/client/server 间上下文与工具协议，不负责决定 Agent 如何规划，也不自动提供权限安全。[官：MCP]

### 当前可安全写的简历 bullet（仍需确认本人贡献）

- 构建多角色 commit 语义分析流水线，将意图抽取、sqlite-vec 检索、答案合成与质量评估解耦，并通过最多 3 轮的有界反馈机制处理低质量回答。
- 对复杂问题并发生成多路检索查询并使用 RRF 融合排名，结合仓库、日期、作者和风险等级等元数据缩小候选 commit。
- 实现 Streamable HTTP MCP Server，将 commit 语义搜索、精确查询和 diff 获取等 6 项能力暴露给 IDE/Agent 客户端，并统一 Web/MCP 调用日志。
- 通过引用约束、相似度/结果数置信度钳制及停滞检测减少 commit 幻觉和无效重试；维护 18 个历史 badcase 的修复对比记录。

### 只有真实落地后才能写 [推]

- “将 18 个历史 badcase 与 10 个固定 use case 自动化为 CI eval gate。”
- “把 riskLevel/changeType 下推到存储层索引，P95 从 X 降到 Y。”
- “会话摘要持久化后 token 成本下降 Z%，且关键约束保留率达到 Q。”

# B. AI Agent 高频题与高质量答案要点

## B1. Agent 通用

### Q1：Workflow 与 Agent 的分界是什么？什么时候不用 Agent？ [帖+官]

- Workflow 的路径/分支由人预先定义；Agent 根据目标与观察动态决定下一步。
- 确定、稳定、合规要求高的任务优先 workflow；输入开放、步骤不可预知、工具反馈会改变计划时才用 Agent。
- Agent 用性能换灵活性，通常增加延迟、成本和失败面。Anthropic 明确建议从最简单方案开始，单次 LLM + RAG 足够时不要上 Agent。
- 结合项目：`adocag-server` 当前应叫有界检索 pipeline；`commit-ai-resolver` 是角色化 workflow + evaluator 反馈，Agent 性取决于模型是否真正动态改写策略。

### Q2：ReAct、Plan-and-Execute、Reflection 怎么选？ [帖+官]

- ReAct：Thought/Action/Observation 交替，适合环境反馈强、步骤短；风险是循环和上下文膨胀。
- Plan-and-Execute：先计划再分步执行，适合长任务；需允许计划因新证据重规划。
- Reflection：生成后由 critic/规则检查并修订；必须有最大轮数、停止条件，且不能把自评当真值。
- 生产护栏：`max_steps + timeout + cost budget + no-progress detector + 可返回当前最优结果`。

### Q3：上下文爆炸与记忆污染怎么处理？ [帖]

- 上下文分层：系统约束、任务状态、近期原文、工具结果、可检索长期记忆；不同层不同保留策略。
- 压缩前抽取不可丢约束（目标、文件、失败尝试、待办、证据 ID）；压缩后做结构化校验，不只让同一模型说“没问题”。
- 长期记忆加来源、时间、版本、置信度和过期策略；新证据覆盖旧结论但保留审计历史。
- 测试：构造必须跨 10+ 轮保留的硬约束，比较压缩前后任务成功率、约束保持率、token 降幅。

## B2. RAG

### Q1：完整 RAG 链路如何讲？ [帖+官]

- 摄取：解析/OCR/清洗/去重 → 语义分块 + 元数据 → embedding/倒排/图索引。
- 查询：意图识别、过滤条件、query rewrite/HyDE → 稀疏+稠密召回 → RRF/加权融合 → rerank → 上下文拼装 → 有引用生成。
- 评测拆开：检索用 Recall@K、MRR、nDCG；生成用 groundedness/faithfulness、answer relevance、引用正确率、人工任务成功率；线上加延迟、成本、空召回率。
- badcase 必须先定位是解析、分块、召回、排序、上下文还是生成问题，不能一律“改 prompt”。

### Q2：BM25 + 向量为什么混合？权重怎么定？ [帖+官]

- BM25 擅长精确术语、错误码、文件名；向量擅长语义改写。代码/commit 场景二者互补。
- 首选 RRF 规避分数尺度不一致；若加权融合，先校准分数，再在按问题类型分层的验证集上网格搜索。
- 不能只报一个全局权重；应按实体查询/自然语言查询分桶，对 Recall、MRR、延迟做消融。

### Q3：分块怎么选？ [帖]

- 优先保持语义边界；代码用 AST，文档用标题/段落/表格；超长节点再固定 token 兜底。
- overlap 能减少边界信息丢失，也增加重复召回和成本；用 parent-child / small-to-big 在小块检索后回填父上下文。
- PDF 要先解决版面、页眉页脚、表格和 OCR，不能把“递归字符切分”当完整 PDF 方案。

### Q4：Agentic RAG 何时值得？ [帖+官]

- 固定 RAG 适合单跳、查询明确、延迟敏感；Agentic RAG 适合需要查询改写、多跳、补检、工具选择或证据冲突处理的 badcase。
- 收益必须在特定 badcase 集上证明；同时设最大补检轮数、并发限制、缓存和早停，报告质量—延迟—成本 Pareto。
- Self-RAG 的关键不是“多检索”，而是按需决定是否检索并反思证据相关性；论文做法涉及训练 reflection token，不能把普通 prompt 自评冒充完整 Self-RAG。

### Q5：HyDE 原理与风险？ [官]

- 先生成假想文档，再对假想文档编码以检索真实文档，缩小 query-document 表达差异。
- 假想文档可能含假事实；它只用于定位语义邻域，最终答案必须由真实语料落地。对精确 ID/代码符号查询未必优于 BM25。

## B3. 工具调用与 MCP

### Q1：模型如何调用工具？ [帖+官]

- 应用把工具名、描述、JSON Schema 和约束发给模型；模型返回 tool call；应用侧验证参数/权限并执行；结果作为 tool output 回传；模型继续调用或生成最终答案。
- 工具描述要明确适用/不适用条件；参数做 schema 校验和业务校验；外部文本一律视为不可信数据。
- 失败分类：可重试瞬态错误（指数退避+jitter）、不可重试参数/权限错误（向模型返回可操作诊断）、有副作用操作（幂等键/审批/补偿）。

### Q2：MCP 解决什么，内部是什么？ [帖+官]

- MCP 是 host—client—server 架构；host 为每个 server 建立独立 client 连接。数据层基于 JSON-RPC，常见 primitives 是 tools、resources、prompts。
- 本地常用 stdio；远程常用 Streamable HTTP。初始化时协商协议版本与能力。
- MCP 只标准化上下文/能力交换，不规定模型如何规划，也不等于自动安全。生产上仍需认证、授权、最小权限、审计、参数验证和用户确认。

### Q3：Skill、Tool、MCP、A2A 的区别？ [帖+官]

- Skill：教 Agent 怎样完成某类任务的能力说明/脚本资产。
- Tool：一次可调用的具体能力。
- MCP：Agent 应用与工具/资源的标准协议。
- A2A：独立 Agent 之间发现、能力声明、任务与消息协作的协议；与 MCP 互补，不是替代关系。

## B4. 多 Agent

### Q1：多 Agent 一定优于单 Agent 吗？ [帖+官]

- 否。只有角色需要不同工具/权限/上下文、任务可并行、或独立 reviewer 能带来可测收益时才拆。
- 代价：通信 token、延迟、状态一致性、冲突、责任不清、调试困难。
- 做单 Agent vs 多 Agent 消融：任务成功率、P95、token、工具错误率；没有显著净收益就回退简单架构。

### Q2：如何协作、传状态、避免冲突？ [帖]

- 用显式共享状态 schema，不传整段自由文本；每个 Agent 定义输入、输出、允许工具、完成条件。
- Supervisor/状态图负责任务分配；写操作用资源 owner、版本号/乐观锁或串行 commit；冲突交给规则或 reviewer 仲裁。
- 每一步带 `task_id/trace_id/parent_step/evidence/status`，允许重放与恢复。

### Q3：多 Agent 如何评测？ [帖+官]

- 端到端成功率之外，测路由正确率、子任务完成率、handoff 丢失率、冲突率、无效通信、轮数、成本与延迟。
- 故障注入：某 Agent 超时、返回错 schema、工具不可用；验证重试、降级、接管与幂等。
- 逐节点 trace + 固定数据集 + 版本对比；否则无法判断 badcase 应修哪个 Agent。

## B5. 评测与可观测性

### Q1：如何搭 Agent Eval Pipeline？ [帖+官]

1. 从真实任务、历史 badcase、边界/对抗样例构成分层数据集，固定版本和切分。
2. 明确成功标准：确定性字段用代码 evaluator；语义质量用 rubric/LLM judge；高风险样本人工复核。
3. 运行多次以估计随机性；对候选版本做 paired comparison，报告均值、方差和失败类别，而非单一总分。
4. 离线回归作为 CI gate；线上采样做持续 evaluation，并将新 badcase 去重后回流。

### Q2：LLM-as-judge 不准怎么办？ [帖+官]

- judge 与生成模型解耦、隐藏候选身份、交换答案顺序检测位置偏差；rubric 要可判定并给证据。
- 与人工标注集校准一致率；对低一致/高风险样本人工仲裁。
- 叠加代码可验证指标：引用是否存在、commit ID 是否真实、工具参数是否有效、检索证据覆盖。
- “再让另一个 LLM 评一次”只能减少部分随机误差，不能消除共同偏差。

### Q3：生产观测什么？ [官+帖]

- 每个 trace：模型/prompt/索引版本、每步输入输出摘要、工具名/参数哈希/状态、重试、token、成本、延迟、检索文档 ID、最终引用。
- 服务黄金信号：latency、traffic、errors、saturation；Agent 特有：任务成功率、步骤数、无进展循环、工具选择/参数准确率、空召回、用户纠正率。
- 敏感信息脱敏；原始 prompt/tool output 设访问控制和保留期限。

## B6. 安全

### Q1：Prompt Injection 为什么不能只靠提示词解决？ [官]

- 外部网页、文档、工具结果可夹带指令；模型不能可靠区分“数据”和“指令”。
- 防护是系统级：不可信内容隔离、最小工具权限、allowlist、参数验证、敏感源与危险 sink 间的策略门、用户确认、沙箱、审计。

### Q2：Agent 最典型风险？ [官]

- Prompt injection、敏感信息泄露、供应链/模型或 embedding 污染、输出处理不当、过度代理权、系统提示泄漏、向量与 embedding 弱点、错误信息、无界资源消耗（OWASP 2025）。
- 对代码 Agent：文件路径沙箱、命令 allow/deny、网络与 secret 隔离、patch diff 审批、测试后再提交、可回滚快照。
- 对 MCP：server 不是天然可信；server 身份、用户授权、tool 元数据变更、token 传递和日志泄密都要控制。

## B7. LLM 基础

### Q1：为什么主流生成模型多为 Decoder-only？ [材]

- 单一 next-token 目标与自回归生成一致；训练/推理接口统一，易于规模化和 in-context learning。
- 不能答成“Decoder-only 理论上一定优于 Encoder-Decoder”；这是工程与经验选择，判别/表征任务仍可能适合 encoder。

### Q2：Self-Attention、Q/K/V 与位置？ [帖]

- 每个 token 生成 Q/K/V；Q 与 K 相似度经缩放 softmax 得权重，再加权 V。多头捕获不同关系。
- 同一 token 在不同位置的输入表示因位置编码和上下文不同而不同；因果 mask 保证生成时只看左侧。
- 长上下文瓶颈包括注意力计算/显存、KV cache、信息利用退化，不只是模型宣称的窗口长度。

### Q3：PPO、DPO、GRPO？ [材]

- PPO RLHF 通常有 policy/reference/reward/value，链路复杂但可在线优化策略。
- DPO 直接从偏好对优化相对偏好目标，省去显式 reward model 与在线 RL；“与 RLHF 完全等价”需附带理论假设，面试不要绝对化。
- GRPO 用同题多样本组内相对奖励估计优势，省 value model；仍依赖奖励设计、采样和稳定训练。

### Q4：推理优化怎么答？ [帖]

- 区分 prefill 与 decode；continuous batching 提升调度利用率，KV cache 避免重复计算历史 token，量化降低显存/吞吐成本。
- 指标需同时看 TTFT、TPOT、吞吐、P95/P99、显存、质量回退；不要只背 vLLM 名词而没有测量。

# C. 其他来源的通用高频题

## C1. 前端通用 [帖/公开手册]

高频簇：

- JavaScript：事件循环（macro/microtask）、闭包、原型链、`this`、Promise、深浅拷贝、ES module、内存泄漏。
- 浏览器：输入 URL 全链路、渲染流水线、重排/重绘、缓存、CORS/CSP、cookie/session/token、XSS/CSRF。
- React/Vue：响应式原理、state 更新与批处理、虚拟 DOM/diff、hooks 闭包、组件通信、SSR/CSR/hydration。
- 性能：Core Web Vitals、代码分割、懒加载、图片策略、长任务、性能采样和回归。
- 前端系统设计：大文件上传、实时聊天、无限滚动、设计系统、微前端、可访问性。

高质量答法：定义只是 20%；必须补“触发条件—底层机制—真实 bug—如何观测/验证—取舍”。结合项目可讲 SSE 为什么适合模型单向流式输出，以及断线重连、事件 ID、背压和取消。

## C2. 后端通用 [帖+官]

- 并发：线程/协程、Python GIL、Lock/RLock、异步 I/O；何时会阻塞事件循环。
- 数据库：B+Tree、联合索引最左前缀、事务隔离、MVCC、慢查询、分页；向量索引与元数据过滤如何协同。
- Redis：缓存穿透/击穿/雪崩、分布式锁、Lua 原子性、固定/滑动窗口限流。
- 分布式：幂等、重试与指数退避+jitter、超时、熔断、消息重复、最终一致性、事务 outbox。
- API：REST、SSE、WebSocket、认证/授权、版本化、结构化错误码、可观测性。
- 测试：单元/集成/契约/E2E，mock 边界，fixture 与生产数据隔离，覆盖率不等于质量。

高质量答法：先判断错误是否瞬态；重试必须有限、有 backoff、有 jitter、有幂等；永久错误/权限错误不能盲重试。[官：AWS]

## C3. 系统设计 [公开手册+公司资料]

常见题：短链、Feed、聊天、搜索/推荐、文件存储、限流器、通知、Ticketmaster/抢票；AI 岗还会问企业 RAG、代码 Agent、模型网关、评测平台。

统一框架：

1. 澄清功能/非功能需求与不做什么。
2. 估算 QPS、数据量、带宽、读写比和 SLO。
3. 定义 API、核心数据模型与一致性要求。
4. 画高层数据流，再深挖数据库、缓存、队列、索引、分片与故障处理。
5. 明确瓶颈、监控、容量、降级、安全和成本；主动讲取舍而不是堆组件。

AI 系统设计附加项：模型/提示词/索引版本、token budget、检索证据、离线/在线 eval、危险工具审批、缓存键、模型降级与回滚。

## C4. 行为面 [公开手册+牛客]

高频题：最大挑战/失败、意见冲突、模糊需求、推动跨团队、紧急事故、优先级取舍、影响力、为何离职、为何该公司、如果重来怎么做。

用 STAR-L：Situation/Task 控制在 20%，Action 重点写“我”而不是“我们”，Result 给可核实指标，Learning 说明复盘后改了什么。每个项目至少准备：

- 一次检索/评测 badcase 如何定位和修复；
- 一次性能/成本取舍；
- 一次错误选型或文档漂移复盘；
- 一次与产品/后端/前端协作；
- 一次主动发现安全/可靠性风险。

避免：把团队结果全归个人、使用占位指标、把尚未实现的改进说成已上线。

# E. 建议的面试准备优先级

1. **先校准简历真实性**：给两个项目各做一张“模块—个人贡献—PR/文件—测试—指标”证据表；删掉假设已完成和占位数字。
2. **各准备 3 分钟 + 10 分钟版本**：业务目标→链路→你的边界→关键选型→一个 badcase→量化→下一步。
3. **优先真正落地两项**：`adocag-server` 的检索 golden set/Recall@K/MRR；`commit-ai-resolver` 的 18 case 自动回归 + 客观 evaluator。它们最能把 Demo 变成工程项目。
4. **准备四组消融**：local/global；向量/BM25/混合；单 Agent/多 Agent；LLM judge/客观规则/人工复核。
5. **背答案不如做证据**：至少带一张 eval 表、一条 trace、一份 badcase 根因树、一组质量—延迟—成本对比。
